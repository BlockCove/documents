一、整体架构概述

Optimism 采用 Optimistic Rollup 技术方案，其标准跨链桥（Standard Bridge）构建在跨域消息传递系统（Cross Domain Messenger）之上，实现了 L1 以太坊与 L2 OP 链之间的资产双向转移。

核心设计思想： L1 托管资产 + L2 映射资产。存款时资产锁定在 L1（ETH 由 OptimismPortal 托管、ERC20 由 L1 桥托管），L2 铸造等额映射代币（ERC20）或转入等额原生 ETH；提款时 L2 销毁映射代币（或扣回 ETH），L1 释放对应资产。

二、ETH 从 L1 跨链到 L2（存款）

ETH 是以太坊原生资产，存款流程相对简单。用户将 ETH 发送到 L1 桥合约后，L2 会自动向用户地址转入等额原生 ETH。

2.2 详细步骤

  1. 用户发起存款交易：调用 L1StandardBridge.depositETH() 或 depositETHTo()，随交易发送 ETH。
  2. L1 托管 ETH：ETH 随跨域消息转入 OptimismPortal 合约托管（Bedrock 起存款 ETH 不再存放于 L1 桥合约）。
  3. 构造跨域消息：L1 桥调用 L1CrossDomainMessenger，封装对 L2StandardBridge.finalizeBridgeETH 的调用。
  4. 写入 Portal：消息通过 OptimismPortal 的 depositTransaction 写入 L1，触发存款事件。
  5. Sequencer 拾取：L2 排序器监听 L1 存款事件，将其作为 L2 存款交易纳入区块。
  6. L2 执行 finalizeBridgeETH：L2CrossDomainMessenger 中继消息，调用 L2StandardBridge。
  7. 用户收到 ETH：L2 桥合约将等额原生 ETH 转入用户地址。
耗时： L1 交易确认后约 1~15 分钟到账 L2，取决于排序器打包速度。用户仅需支付 L1 Gas 费。

三、ETH 从 L2 提现到 L1（提款）

提现流程更为复杂，涉及 Optimistic Rollup 的欺诈证明挑战期。提现发起后需等待约 7 天挑战期：期间任何人可对包含该交易的输出根提交欺诈证明，输出根通过挑战期后提现方可最终确认。

3.3 四步提现详解

第一步：发起提现（Initiate Withdrawal）

用户在 L2 向 L2StandardBridge 发送 ETH（receive() 直接触发）或调用 withdrawTo()，ETH 转入 L2 桥合约。交易生成一条跨域消息，随后包含该交易的输出根会被提交到 L1。

第二步：等待输出根提交并通过挑战期

L2 的状态输出根（Output Root）约每小时提交一次到 L1 的 L2OutputOracle 合约。每个输出根都有 7 天的挑战窗口，在此期间验证者可提交欺诈证明。

7 天挑战期的意义： Optimistic Rollup 「乐观假设」交易正确，但留出时间让任何人挑战。只有挑战期内无人成功挑战，状态根才被视为最终确认。这是资金安全的核心保障。

第三步：提交提现证明（Prove Withdrawal）

输出根提交到 L1 后，用户即可调用 OptimismPortal.proveWithdrawalTransaction() 提交 Merkle 证明，证明该提现交易已包含在某个输出根中（此步无需等待挑战期结束）。

第四步：最终确认（Finalize Withdrawal）

输出根通过 7 天挑战期后，调用 finalizeWithdrawalTransaction()，Portal 将托管的 ETH 经 L1 桥释放给用户。（合约要求输出根提案与证明提交均满 7 天，正常流程下二者几乎同时满足。）

⚠️ 2024 年起的现状： OP Mainnet 已于 2024 年 6 月启用无许可欺诈证明（Cannon Fault Proofs），L2OutputOracle 被 DisputeGame 争议游戏合约体系取代，提现证明改为针对争议游戏进行。但用户可感知的提现总等待时间仍约 7 天。本文沿用经典的 L2OutputOracle 模型讲解，便于理解整体机制。

四、ERC20 代币从 L1 跨链到 L2

五、L2 无对应合约的解决方案

这是开发者最常遇到的问题：L1 上有 ERC20 合约，但 L2 上没有对应的映射代币，能直接跨链吗？

答案：不能直接跨链。 Standard Bridge 在 L2 端通过 ERC-165 检测识别 OptimismMintableERC20 并铸造代币；如果 L2 没有对应合约（或未实现接口），L2 端的 finalizeBridgeERC20 会执行失败，存款交易失败，代币滞留 L1 桥合约，且没有自动退款机制。必须先部署映射代币再发起存款。

5.3 方案二：自定义 L2 代币合约

如果需要自定义逻辑（如征税、反射、权限控制等），可以自行部署合约，但必须实现 ILegacyMintableERC20（旧 L2 标准接口）或新版 IOptimismMintableERC20 接口，并通过 ERC-165 声明支持——标准桥正是通过 ERC-165 接口检测来识别「可铸造代币」的。注意 mint/burn 应仅允许桥合约调用，且代币配对地址（l1Token() / remoteToken()）必须准确。

interface ILegacyMintableERC20 { function l1Token() external view returns (address); function l2Bridge() external view returns (address); function mint(address _to, uint256 _amount) external; function burn(address _from, uint256 _amount) external; // ERC-165 接口支持检查（新接口 IOptimismMintableERC20 // 对应 getter 为 remoteToken() / bridge()，标准实现两者都兼容） function supportsInterface(bytes4 _interfaceId) external view returns (bool); }
重要约束：
  • l1Token() / remoteToken() 必须准确返回 L1 对应代币地址，桥合约会校验代币配对
  • mint 和 burn 权限必须仅限 L2StandardBridge 调用
  • 必须通过 ERC-165 声明支持 ILegacyMintableERC20 或 IOptimismMintableERC20 接口
  • 小数位数（decimals）建议与 L1 保持一致，否则数量会有偏差

六、ERC20 代币从 L2 提现回 L1

ERC20 提现流程与 ETH 提现的挑战期机制相同，区别在于资产处理方式：L2 销毁映射代币，L1 释放锁定的原生代币。

6.2 提现核心逻辑

  1. L2 销毁代币：调用 L2StandardBridge.withdraw，桥合约调用 L2 代币的 burn 方法销毁映射代币。
  2. 生成跨域消息：构造调用 L1 桥 finalizeBridgeERC20 的消息，随 L2 状态根提交到 L1。
  3. 等待挑战期：同 ETH 提现，需等待 7 天确保状态根最终确认。
  4. 提交 Merkle 证明：在 L1 证明该提现交易存在于已确认的状态根中。
  5. 最终确认释放代币：调用 finalizeWithdrawalTransaction，L1 桥将之前锁定的 ERC20 代币转账给用户。
注意： 如果 L2 代币合约不标准（如转账收税、实际到账少于转账额），可能导致 burn 数量与 L1 释放数量不一致，引发会计问题。建议使用标准代币实现。
