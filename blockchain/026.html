1. 问题本质：位置寻址 vs 内容寻址

传统 HTTPS URL 主要解决的是“通过某个位置取得资源”。例如 https://example.com/data.json 在 URL 不变的情况下，服务器可以把返回内容替换掉。URL 本身并不承诺响应体的字节内容。

IPFS 的 CID 则是内容寻址标识符：它由内容对应的数据结构的密码学摘要派生而来。IPFS 官方文档明确指出，内容发生变化会产生不同 CID；同一内容只有在使用相同导入/结构化参数时，才会得到相同 CID。[1]

图 1：位置寻址与内容寻址的核心差异
关键区别：URL 标识位置；CID 标识特定内容表示（更准确地说，是对其 IPFS 数据结构的内容指纹）。
必须避免的简化

不能把“CID = 原始文件 SHA-256”作为普遍规律。IPFS 文件通常会先经过分块、DAG 组织和 codec 编码；CID 中的 multihash 通常针对 CID 所代表的根 block，而不是简单地对整个原始文件字节做一次 SHA-256。只有特定的单块 raw 情况下，CID 中的摘要才可以直接等同于文件内容的哈希。[1]

2. 核心机制：CID 到底验证了什么

2.1 CIDv1 的结构

CIDv1 不是“一个哈希字符串”，而是一个由 multibase、CID version、multicodec 和 multihash 共同构成的自描述标识符。Multicodec 描述目标内容的编码形式，Multihash 记录哈希算法、摘要长度与摘要本身。[1]

组成作用示例/说明
Multibase指定 CID 二进制部分采用何种文本编码CIDv1 常见前缀 b 表示 base32
CID Version指出 CID 版本CIDv1 的版本字段为 1
Multicodec指出目标内容/节点的 codec例如 raw、dag-pb
Multihash记录哈希算法、摘要长度和摘要常见为 SHA-256，也支持其他算法

2.2 为什么“相同文件”不一定天然得到相同 CID

IPFS 官方文档特别强调：两个完全相同的文件，也可能因为 chunking、DAG layout、codec、CID 版本或哈希算法不同而得到不同 CID。反过来，想在不同工具/环境中稳定复现 CID，就必须固定这些导入参数。[1]

2.3 大文件与 Merkle DAG

大文件通常会被切分为多个 block，再通过 UnixFS / DAG 结构把这些 block 组织起来。常见 chunk 大小可以是 256 KiB 或 1 MiB，但并不存在一个脱离实现与配置的“IPFS 固定 256 KB 默认值”；chunking 和 layout 都可能影响最终 CID。当前 Kubo 还提供用于跨实现确定性导入的 UnixFS profile，例如 1 MiB chunk 的 unixfs-v1-2025。[1] [2]

因此，Merkle DAG 的价值不是简单的“每个文件都有一个文件级 SHA-256”，而是把多个内容 block 通过 CID 链接起来，最终由根节点的内容标识代表整个数据结构。

图 2：文件的 DAG 结构与完整性验证
篡改任一被引用 block，会破坏该 block 的内容标识并沿 DAG 影响上层内容标识。

3. 智能合约中的正确验证模式

3.1 最重要的架构边界：智能合约不能直接读取 IPFS

原稿中的关键错误已修正

EVM 合约执行时并没有“从 IPFS 下载文件”的能力。合约不能像浏览器一样调用 https://ipfs.io/ipfs/... 或直接读取 IPFS 网络。正确模式是：客户端/后端先从 IPFS 取回数据并完成解析、重构或哈希计算，再把证明材料提交给合约验证。

图 3：正确的链下数据完整性验证流程
重点：IPFS 取数发生在链下；链上验证的是客户端提交的可验证摘要或证明，而不是让合约直接“下载 IPFS”。

3.2 Solidity：用链上 Keccak 做简单锚定

如果业务场景不要求合约理解 CID 的完整结构，而只是希望锚定一份“规范化后的字节序列”，最简单的做法是直接锚定 keccak256(data)。这样与 IPFS CID 是两条不同但可以并存的完整性链路。

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract DataAnchor {
    mapping(bytes32 => bytes32) public contentHashes;

    event DataAnchored(
        bytes32 indexed fileId,
        bytes32 contentHash,
        address uploader
    );

    function anchor(bytes32 fileId, bytes32 contentHash) external {
        require(contentHashes[fileId] == bytes32(0), "already anchored");
        contentHashes[fileId] = contentHash;
        emit DataAnchored(fileId, contentHash, msg.sender);
    }

    function verify(bytes32 fileId, bytes32 contentHash)
        external view returns (bool)
    {
        return contentHashes[fileId] == contentHash;
    }

    function verifyRaw(bytes calldata data, bytes32 expected)
        external pure returns (bool)
    {
        return keccak256(data) == expected;
    }
}
关于 SHA-256 与 EVM 的准确说法

Solidity 同时提供 keccak256 和 sha256 内建函数；SHA-256 并不是“EVM 不支持、只能靠第三方库”。在 Ethereum 主网等标准 EVM 环境中，sha256 通过预编译合约实现。原稿中的“EIP-198 是 SHA-256 预编译”是错误的：EIP-198 对应的是大整数模幂运算（ModExp）；SHA-256 对应的是预编译地址 0x02。[3] [4]

3.3 IPFS CID 与 Keccak 哈希应该如何配合

如果项目既要 IPFS 生态兼容，又要在 EVM 合约里方便验证，可以采用“双锚点”设计：

链上字段作用注意点
CID / CID 编码后的 bytes标识 IPFS 数据应保留 codec / version / hash algorithm 等信息；不要默认把 CID 等同于文件 SHA-256
Keccak-256 digest便于 EVM 合约直接比较/验证必须明确“对什么字节序列计算”——例如规范化 JSON，而不是任意网关响应

若直接把 CID 字符串作为链上存储内容，成本通常会高于存储固定长度 digest。生产系统常见做法是按业务需求保存完整 CID、CID 的 digest/元数据，或保存更高层的数据承诺，而不是无条件把所有字符串原样写入 storage。

3.4 Merkle Proof：证明“某条数据属于已锚定集合”

当业务不是验证整份文件，而是验证“这条记录属于已经在链上承诺过的数据集”时，Merkle Root 很合适。链上保存 root；用户提交 leaf 与 proof，合约重新计算根并比较。

function verifyMerkle(
    bytes32 root,
    bytes32 leaf,
    bytes32[] calldata proof,
    uint256 index
) external pure returns (bool) {
    bytes32 hash = leaf;
    for (uint256 i = 0; i < proof.length; ++i) {
        if (index % 2 == 0) {
            hash = keccak256(abi.encodePacked(hash, proof[i]));
        } else {
            hash = keccak256(abi.encodePacked(proof[i], hash));
        }
        index /= 2;
    }
    return hash == root;
}

该示例是“位置敏感”的 Merkle 树实现：树的构造规则、叶子编码、奇数节点处理、排序策略都必须与生成 proof 的程序完全一致。生产环境优先使用经过审计的 MerkleProof 实现，避免自定义树规则导致验证不一致。

4. IPFS / Arweave / Filecoin 对比

这三者并非单纯的“谁更永久”。它们解决的问题不同：IPFS 主要是内容寻址与点对点分发；Filecoin 把存储作为带期限的市场交易并提供链上存储证明；Arweave 则通过 endowment 机制提供长期存储经济模型。[1] [5] [6]

维度IPFSArweaveFilecoin
核心定位内容寻址、点对点分发长期/永久存储经济模型可验证去中心化存储市场
寻址CID交易/数据寻址体系数据 CID + 存储 deal
持久性需要至少一个节点持续保有数据；Pin 可防本地 GC基于 endowment 的长期存储模型依赖具体 storage deal 的期限，并可续约
完整性内容寻址与 DAG/CID 验证数据提交后与链上历史绑定PoRep / PoSt 等存储证明
典型使用场景NFT 元数据、内容分发、可验证静态资源长期归档、不可变数据大数据集、长期但有明确 deal 生命周期的存储
不要把经济承诺写成绝对物理保证

原稿把 Arweave 写成“高（经济激励保证 200+ 年）”、Filecoin 写成“合约期内有保证”。更严谨的表达是：Arweave 的协议经济模型以 endowment 支撑长期存储，并以当前价格模型描述“200 年存储购买力”的设计假设；它不是数学意义上的永久可用承诺。Filecoin 则通过 storage deal + proof-of-storage 约束 provider 在约定期限内持续提供存储证明。[6] [9]

5. 局限性与风险

5.1 完整性 ≠ 可用性

CID 能帮助验证“拿到的数据是否符合该 CID”，但不负责保证你一定能拿到数据。IPFS 节点有垃圾回收机制，pin 可以使数据免于常规 GC；生产系统应将关键数据保存在一个或多个长期在线的节点、pinning 服务或其他长期存储系统中。[7]

5.2 网关不是信任根

HTTP Gateway 只是获取 IPFS 数据的一种方式。恶意或错误配置的网关可能返回错误内容，但如果客户端按 CID 做完整验证，那么“网关返回了什么”与“你最终接受什么”可以被分离。对于高安全场景，优先使用支持 trustless verification 的检索方式或客户端本地验证，而不要把网关当作完整性证明。

5.3 IPNS 是可变命名系统，不等于 CID

IPNS 的目标就是提供“指向可变数据”的名字；记录包含签名、sequence、validity 和 TTL 等信息。IPNS 记录的 EOL/Validity 与 DHT 的缓存/保留窗口也需要考虑，因此把 IPNS 当成“永久不变的 CID 替代物”是不准确的。[8]

工程建议

ipfs://CID 适合做不可变内容锚点；ipns://name 适合做可更新指针。需要版本可追溯时，建议把实际 CID 版本写入链上状态，而不是只记录 IPNS name。

5.4 完整性 ≠ 真实性 ≠ 授权

哈希只能回答“内容有没有变”。它不能回答“内容是谁发布的”“内容是否真实”“发布者是否获得授权”。如果业务还要证明来源，应增加数字签名或链上身份/权限校验。

5.5 哈希抗碰撞是概率安全假设

SHA-256、Keccak-256 等现代密码学哈希在常规攻击模型下提供很强的抗碰撞性，但不要把“不可碰撞”写成绝对数学结论。密码学算法也应保留升级空间，CID/Multihash 的设计本身就考虑了不同哈希算法的并存。[1]

6. 最佳实践清单

#实践优先级
1链上保存实际 CID，而不是把 IPNS 当成不可变锚点。需要版本管理时，直接记录 CID 版本映射。必须
2固定 IPFS 导入参数。特别是 codec、chunking、layout、hash algorithm；否则同一文件可能得到不同 CID。必须
3验证 CID 时不要只对原文件做 SHA-256。要根据 CID 的 codec、DAG/UnixFS 结构正确验证对应 block/数据结构。必须
4不要设计成“智能合约去 IPFS 拉文件”。IPFS 检索和解析发生在链下，链上验证 proof/digest/root。必须
5解决可用性问题。关键数据应多点 pin，或同时采用 Filecoin / Arweave 等长期存储方案。重要
6明确 hash 输入的规范。尤其是 JSON 必须先规定 canonicalization / serialization，否则字段顺序、空白等都可能产生不同 digest。重要
7大数据集优先使用 Merkle Root + Proof。链上只保存 root，单条记录按需证明成员关系。推荐
8需要来源证明时增加数字签名。完整性解决“没变”，签名解决“谁签的”。推荐
9CIDv1 是新项目的优先选择之一，但不要写成“CIDv0 错误/不可用”。CIDv0 仍广泛存在，互操作性场景通常需要兼容 v0。[1]推荐

7. 总结

回到核心问题：智能合约中保存 IPFS 链接，如何确保链下数据没有偷偷变化？

  1. 保存 CID 本身就是一次内容承诺。它把内容与一个密码学内容标识绑定起来。
  2. 但 CID 不是简单的“文件 SHA-256 字符串”。尤其对 UnixFS 大文件，需要考虑 chunking、DAG layout 和 codec。
  3. 智能合约不能直接访问 IPFS。真正的验证者通常是客户端、后端或专门的证明程序；合约验证的是提交上来的 digest、Merkle proof 或其他密码学证明。
  4. 完整性、可用性、真实性是三个不同问题。CID 主要解决完整性/内容身份；Pin 或长期存储方案解决可用性；签名和身份系统解决来源真实性。

一句话总结：内容寻址把“我要相信这个服务器”转换成“我要验证返回的数据是否符合这个内容承诺”。真正可靠的系统，则需要在此基础上继续解决可用性、来源和版本治理问题。
