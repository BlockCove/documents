1. 问题本质：位置寻址 vs 内容寻址

传统 HTTPS URL 主要解决的是"通过某个位置取得资源"。例如 https://example.com/data.json 在 URL 不变的情况下，服务器可以把返回内容替换掉。URL 本身并不承诺响应体的字节内容。

IPFS 的 CID 则是内容寻址标识符：它由内容对应的数据结构的密码学摘要派生而来。IPFS 官方文档明确指出，在相同导入参数下，内容发生变化会产生不同 CID；同一内容只有在使用相同导入/结构化参数时，才会得到相同 CID。[1]

图 1：位置寻址与内容寻址的核心差异
关键区别：URL 标识位置；CID 标识特定内容表示（更准确地说，是对其 IPFS 数据结构的内容指纹）。
必须避免的简化

不能把"CID = 原始文件 SHA-256"作为普遍规律。IPFS 文件通常会先经过分块、DAG 组织和 codec 编码；CID 中的 multihash 通常针对 CID 所代表的根 block，而不是简单地对整个原始文件字节做一次 SHA-256。只有当文件足够小（单块）且使用 raw codec 时，CID 中的摘要才直接等同于文件内容的哈希；大文件会被切分为多个 block 并通过 DAG 组织，此时根 CID 承诺的是整个 DAG 结构。[1]

2. 核心机制：CID 到底验证了什么

2.1 CIDv1 的结构

CIDv1 不是"一个哈希字符串"，而是一个由 multibase、CID version、multicodec 和 multihash 共同构成的自描述标识符。Multicodec 描述目标内容的编码形式，Multihash 记录哈希算法、摘要长度与摘要本身。[1]

完整 CIDv1：bafybeigdyrzt5sfp7udm7hu76uh7y26nf3efuylqabf3oclgtqy55fbzdi
Multibase：b → base32（小写）
CID Version：0x01 → CIDv1
Multicodec：0x70 → dag-pb（UnixFS 目录/文件节点）
Multihash：0x12（sha2-256）+ 0x20（32 字节）+ 32 字节摘要

上表是一个典型 CIDv1 的结构拆解。实际解码时，先去掉 multibase 前缀 b，再按 varint 依次解析 version、codec 和 multihash。常见 codec 还包括 raw（0x55，原始字节）、dag-cbor（0x71）等。

组成作用示例/说明
Multibase指定 CID 二进制部分采用何种文本编码CIDv1 常见前缀 b 表示 base32
CID Version指出 CID 版本CIDv1 的版本字段为 1
Multicodec指出目标内容/节点的 codec例如 raw、dag-pb、dag-cbor
Multihash记录哈希算法、摘要长度和摘要常见为 SHA-256，也支持其他算法

2.2 为什么"相同文件"不一定天然得到相同 CID

IPFS 官方文档特别强调：两个完全相同的文件，也可能因为 chunking、DAG layout、codec、CID 版本或哈希算法不同而得到不同 CID。反过来，想在不同工具/环境中稳定复现 CID，就必须固定这些导入参数。[1]

2.3 大文件与 Merkle DAG

大文件通常会被切分为多个 block，再通过 UnixFS / DAG 结构把这些 block 组织起来。Kubo 等实现的默认固定分块大小为 256 KiB（size-262144），但这是实现默认值，不是 IPFS 协议规定的固定值；不同实现或配置可能使用不同大小，也可以使用 Buzhash/Rabin 等内容定义分块器。需要注意：只有固定大小分块器（size-N）能保证相同数据始终产生相同 CID；rabin 和 buzhash 分块器的内部参数可能在未来版本中变化。[2]

为了跨实现稳定复现 CID，Kubo 提供了确定性导入 profile。例如 unixfs-v1-2025 固定使用：CIDv1、raw leaves、sha2-256、1 MiB chunks、每文件节点 1024 个链接、256 HAMT fanout、基于 block 的 HAMT 阈值估算。对应的旧版兼容 profile 是 unixfs-v0-2015（CIDv0、256 KiB chunks、无 raw leaves）。[2] [10]

因此，Merkle DAG 的价值不是简单的"每个文件都有一个文件级 SHA-256"，而是把多个内容 block 通过 CID 链接起来，最终由根节点的内容标识代表整个数据结构。

图 2：文件的 DAG 结构与完整性验证
篡改任一被引用 block，会破坏该 block 的内容标识并沿 DAG 影响上层内容标识。

3. 智能合约中的正确验证模式

3.1 最重要的架构边界：智能合约不能直接读取 IPFS

原稿中的关键错误已修正

EVM 合约执行时并没有"从 IPFS 下载文件"的能力。合约不能像浏览器一样调用 https://ipfs.io/ipfs/... 或直接读取 IPFS 网络。正确模式是：客户端/后端先从 IPFS 取回数据并完成解析、重构或哈希计算，再把证明材料提交给合约验证。Chainlink Functions 等 oracle 方案可以让合约间接触发外部数据获取，但那是 oracle 节点在链下执行后回传结果，并非合约直接访问 IPFS。

图 3：正确的链下数据完整性验证流程
重点：IPFS 取数发生在链下；链上验证的是客户端提交的可验证摘要或证明，而不是让合约直接"下载 IPFS"。

3.2 Solidity：用链上 Keccak 做简单锚定

如果业务场景不要求合约理解 CID 的完整结构，而只是希望锚定一份"规范化后的字节序列"，最简单的做法是直接锚定 keccak256(data)。这样与 IPFS CID 是两条不同但可以并存的完整性链路。

// SPDX-License-Identifier: MIT

pragma solidity ^0.8.20;




contract DataAnchor {

mapping(bytes32 => bytes32) public contentHashes;




event DataAnchored(

bytes32 indexed fileId,

bytes32 contentHash,

address uploader

    );




function anchor(bytes32 fileId, bytes32 contentHash) external {

require(contentHashes[fileId] == bytes32(0), "already anchored");

        contentHashes[fileId] = contentHash;

emit DataAnchored(fileId, contentHash, msg.sender);

    }




function verify(bytes32 fileId, bytes32 contentHash)

external view returns (bool)

    {

return contentHashes[fileId] == contentHash;

    }




function verifyRaw(bytes calldata data, bytes32 expected)

external pure returns (bool)

    {

return keccak256(data) == expected;

    }

}
关于 SHA-256 与 EVM 的准确说法

Solidity 同时提供 keccak256 和 sha256 内建函数；SHA-256 并不是"EVM 不支持、只能靠第三方库"。在 Ethereum 主网等标准 EVM 环境中，sha256 通过预编译合约实现。原稿中的"EIP-198 是 SHA-256 预编译"是错误的：EIP-198 对应的是大整数模幂运算（ModExp，地址 0x05）；SHA-256 对应的是预编译地址 0x02。[3] [4]

verifyRaw 的实际适用范围

verifyRaw 把完整数据作为 calldata 传入合约重新计算哈希，这只适合很小的数据（通常不超过几 KB）。对于图片、文档等大文件，将整个文件作为 calldata 上传的 gas 成本极高（calldata 每字节 16 gas，非零字节），在 Ethereum 主网上几 MB 的文件就可能超过区块 gas 上限。生产环境的正确做法是：链下计算哈希后只提交 bytes32 摘要，或使用 Merkle Proof 只提交必要的证明路径。

3.3 IPFS CID 与 Keccak 哈希应该如何配合

如果项目既要 IPFS 生态兼容，又要在 EVM 合约里方便验证，可以采用"双锚点"设计：

链上字段作用注意点
CID / CID 编码后的 bytes标识 IPFS 数据应保留 codec / version / hash algorithm 等信息；不要默认把 CID 等同于文件 SHA-256
Keccak-256 digest便于 EVM 合约直接比较/验证必须明确"对什么字节序列计算"——例如规范化 JSON，而不是任意网关响应

关于链上存储成本：一个 CIDv1（SHA-256）的 base32 字符串约 59 字符，作为 string 存入 storage 的成本显著高于固定长度的 bytes32。若将 CID 解码为原始 bytes 存储（multicodec + multihash 约 36 字节），成本会降低但仍高于纯 digest。生产系统应按业务需求选择：需要 IPFS 生态互操作时存完整 CID 或其编码 bytes；只需要链上验证时存 bytes32 digest；也可以两者并存。

3.4 Merkle Proof：证明"某条数据属于已锚定集合"

当业务不是验证整份文件，而是验证"这条记录属于已经在链上承诺过的数据集"时，Merkle Root 很合适。链上保存 root；用户提交 leaf 与 proof，合约重新计算根并比较。

function verifyMerkle(

bytes32 root,

bytes32 leaf,

bytes32[] calldata proof,

uint256 index

) external pure returns (bool) {

bytes32 hash = leaf;

for (uint256 i = 0; i < proof.length; ++i) {

if (index % 2 == 0) {

            hash = keccak256(abi.encodePacked(hash, proof[i]));

        } else {

            hash = keccak256(abi.encodePacked(proof[i], hash));

        }

        index /= 2;

    }

return hash == root;

}

该示例是"位置敏感"的 Merkle 树实现：index 用于确定每一层中当前哈希与兄弟节点的拼接顺序（左/右），树的构造规则、叶子编码、奇数节点处理、排序策略都必须与生成 proof 的程序完全一致。生产环境优先使用经过审计的 OpenZeppelin MerkleProof 实现，避免自定义树规则导致验证不一致。

4. IPFS / Arweave / Filecoin 对比

这三者并非单纯的"谁更永久"。它们解决的问题不同：IPFS 主要是内容寻址与点对点分发；Filecoin 把存储作为带期限的市场交易并提供链上存储证明；Arweave 则通过 endowment 机制提供长期存储经济模型。[1] [5] [6]

维度IPFSArweaveFilecoin
核心定位内容寻址、点对点分发长期/永久存储经济模型可验证去中心化存储市场
寻址CID（内容标识）交易 ID（Transaction ID），数据通过 Merkle root 承诺在交易中数据 CID + 存储 deal（deal ID）
持久性需要至少一个节点持续保有数据；Pin 可防本地 GC基于 endowment 的长期存储模型依赖具体 storage deal 的期限（最短 180 天），并可续约
完整性内容寻址与 DAG/CID 验证交易 ID 承诺交易签名，数据通过 Merkle root 绑定到交易PoRep / PoSt 等存储证明
典型使用场景NFT 元数据、内容分发、可验证静态资源长期归档、不可变数据大数据集、长期但有明确 deal 生命周期的存储
不要把经济承诺写成绝对物理保证

原稿把 Arweave 写成"高（经济激励保证 200+ 年）"、Filecoin 写成"合约期内有保证"。更严谨的表达是：Arweave 的协议经济模型以 endowment 支撑长期存储，并以当前价格模型描述"200 年存储购买力"的设计假设；它不是数学意义上的永久可用承诺。Filecoin 则通过 storage deal + proof-of-storage 约束 provider 在约定期限内持续提供存储证明，deal 最短 180 天，到期后需要续约否则 provider 不再有义务保留数据。[6] [5]

5. 局限性与风险

5.1 完整性 ≠ 可用性：以 FileBase 和 NFT 为例

CID 能帮助验证"拿到的数据是否符合该 CID"，但不负责保证你一定能拿到数据。这是 IPFS 最容易被误解的一点：CID 永远不会"失效"，但它指向的内容可能变得不可获取。

以一个典型 NFT 场景为例：你把图片和元数据上传到 FileBase（一个提供 S3 接口的 IPFS pinning 服务，同时自动创建 Filecoin storage deal），然后把 CID 写入 NFT 合约。之后你在 FileBase 控制台手动删除了这个文件。会发生什么？

  1. FileBase 端的 pin 被移除：FileBase 不再在自己的 IPFS 节点上保留该数据，该节点的垃圾回收（GC）可能清理这些 block。
  2. Filecoin deal 期内数据仍在：如果 FileBase 为该文件创建了 Filecoin storage deal，在 deal 有效期内（最短 180 天），存储提供者仍有义务保留数据并提交 PoSt。但从 Filecoin 直接检索数据比从 IPFS 网关慢得多，且需要专门的检索流程。
  3. 其他 IPFS 节点可能仍有缓存：如果曾经有其他节点（网关、用户浏览器等）访问过该 CID 并缓存了数据，在这些节点清理缓存之前，内容仍可获取。但缓存是临时的，不保证长期保留。
  4. NFT 合约中的 CID 不受影响：链上记录的 CID 本身不会改变，也不会因为你删除了 FileBase 中的文件而失效。但如果全网没有任何节点再持有该数据，ipfs://CID 链接将无法解析到内容——表现为"链接还在，但图裂了"。
核心结论：没有任何单一 pinning 服务能保证"删不掉"

从 FileBase（或任何单一 pinning 服务）删除文件后，不存在机制阻止该文件最终从 IPFS 网络中消失。Filecoin deal 只能在 deal 期内提供经济约束下的存储保证，且检索体验远不如 IPFS 网关。要真正降低 NFT 元数据不可用的风险，必须在上传时就做多点冗余，而不是依赖单一服务。[7] [11]

生产系统应将关键数据保存在一个或多个长期在线的节点、pinning 服务或其他长期存储系统中。对于 NFT 场景，推荐的冗余策略包括：

  • 至少 2-3 个独立 pinning 服务（如 Pinata + FileBase + 自建节点），一个服务删除或宕机不影响可用性。
  • 使用 NFT.Storage 等专门服务：自动在专用 IPFS 服务器和 Filecoin 网络中多点冗余存储。[11]
  • 关键资产同步到 Arweave：一次性付费的长期存储，作为最终归档层。
  • 定期检查 CID 可访问性：通过多个公共网关验证 CID 是否可解析，及时发现并补救不可用的内容。

5.2 网关不是信任根

HTTP Gateway 只是获取 IPFS 数据的一种方式。恶意或错误配置的网关可能返回错误内容，但如果客户端按 CID 做完整验证（trustless verification），那么"网关返回了什么"与"你最终接受什么"可以被分离——网关返回的数据会被客户端重新计算哈希并与 CID 比对，不匹配则拒绝。对于高安全场景，优先使用支持 trustless verification 的检索方式（如返回 block + CID 而非仅返回处理后的数据）或客户端本地验证，而不要把网关当作完整性证明。

5.3 IPNS 是可变命名系统，不等于 CID

IPNS 的目标就是提供"指向可变数据"的名字。每条 IPNS 记录包含发布者的签名、序列号（sequence，用于防止重放）、有效期（Validity / EOL，即这条记录到什么时间过期）和 TTL（缓存建议时间）。发布者可以随时用同一私钥发布一条新记录，指向不同的 CID。

需要注意的是：IPNS 记录有过期时间，且 DHT 中的记录也有缓存/保留窗口。如果发布者不定期重新发布（republish），记录可能从 DHT 中消失，导致名字无法解析。因此把 IPNS 当成"永久不变的 CID 替代物"是不准确的——它本质上是一个带签名的、可更新的、有过期时间的指针。[8]

工程建议

ipfs://CID 适合做不可变内容锚点；ipns://name 适合做可更新指针。需要版本可追溯时，建议把实际 CID 版本写入链上状态，而不是只记录 IPNS name。

5.4 完整性 ≠ 真实性 ≠ 授权

哈希只能回答"内容有没有变"。它不能回答"内容是谁发布的""内容是否真实""发布者是否获得授权"。如果业务还要证明来源，应增加数字签名或链上身份/权限校验。

5.5 哈希抗碰撞是概率安全假设

SHA-256、Keccak-256 等现代密码学哈希在常规攻击模型下提供很强的抗碰撞性，但不要把"不可碰撞"写成绝对数学结论。密码学算法也应保留升级空间，CID/Multihash 的设计本身就考虑了不同哈希算法的并存。[1]

7. 总结

回到核心问题：智能合约中保存 IPFS 链接，如何确保链下数据没有偷偷变化？

  1. 保存 CID 本身就是一次内容承诺。它把内容与一个密码学内容标识绑定起来，内容变化（在相同导入参数下）必然导致 CID 变化。
  2. 但 CID 不是简单的"文件 SHA-256 字符串"。尤其对 UnixFS 大文件，需要考虑 chunking、DAG layout 和 codec。
  3. 智能合约不能直接访问 IPFS。真正的验证者通常是客户端、后端或专门的证明程序；合约验证的是提交上来的 digest、Merkle proof 或其他密码学证明。
  4. 完整性、可用性、真实性是三个不同问题。CID 主要解决完整性/内容身份；多点 Pin 或长期存储方案解决可用性；签名和身份系统解决来源真实性。
  5. 没有任何单一服务能保证"删不掉"。从 FileBase 等 pinning 服务删除文件后，CID 本身不会失效，但内容可能最终不可获取。必须通过多点冗余和长期存储方案来降低可用性风险。

一句话总结：内容寻址把"我要相信这个服务器"转换成"我要验证返回的数据是否符合这个内容承诺"。真正可靠的系统，则需要在此基础上继续解决可用性、来源和版本治理问题。
