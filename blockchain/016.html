EVM Internals · 从 C++ 到 EVM

理解 EVM 的五类核心数据区
像理解 C++ 内存一样

你已经知道 C++ 程序如何加载到内存、PC 如何移动、函数栈如何入栈退栈、如何在堆上 new 空间。 EVM 作为一台栈式虚拟机，有着惊人相似但又截然不同的存储模型。这份报告用你熟悉的 C++ 概念做锚点， 逐层拆解 Stack、Memory、Storage、Calldata、Transient Storage 的本质，并单独说明合约 Code。

01 · 执行模型对比

C++ 进程 vs EVM 执行环境

C++ 进程通常可抽象为代码段、数据段/BSS、堆、栈等区域，并由操作系统提供独立的虚拟地址空间。 EVM 没有操作系统进程和虚拟地址空间；它更准确地应理解为确定性的状态转换环境。 对一笔交易而言，可以把执行过程理解为：给定区块链状态、交易和执行环境 → 经过 EVM 执行 → 得到新的状态以及执行结果/日志等。 每个 EVM 调用帧都有自己的 Stack、Memory 和 Calldata；Transient Storage 按合约在整笔交易范围内共享，Storage 则跨交易持久化。

内存布局对照 · C++ Process Memory Layout ↔ EVM Execution Context
核心差异 · C++ vs EVM 
// C++: 有操作系统管理的虚拟地址空间，进程长期运行
// EVM: 无 OS 进程模型；交易执行从当前状态与环境出发，产生确定性的状态变更与执行结果

// C++ 函数调用时:
void foo(int a, int b) {  // 参数压栈 → 栈帧创建 → 局部变量在栈上
    int* p = new int[10];  // 堆分配，需手动 delete
}  // 栈帧销毁，堆内存泄漏风险

// EVM 合约调用时:
// 1. Calldata 载入 (函数选择器 + 参数, 只读)
// 2. Stack 初始为空, 指令 PUSH 操作数
// 3. Memory 初始为空, MSTORE 按需扩展
// 4. Storage 读取当前状态；Transient 按合约在同一交易的相关调用帧之间共享
// 5. 调用帧结束时 Stack/Memory/Calldata 丢弃；交易成功后 Storage 修改提交，Transient 在交易结束清零
02 · STACK
EVM Stack — 操作数栈
类比 C++: CPU 寄存器集合 + 表达式求值栈（不是函数调用栈）

EVM 是一台栈式虚拟机——所有运算都在栈上完成。你可以把它想象成一个只能从顶端操作的"盘子堆"： 指令从栈顶弹出操作数、计算、再把结果压回栈顶。这和 x86 的寄存器模型不同，EVM 没有通用寄存器， 栈就是它的"运算工作台"。

关键区别：C++ 的函数调用栈存储的是局部变量、返回地址、帧指针； EVM 的栈主要承载操作数和临时值；标量局部变量通常也由编译器放在 Stack，而动态数组、struct 等引用类型可位于 Memory/Storage。调用返回地址由调用帧与 EVM 控制流机制管理，而不是作为普通局部变量放在栈帧中。

  • 字长：每个元素 256 bit (32 字节)，EVM 原生字长
  • 深度上限：1024 个元素，超出触发 Stack Overflow 异常
  • 核心指令：PUSH1~PUSH32 (压栈)、POP (弹栈)、DUP1~DUP16 (复制第 N 个)、SWAP1~SWAP16 (交换栈顶与第 N 个)
  • 算术指令：ADD、SUB、MUL、DIV 等均从栈顶弹 2 个、压 1 个结果
  • Gas：PUSH 3 gas、POP 2 gas、DUP/SWAP 3 gas；这些是 opcode 基础费用
Solidity · 栈上的简单运算 
function addExample() pure returns (uint) {
    uint a = 10;   // PUSH1 0x0a → 栈: [10]
    uint b = 20;   // PUSH1 0x14 → 栈: [10, 20]
    return a + b;     // ADD → 弹出 20,10 → 压入 30 → 栈: [30]
}

EVM 栈操作示意：所有算术/逻辑指令都是"弹 N 个、压 M 个"的栈操作

03 · MEMORY
Memory — 调用帧临时字节数组
类比 C++: 堆内存 (new / malloc)，但交易结束自动"释放"

EVM Memory 是一个字节可寻址的线性字节数组。访问尚未扩展的区域时，内存会按 32 字节字对齐扩展， 新扩展区域按 EVM 语义视为零。它和 C++ 堆有一点相似：可动态扩展、执行后丢弃；但更准确地说， Memory 属于当前 EVM 调用帧，每个 CALL/CREATE 等调用帧都有独立 Memory，帧结束后即丢弃。

Memory 的大小按 32 字节（一个 word）向上取整计费。当某条指令访问超出当前内存大小的区域时， EVM 会扩展 Memory，并支付一次增量内存扩展成本。内存总成本函数包含线性项和二次项， 因此扩展到非常大的内存范围会越来越昂贵。

  • 寻址：字节级寻址，偏移量 256 bit（实际可用受 Gas 限制）
  • 扩展粒度：按 32 字节 word 向上取整；实际扩展长度由被访问的最高字节决定
  • 核心指令：MLOAD (从内存读 32B 到栈)、MSTORE (写 32B)、MSTORE8 (写 1B)
  • 生命周期：单笔交易内有效，交易结束清零
  • 典型用途：动态数组、ABI 编解码缓冲区、返回数据准备区及其他临时数据；标量局部变量通常由编译器放在 Stack，而不是 Memory
Solidity · memory 关键字 
function processArray(uint[] calldata input)
    pure returns (uint[] memory)
{
    // 在 memory 中分配数组 (类似 new uint[](size))
    uint[] memory result = new uint[](input.length);

    for (uint i = 0; i < input.length; i++) {
        result[i] = input[i] * 2;
    }
    return result;  // 返回值会经过 ABI 编码；跨外部调用时由 returndata 机制传递
}

Solidity 约定：0x00~0x3f 为临时槽，0x40 存 free memory pointer，0x60 为零值槽，实际分配从 0x80 开始

04 · STORAGE
Storage — 持久化状态
类比 C++: 全局变量 / 静态存储区，但每个合约独立、永久写入区块链

Storage 是 EVM 中用于持久化合约状态的核心键值空间。每个合约拥有独立的 2²⁵⁶ 个逻辑 slot， 每个 slot 宽 32 字节。它可以类比 C++ 的全局/静态数据，但并不等同于进程内存： 状态修改只有在交易成功时才会提交到链上状态；SSTORE 的实际 Gas 还取决于槽位冷热状态以及 original/current/new value。

Slot 布局规则：状态变量按声明顺序从 slot 0 开始连续分配； 小于 32 字节的变量会被打包进同一个 slot；mapping 和动态数组不占用连续 slot， 而是通过哈希计算定位到"随机"位置。

  • 容量：2²⁵⁶ 个 slot，每个 32 字节（理论上无限大）
  • 核心指令：SLOAD (读 slot)、SSTORE (写 slot)
  • Gas (读)：冷访问 2100 gas，热访问 100 gas (EIP-2929)
  • Gas (写)：常见基础值为零→非零 20,000、非零→非零 5,000；冷槽还可能增加 2,100 的访问成本。非零→零的 SSTORE 清零退款为 4,800，且退款受 EIP-3529 的上限约束
  • 生命周期：成功执行后的状态跨交易保留，通常直到后续状态修改；EIP-6780 后，普通已有合约的 SELFDESTRUCT 不再删除其 code/storage，仅在“创建该合约的同一交易内”才保留删除语义
Solidity · Storage 变量与 Slot 分配 
contract StorageDemo {
    uint256 public count;     // slot 0
    address public owner;     // slot 1
    uint128 a;                // slot 2 (低 16 字节)
    uint128 b;                // slot 2 (高 16 字节, 打包!)
    mapping(address=>uint) balances; // slot 3 (仅占位)
    uint[] public arr;       // slot 4 (存长度)

    // mapping(uint => V) 的值槽：keccak256(abi.encode(key, slot))
    // uint256[] 的数据区从 keccak256(slot) 开始；元素位置还需遵循元素打包规则
}

普通定长状态变量按布局规则连续分配；mapping/动态数组使用 keccak256 派生数据位置。动态数组元素还需考虑元素是否可以在一个 slot 内打包

05 · CALLDATA
Calldata — 只读调用数据
类比 C++: 函数参数列表（调用方传入，函数内只读）

当你调用一个合约函数时，交易的 data 字段就是 Calldata。它包含 4 字节函数选择器 + ABI 编码的参数，完全只读，不可修改。 这就像 C++ 函数的 const 引用参数——调用方准备好了数据，函数只能读不能写。

对于交易输入数据，EIP-2028 规定零字节 4 gas、非零字节 16 gas；这是交易的 intrinsic data cost。 读取 calldata 本身还会涉及 CALLDATALOAD/COPY 等 opcode 成本，而不是简单按 4/16 gas 再收费一次。 这就是为什么优化合约时人们会尽量用零字节——比如 address(0) 比随机地址便宜。

  • 可变性：只读，无法在合约中修改 calldata
  • 结构：前 4 字节 = 函数选择器 (keccak256 签名前 4 字节)，后续 = ABI 编码参数
  • 核心指令：CALLDATALOAD (读 32B)、CALLDATASIZE、CALLDATACOPY (复制到 memory)
  • 交易数据费：顶层交易 input data 的零字节 4 gas/byte，非零字节 16 gas/byte（EIP-2028）
  • 最佳实践：外部函数的数组参数用 calldata 而非 memory，省一次拷贝
Solidity · calldata vs memory 参数 
// 推荐: calldata 直接引用, 不复制
function sum(uint[] calldata arr) external pure returns (uint) {
    uint s = 0;
    for (uint i; i < arr.length; i++) s += arr[i];
    return s;
}

// 不推荐: memory 会把 calldata 完整复制一份到 memory
function sumBad(uint[] memory arr) external pure returns (uint s) {
    // calldata → memory 会发生一次数据复制
    for (uint i; i < arr.length; i++) s += arr[i];
}

函数选择器 = keccak256("transfer(address,uint256)") 的前 4 字节 = 0xa9059cbb

06 · TRANSIENT
Transient Storage — 瞬时存储
类比 C++: thread_local 变量 / 请求级缓存（同一交易内同一合约的调用帧可共享，交易结束清零）

Transient Storage 由 EIP-1153 引入，并随 Ethereum 的 Cancun/Deneb 升级启用。 它的语义是：同一笔交易内持久化，交易结束后自动清零。 但它不是“所有合约共享的一张临时表”：每个合约拥有独立的 transient storage，只有属于同一合约的相关调用帧才能共享该合约的 transient state。

在 Transient 出现之前，如果你想在一笔交易的多次内部调用间共享数据（如重入锁）， 只能用 Storage（贵）或把数据通过参数传来传去（麻烦）。Transient 提供了廉价的交易级共享存储。

  • 引入：EIP-1153，随 2024 年 3 月的 Cancun/Deneb 升级启用
  • 核心指令：TLOAD (读)、TSTORE (写)，操作码与 SLOAD/SSTORE 同构
  • Gas：TLOAD 100 gas，TSTORE 100 gas（比 Storage 冷读便宜 21 倍）
  • 生命周期：交易开始时为空；同一合约的调用帧在交易内共享；交易结束清零
  • 典型用途：重入锁、交易内缓存、权限标记、批量操作的中间状态
  • 不持久化：不会写入持久状态树；调用帧回滚会回滚该帧及其嵌套调用对 transient state 的修改
Solidity 0.8.24+ / EVM Cancun+ · transient 关键字 (重入锁) 
contract ReentrancyGuard {
    // 交易级变量, 交易结束自动归零
    uint256 private transient _status;

    modifier nonReentrant() {
        require(_status == 0, "Reentrancy");
        _status = 1;   // TSTORE, 100 gas
        _;
        _status = 0;   // 必须在本次调用结束时解锁，保证同一交易内可再次组合调用
    }
}

TSTORE 的基础费用为 100 gas；相较 20,000 gas 的 SSTORE“零→非零”基础费用约为 1/200，但两者并非所有场景都如此

// 1. 能用 calldata 就不用 memory (省拷贝)
// 2. 能在 Stack / Memory 中完成的计算，尽量不要反复访问 Storage
// 3. 需要同一合约内跨调用帧共享时，可考虑 transient（需注意交易级生命周期）
// 4. 打包小变量到同一个 slot (uint128+uint128 = 1 次 SSTORE)
// 5. 循环内缓存 storage 变量到 memory, 循环结束写回一次

// 反面教材: 循环内每次都 SLOAD + SSTORE
for (uint i = 0; i < n; i++) {
    count = count + 1;  // 每次都访问 Storage! 贵!
}

// 正确做法: 用局部标量变量累加，最后写回一次（通常由编译器放在 Stack）
uint _count = count;  // 1 次 SLOAD；标量局部变量通常由编译器放在 Stack
for (uint i = 0; i < n; i++) {
    _count = _count + 1;  // 主要是 Stack 上的局部计算
}
count = _count;  // 1 次 SSTORE
09 · 常见陷阱

C++ 程序员最容易踩的坑

从 C++ 转到 Solidity，有几个思维定式会让你写出昂贵甚至有安全漏洞的代码。

Storage 指针 vs Memory 拷贝

C++ 里引用和指针很直观，但 Solidity 中 storage 类型的局部变量是指向状态的引用，修改它直接写 Storage；memory 是独立拷贝。声明时漏写 memory 可能意外修改状态。

没有 free，也没有 GC

C++ 里你要关心堆资源生命周期；EVM Memory 则随调用帧结束丢弃。反过来：Storage 状态不会因为交易结束自动释放。删除值可以产生有限退款，但逻辑上的 slot 仍可再次写入；而且零值槽通常不会以一个显式条目存在于状态 Trie 中。

Memory 不是无限的

C++ 堆有几个 GB，EVM Memory 受 Gas 限制。扩展成本是二次方的，分配 MB 级内存会耗尽 Gas。大数组处理要分批或用 Calldata 直接读。

Calldata 不是数组

虽然 calldata 数组看起来和 memory 数组用法一样，但它不可修改。尝试 arr[0] = x 会编译失败。需要修改时先拷贝到 memory。

Proxy Storage Layout 冲突

代理合约通过 DELEGATECALL 让实现代码在代理合约的 Storage 上运行。若实现代码与代理的状态布局不兼容，可能发生Storage Layout 冲突并覆盖错误槽位，进而造成严重安全问题。现代代理通常使用 EIP-1967、ERC-7201 等约定降低此类风险。

Transient 不跨交易

Transient 看起来像"便宜的 Storage"，但它交易结束就清零。不能用来存用户余额、授权状态等需要持久化的数据。它只适合重入锁、一次性标记等交易级场景。

一图记住 EVM 存储

把 EVM 想象成一个确定性的状态转换环境：执行从当前区块链状态、交易和执行环境出发， 在调用帧自己的 Stack / Memory / Calldata 上工作，同时按合约访问 Storage 和 Transient Storage。 交易成功后，持久状态修改才会提交；Stack、Memory、Calldata 随各自调用帧结束而丢弃，Transient Storage 在交易结束清零。

EVM 存储决策树 · 我该用哪个？

核心记忆口诀

Stack = 运算工作台，弹弹压压，3 gas

Memory = 调用帧便签纸，写完即丢，3 gas + 内存扩展费

Storage = 持久化状态，昂贵；SSTORE 成本取决于状态变化和槽位冷热

Calldata = 只读信封，调用方给的，零字节便宜

Transient = 同一合约交易内白板，帧间可共享，100 gas

Code = 合约本身，只读，部署定终身
