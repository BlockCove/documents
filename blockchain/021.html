01 / ARCHITECTURE

UUPS 代理模式架构

UUPS（Universal Upgradeable Proxy Standard）将升级逻辑放在实现合约中，而非代理合约中。这意味着代理合约本身极其轻量，所有业务逻辑和升级能力都由实现合约提供。

P

代理合约 (Proxy)

用户始终与代理合约交互。它不包含业务逻辑，通过 delegatecall 将调用转发给当前实现合约。存储槽位中记录实现合约地址。

ERC1967Proxy
I

实现合约 (Implementation)

包含实际业务逻辑（如 listNFT、buyNFT）。UUPS 模式下，升级函数 upgradeToAndCall() 定义在实现合约一侧，由 UUPSUpgradeable 提供。当前 OpenZeppelin Contracts 5.x 的 UUPS 接口只提供 upgradeToAndCall()，应通过它完成升级。

NFTMarket + UUPSUpgradeable
S

存储隔离

所有状态变量存储在代理合约的存储上下文中。delegatecall 在代理的存储环境中执行实现合约的代码，因此升级实现合约不会丢失已有数据。

delegatecall 存储上下文

UUPS vs Transparent Proxy

维度 UUPS (本指南) Transparent Proxy
升级逻辑位置 实现合约中 (UUPSUpgradeable) TransparentUpgradeableProxy + ProxyAdmin
代理合约大小 极小，仅 ERC1967Proxy 较大，含 admin 管理逻辑
部署 Gas 更低 更高
实现合约要求 必须继承 UUPSUpgradeable，实现 _authorizeUpgrade 实现合约无需 UUPS 升级入口，由 Transparent Proxy 的管理员控制升级
升级风险 当前 UUPS 实现会在链上校验新实现的 ERC-1822 UUID；不兼容的实现通常会直接拒绝升级 升级逻辑在代理中，相对安全
适用场景 Gas 敏感、追求轻量代理的项目 需要 ProxyAdmin 统一管理多合约的项目
02 / CONTRACT

NFTMarket 合约代码

一个标准的 UUPS 可升级合约需要：继承 UUPSUpgradeable、使用 initialize() 替代 constructor、实现 _authorizeUpgrade() 权限控制。

contracts/NFTMarket.sol Solidity ^0.8.20 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.22;

import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/proxy/utils/UUPSUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/OwnableUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/utils/PausableUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/utils/ReentrancyGuardUpgradeable.sol";
import "@openzeppelin/contracts/token/ERC721/IERC721.sol";

/**
 * @title NFTMarket
 * @notice UUPS 可升级的 NFT 交易市场合约
 * @dev 业务状态通过 initialize 初始化；implementation constructor 仅用于 _disableInitializers()
 */
contract NFTMarket is
    Initializable,
    UUPSUpgradeable,
    OwnableUpgradeable,
    PausableUpgradeable,
    ReentrancyGuardUpgradeable
{
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }
    // ===== 状态变量（存储在 Proxy 中，升级时不可乱序）=====

    /// @notice 平台手续费 (basis points, 100 = 1%)
    uint256 public feeBps;

    /// @notice 手续费接收地址
    address public feeRecipient;

    /// @notice 挂牌信息: listingId => Listing
    struct Listing {
        address seller;
        address nftContract;
        uint256 tokenId;
        uint256 price;
        bool active;
    }
    mapping(uint256 => Listing) public listings;
    uint256 public nextListingId;

    // ===== 事件 =====
    event NFTListed(uint256 indexed listingId, address indexed seller, uint256 price);
    event NFTSold(uint256 indexed listingId, address indexed buyer, uint256 price);

    /**
     * @notice 初始化函数，替代 constructor
     * @dev 仅在代理部署时通过 delegatecall 调用一次
     * @param _feeBps 平台手续费 (basis points)
     * @param _feeRecipient 手续费接收地址
     */
    function initialize(uint256 _feeBps, address _feeRecipient) public initializer {
        // 初始化需要初始化的父模块
        __Ownable_init(msg.sender);
        __Pausable_init();
        __ReentrancyGuard_init();

        // 初始化业务状态
        require(_feeBps <= 10000, "Fee too high");
        require(_feeRecipient != address(0), "Invalid fee recipient");
        feeBps = _feeBps;
        feeRecipient = _feeRecipient;
        nextListingId = 1;
    }

    /**
     * @notice UUPS 升级授权钩子
     * @dev 每次 UUPS 升级调用前都会执行此函数
     *      只有 owner 可以授权升级
     * @param newImplementation 新实现合约地址
     */
    function _authorizeUpgrade(address newImplementation) internal override onlyOwner {
        // 空函数体即可，onlyOwner 修饰器已完成权限检查
        // 可在此添加额外检查：如新实现地址的代码大小验证
    }

    // ===== 业务函数 =====

    function listNFT(address nftContract, uint256 tokenId, uint256 price)
        external whenNotPaused nonReentrant
    {
        require(nftContract != address(0), "Invalid NFT contract");
        require(price > 0, "Price must be > 0");
        require(IERC721(nftContract).ownerOf(tokenId) == msg.sender, "Not NFT owner");
        require(
            IERC721(nftContract).getApproved(tokenId) == address(this) ||
            IERC721(nftContract).isApprovedForAll(msg.sender, address(this)),
            "Marketplace not approved"
        );

        uint256 listingId = nextListingId++;
        listings[listingId] = Listing(msg.sender, nftContract, tokenId, price, true);
        emit NFTListed(listingId, msg.sender, price);
    }

    function buyNFT(uint256 listingId) external payable whenNotPaused nonReentrant {
        Listing storage listing = listings[listingId];
        require(listing.active, "Not active");
        require(msg.value == listing.price, "Wrong price");
        require(feeBps <= 10000, "Fee too high");

        listing.active = false;

        // 先完成 NFT 交割；失败则整笔交易回滚
        IERC721(listing.nftContract).safeTransferFrom(listing.seller, msg.sender, listing.tokenId);

        uint256 fee = msg.value * feeBps / 10000;
        (bool sellerOk, ) = payable(listing.seller).call{value: msg.value - fee}("");
        require(sellerOk, "Seller payment failed");

        (bool feeOk, ) = payable(feeRecipient).call{value: fee}("");
        require(feeOk, "Fee payment failed");

        emit NFTSold(listingId, msg.sender, msg.value);
    }

    // ===== Owner 管理函数 =====
    function setFeeBps(uint256 _feeBps) external onlyOwner { require(_feeBps <= 10000, "Fee too high"); feeBps = _feeBps; }
    function pause() external onlyOwner { _pause(); }
    function unpause() external onlyOwner { _unpause(); }
}
!
存储布局不可变（Storage Gap 规则）
对于采用传统线性 storage 的自定义状态变量，升级时不能在旧变量前面插入、删除或重排变量，新增变量通常只能追加到已有布局末尾。与此同时，OpenZeppelin Contracts 5.x 的多个 upgradeable 模块已经采用 ERC-7201 namespaced storage，因此不要把“所有继承变量都必须按声明顺序排列”作为绝对规则；应以实际 storage layout 检查结果为准。对于自定义线性 storage，可按项目需要设计 storage gap；使用 ERC-7201 namespace 的模块则应遵循其 namespace 设计。
i
版本说明：OpenZeppelin 5.x
本示例按 OpenZeppelin Contracts Upgradeable 5.x 编写：OwnableUpgradeable 使用 __Ownable_init(initialOwner)；PausableUpgradeable 位于 utils/；UUPS 使用 upgradeToAndCall()。实际项目请固定依赖版本，避免不同主版本之间的 storage layout 和 API 差异。
03 / FIRST DEPLOY

首次部署完整流程

首次部署需要依次完成：部署实现合约 → 部署代理合约（同时触发初始化）→ 验证合约。部署者使用 EOA 账户，初始化后 owner 默认为该 EOA。

1

准备部署者 EOA 账户 EOA

使用一个外部拥有账户（Externally Owned Account）作为部署者。这个账户需要有足够的原生代币（ETH / BNB / MATIC 等）支付 Gas。

  • 私钥管理：使用 Hardhat 配置中的 PRIVATE_KEY 环境变量，绝不要提交到 Git
  • 推荐做法：使用专门的部署账户，不要用日常交互账户；部署完成后该账户仅保留 owner 角色直到迁移到多签
  • 非部署者选项：也可以使用 CREATE2 工厂合约确定性部署，但首次部署通常直接用 EOA 更简单
Deployer EOA 0x7a3F9c2E... (示例，替换为你的地址)
2

部署实现合约 NFTMarket EOA 发起

将 NFTMarket.sol 的字节码部署到链上。这一步部署的是实现合约，它不会被直接使用，而是作为代理合约的逻辑目标。

i
实现合约自身的 constructor 中应调用 _disableInitializers()，锁定实现合约的 initializer；这也是 OpenZeppelin 对 upgradeable implementation 的推荐做法。OpenZeppelin 推荐在实现合约的 constructor 中禁用初始化。
3

部署 ERC1967Proxy 并触发初始化 核心步骤 必须

部署代理合约时，在构造函数中传入两个参数：实现合约地址 + 初始化调用的 calldata。代理合约在构造时会通过 delegatecall 执行 initialize()。

在 OpenZeppelin Contracts 5.x 中，ERC1967Proxy 的构造函数仍接收 implementation 和初始化 calldata；提供非空 data 时会在构造阶段 delegatecall 到实现合约。当前版本默认不允许以空 calldata 留下未初始化的代理。

ERC1967Proxy 构造函数 Solidity 
constructor(address implementation, bytes memory data) payable {
    // 当前 OpenZeppelin 5.x：设置实现地址，并把 data delegatecall 到实现合约
    ERC1967Utils.upgradeToAndCall(implementation, data);
}

初始化完成后，owner() 返回部署者 EOA 地址：initialize() 中调用 __Ownable_init(msg.sender)，而代理构造阶段的 delegatecall 保留原始调用者的 msg.sender。

4

在区块浏览器验证合约 强烈推荐

验证代理合约和实现合约的源代码，使用户可以在 Etherscan 等浏览器上直接读取合约和调用函数。

  • 实现合约验证：标准的 Solidity 源码验证
  • 代理合约验证：验证为 ERC1967Proxy，浏览器会自动识别代理模式并提供 "Read as Proxy" / "Write as Proxy" 界面
  • 使用 hardhat verify 或 @nomicfoundation/hardhat-verify 插件自动化验证

Hardhat 部署脚本

scripts/deploy.ts TypeScript / Hardhat 
import hre from "hardhat";

async function main() {
  const connection = await hre.network.create();
  const { ethers } = connection;
  // ===== 配置参数 =====
  const FEE_BPS = 250;           // 2.5% 手续费
  const FEE_RECIPIENT = "0xYourTreasuryAddress...";

  const [deployer] = await ethers.getSigners();
  console.log(`Deployer: ${deployer.address}`);

  // ===== Step 1: 部署实现合约 =====
  console.log("\n[1/3] Deploying NFTMarket implementation...");
  const NFTMarket = await ethers.getContractFactory("NFTMarket");
  const implementation = await NFTMarket.deploy();
  await implementation.waitForDeployment();
  const implAddress = await implementation.getAddress();
  console.log(`  Implementation: ${implAddress}`);

  // ===== Step 2: 编码 initialize 调用数据 =====
  // initialize(uint256,address) 的 ABI 编码
  const initializeData = NFTMarket.interface.encodeFunctionData(
    "initialize",
    [FEE_BPS, FEE_RECIPIENT]
  );

  // ===== Step 3: 部署 ERC1967Proxy =====
  console.log("\n[2/3] Deploying ERC1967Proxy...");
  const ERC1967Proxy = await ethers.getContractFactory("ERC1967Proxy");
  const proxy = await ERC1967Proxy.deploy(implAddress, initializeData);
  await proxy.waitForDeployment();
  const proxyAddress = await proxy.getAddress();
  console.log(`  Proxy Address:  ${proxyAddress}`);

  // ===== Step 4: 验证初始化结果 =====
  console.log("\n[3/3] Verifying initialization...");
  const market = NFTMarket.attach(proxyAddress);
  console.log(`  owner():         ${await market.owner()}`);
  console.log(`  feeBps():         ${await market.feeBps()}`);
  console.log(`  feeRecipient():   ${await market.feeRecipient()}`);

  console.log("\n=== Deployment Complete ===");
  console.log(`Proxy: ${proxyAddress}`);
  console.log(`Impl:  ${implAddress}`);
}

main().catch((error) => {
  console.error(error);
  process.exit(1);
});
!
为什么不用 OpenZeppelin upgrades 插件的 deployProxy？
@openzeppelin/hardhat-upgrades 插件的 deployProxy() 会自动完成上述三步（部署实现 + 部署代理 + 初始化），非常方便。但手动部署能让你理解每一步发生了什么，也便于在不支持插件的环境中操作。生产环境推荐使用插件，它还会自动检查存储布局兼容性。
04 / OWNERSHIP

Owner 迁移到 Safe 多签

首次部署后 owner 是 EOA 账户，这意味着任何拿到该私钥的人都可以升级合约。生产环境必须将 owner 转移到 Gnosis Safe 多签钱包，使升级需要多个签名者共同确认。

!
为什么必须迁移到多签？
EOA 私钥是单点故障：电脑被入侵、私钥泄露、助记词丢失，都可能导致恶意升级或永久失去升级能力。Safe 多签要求 N 个签名者中至少 M 个确认（如 3/5），大幅提高安全性。
+
迁移时机
部署完成并验证无误后立即迁移。不要让 EOA owner 状态持续超过必要时间。迁移前确保 Safe 钱包已正确配置（签名者列表、阈值、链网络）。

Safe 多签配置建议

  • +签名者数量：3-5 人，阈值设为多数（如 3/5、2/3）
  • +签名者使用硬件钱包（Ledger / Trezor），不用热钱包
  • +签名者分布在不同地理位置、不同设备
  • +记录 Safe 地址和交易哈希，存档备查
  • +在测试网先演练完整的部署→迁移→升级流程

所有权迁移代码

scripts/transfer-ownership.ts TypeScript / Hardhat 
import hre from "hardhat";

async function main() {
  const connection = await hre.network.create();
  const { ethers } = connection;

  const PROXY_ADDRESS = "0x9f1...a4b7";     // 你的代理合约地址
  const SAFE_ADDRESS = "0xSafe...Address";    // 你的 Gnosis Safe 地址

  const [deployer] = await ethers.getSigners();
  console.log(`Current owner (EOA): ${deployer.address}`);

  // 附加到代理合约
  const NFTMarket = await ethers.getContractFactory("NFTMarket");
  const market = NFTMarket.attach(PROXY_ADDRESS);

  // 迁移前确认
  const currentOwner = await market.owner();
  if (currentOwner !== deployer.address) {
    throw new Error(`Deployer is not owner! Current owner: ${currentOwner}`);
  }

  // 执行所有权转移
  console.log(`\nTransferring ownership to Safe: ${SAFE_ADDRESS}`);
  const tx = await market.transferOwnership(SAFE_ADDRESS);
  await tx.wait();
  console.log(`Tx hash: ${tx.hash}`);

  // 验证
  const newOwner = await market.owner();
  console.log(`\nNew owner: ${newOwner}`);
  console.log(newOwner === SAFE_ADDRESS ? "✓ Ownership transferred successfully" : "✗ Transfer failed");
}

main().catch((error) => {
  console.error(error);
  process.exit(1);
});
!
迁移后 EOA 账户的处理
所有权转移后，原 EOA 不再具有升级权限。但该 EOA 仍可能有其他角色（如 Pauser），请检查并一并迁移或撤销。建议将 EOA 私钥安全冷存储，作为应急恢复的最后手段（但在多签正常工作时不应使用）。
05 / UPGRADE

后续升级完整流程

当需要添加新功能或修复 Bug 时，部署新的实现合约，然后由 owner（Safe 多签）通过代理合约调用 upgradeToAndCall() 将代理指向新实现。已有数据完全保留。

1

编写新实现合约 NFTMarketV2 存储兼容

新合约必须继承旧合约的存储布局，只能在末尾追加新状态变量。必须继续继承 UUPSUpgradeable 并实现 _authorizeUpgrade。

!
如果 V2 不再提供兼容的 UUPS 升级机制，OpenZeppelin 5.x 的 UUPS 实现会在升级时通过 ERC-1822 proxiableUUID() 做兼容性校验，通常会直接拒绝这次升级，因此代理仍停留在 V1。真正危险的是绕过这些检查的自定义升级机制，或部署了错误但仍满足接口的实现。
2

存储布局兼容性检查 必须

使用 OpenZeppelin upgrades 插件的 validateUpgrade() 或 hardhat upgrade:validate 检查新旧合约的存储布局是否兼容。

  • 检查项：变量类型变更、变量顺序变更、变量删除、结构体/枚举修改
  • 通过标准：旧变量的存储布局必须保持兼容；传统线性 storage 中新增变量通常追加在末尾
  • 使用 @openzeppelin/upgrades-core 的 storageLayout 对比工具
3

部署新实现合约 V2 EOA 或 Safe 发起

将 NFTMarketV2 部署到链上。这一步只部署实现合约，不影响代理。部署者可以是任意有 Gas 的账户，不要求是 owner。

  • 记录新实现合约地址
  • 在区块浏览器验证新合约源码
  • （可选）在测试网先完整演练升级流程
4

Safe 多签发起升级交易 多签确认 核心

在 Gnosis Safe 界面中，创建一笔交易调用代理合约的 upgradeToAndCall(newImplementation, bytes) 函数；如果不需要额外初始化，第二个参数传 0x。需要达到签名阈值（如 3/5）后才能执行。

  • 目标地址：Proxy 合约地址（不是实现合约）
  • 调用函数：upgradeToAndCall(address newImplementation, bytes data)
  • 参数：新部署的 V2 实现合约地址
  • 如果需要同时执行初始化（如设置新变量的初始值），使用 upgradeToAndCall(newImpl, data)
5

验证升级成功 必须

升级交易上链后，立即验证代理合约的实现地址已更新，且新功能正常工作。

  • 读取代理的实现槽位：ethers.getStorageAt(proxyAddress, IMPLEMENTATION_SLOT)
  • 确认返回值等于 V2 实现合约地址
  • 调用新函数（如 auctionNFT()）确认可执行
  • 确认旧数据完好：读取已有 listing、feeBps 等状态
  • 在区块浏览器确认代理已识别新实现（"Read as Proxy" 显示 V2 的 ABI）

升级脚本（准备 + 验证）

scripts/prepare-upgrade.ts TypeScript / Hardhat 
import hre from "hardhat";
import { upgrades } from "@openzeppelin/hardhat-upgrades";

async function main() {
  const connection = await hre.network.create();
  const { ethers } = connection;
  const upgradesApi = await upgrades(hre, connection);
  const PROXY_ADDRESS = "0x9f1...a4b7";  // 代理合约地址

  // ===== Step 1: 存储布局兼容性检查 =====
  console.log("[1/4] Validating storage layout compatibility...");
  const NFTMarketV2 = await ethers.getContractFactory("NFTMarketV2");
  // validateUpgrade 会检查 V1 -> V2 的存储兼容性
  await upgrades.validateUpgrade(PROXY_ADDRESS, NFTMarketV2);
  console.log("  ✓ Storage layout compatible");

  // ===== Step 2: 部署新实现合约 =====
  console.log("\n[2/4] Deploying NFTMarketV2 implementation...");
  const newImpl = await upgrades.prepareUpgrade(PROXY_ADDRESS, NFTMarketV2);
  const newImplAddress = await newImpl.getAddress();
  console.log(`  New implementation: ${newImplAddress}`);

  // ===== Step 3: 输出 Safe 交易参数 =====
  console.log("\n[3/4] Gnosis Safe transaction parameters:");
  console.log(`  To:             ${PROXY_ADDRESS}`);
  console.log(`  Function:       upgradeToAndCall(address, bytes)`);
  console.log(`  newImplementation: ${newImplAddress}`);

  // 编码 calldata（可直接在 Safe 中使用）
  const upgradeCalldata = NFTMarketV2.interface.encodeFunctionData(
    "upgradeTo",
    [newImplAddress]
  );
  console.log(`  Calldata:       ${upgradeCalldata}`);

  // ===== Step 4: 升级后验证（在 Safe 执行后运行）=====
  console.log("\n[4/4] After Safe execution, verify with:");
  console.log(`  const marketV2 = NFTMarketV2.attach("${PROXY_ADDRESS}");`);
  console.log(`  console.log(await marketV2.owner());        // 应为 Safe 地址`);
  console.log(`  console.log(await marketV2.feeBps());       // 旧数据应保留`);
  console.log(`  // 调用新函数确认升级成功`);
}

main().catch((error) => {
  console.error(error);
  process.exit(1);
});
i
upgradeTo vs upgradeToAndCall
upgradeToAndCall(newImpl, 0x)：仅切换实现地址，不执行额外调用。适用于新变量有默认值或不需要初始化的场景。
upgradeToAndCall(newImpl, data)：切换实现并在同一笔交易中 delegatecall 执行指定数据。若不需要迁移初始化，传 0x；若需要初始化新增状态，应在 V2 中提供版本化的迁移函数，例如 initializeV2() + reinitializer(2)。当前 OpenZeppelin 5.x 的接口本身没有单独的 forceCall 参数。
06 / SECURITY

安全检查清单与常见陷阱

可升级合约引入了额外的攻击面。以下清单覆盖部署、迁移和升级全流程的关键安全点。

部署阶段检查

  • +实现合约 constructor 中调用 _disableInitializers()
  • +initialize() 使用 initializer 修饰器，且只调用一次
  • +显式调用需要初始化的父合约 initializer，并避免同一父初始化函数被重复调用
  • +_authorizeUpgrade 使用 onlyOwner 限制
  • +部署后立即验证 owner()、各状态变量初始值
  • +代理和实现合约均在区块浏览器验证源码

多签迁移检查

  • +Safe 钱包已在正确的链上创建
  • +签名者使用硬件钱包，阈值设为多数
  • +迁移前确认 EOA 是当前 owner
  • +迁移后验证 owner() == Safe 地址
  • +检查并迁移其他角色（Pauser、Minter 等）
  • +原 EOA 私钥冷存储，不丢弃

升级阶段检查

  • +新合约保留兼容的 UUPS 升级机制，并通过 OpenZeppelin 校验工具检查
  • +存储布局兼容性检查通过
  • +自定义线性 storage 变量按兼容规则追加；ERC-7201 namespace 按其 namespace 规则演进
  • +新合约通过完整测试套件（含升级测试）
  • +在测试网/主网 fork 演练完整升级
  • +升级后验证实现地址、旧数据、新功能

持续安全运营

  • +监控 ERC-1967 Implementation 变更及对应的 Upgraded 事件
  • +建立升级的 Timelock（时间锁）延迟
  • +升级前公开审计报告和变更说明
  • +保留紧急暂停（Pausable）能力
  • +定期轮换 Safe 签名者
  • +保留旧实现地址、源码、构建产物和审计记录；不要把“旧实现不销毁”当作回滚机制

常见致命陷阱

1
新实现忘记继承 UUPSUpgradeable
UUPS 的升级机制位于实现合约中。当前 OpenZeppelin 5.x 使用 upgradeToAndCall()，并在升级时校验新实现的 ERC-1822 UUID；如果 V2 不兼容，升级交易会回滚，而不是让代理先切换到一个不可升级实现。因此不要把“缺少 UUPS”描述成升级成功后的必然永久锁死。
2
存储布局错乱
在旧变量中间插入新变量、修改变量类型、删除变量、重排结构体字段，都会导致存储槽位错位。例如在传统线性 storage 中，如果 V1 的自定义变量已经占据前部槽位，V2 却在这些变量之前插入新变量，就会改变后续变量的槽位解释，导致已有数据被错误读取。具体槽位应通过编译器和 storage layout 工具确认，不应硬编码“feeBps 一定在 slot 2”。使用 storage gap 预留空间，用工具自动检查。
3
实现合约自身被初始化攻击
实现合约本身也在链上，如果不在 constructor 中调用 _disableInitializers()，攻击者可能直接调用实现合约的 initialize()，在实现合约自己的存储中取得 owner；但 UUPS 的 onlyProxy 检查会阻止从实现合约自身直接执行升级。仍然应使用 _disableInitializers() 锁定实现合约，避免不必要的初始化状态和与其他逻辑组合产生风险。
4
constructor 中的逻辑不会执行
代理合约通过 delegatecall 调用实现合约，但实现合约的 constructor 只在部署实现合约时执行一次，且是在实现合约自己的存储上下文中执行。因此 所有初始化逻辑必须放在 initialize() 中，不能依赖 constructor 设置状态变量。
