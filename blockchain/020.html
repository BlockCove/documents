1. 为什么需要代理升级

智能合约一旦部署即不可变。要在保留地址与存储状态的前提下替换业务逻辑，唯一通用手段是代理模式：用户与一个永不更换的 Proxy 合约交互，Proxy 通过 delegatecall 把调用转发给可替换的 Implementation（逻辑合约）。

flowchart LR U([User]) -->|call| P[Proxy 合约
地址永久不变
存储状态在这里] P -->|delegatecall| I[Implementation
业务逻辑可替换] style P fill:#1f6feb,stroke:#58a6ff,color:#fff style I fill:#238636,stroke:#7ee787,color:#fff

delegatecall 的关键语义：代码在 Implementation 中运行，但上下文（msg.sender / msg.value / 存储）属于 Proxy。因此状态永远留在 Proxy，升级只需把 Proxy 指向的 Implementation 地址换掉。

核心矛盾：Proxy 自己也要存"implementation 地址"等元数据，而 Implementation 的状态变量也按槽位写存储——两者必须不冲突，这就是 EIP-1967 要解决的问题。

2. 共同地基：EIP-1967 代理存储槽

EIP-1967 定义了一组伪随机存储槽，通过 keccak256 计算并减 1，使代理元数据几乎不可能与逻辑合约的正常状态变量冲突。所有现代代理（透明 / UUPS / 信标）都基于它。

槽位值用途
Implementation 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc 当前逻辑合约地址
Admin 0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103 可升级代理的管理员地址（透明代理用）
Beacon 0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50 信标合约地址（信标代理用，此时 implementation 槽为空）

计算方式示例：bytes32(uint256(keccak256("eip1967.proxy.implementation")) - 1)

3. 透明代理 Transparent Proxy

基于 EIP-1967可升级OpenZeppelin TransparentUpgradeableProxy 是最经典的实现。升级逻辑写在 Proxy 合约里，并通过一个独立的 ProxyAdmin 合约管理。

3.1 解决什么问题

  • 函数选择器冲突：如果 Implementation 里也有 upgradeTo()，admin 调用时到底走代理的升级函数还是 delegate 到实现？透明代理用调用者身份解决：admin 调用永远走 Proxy 自身逻辑，普通用户调用永远 delegatecall。对用户来说"看不到"代理的存在，故称"透明"。
  • 把升级权限与业务权限隔离，admin 地址通常是多签或 ProxyAdmin 合约。

优点
  • 升级逻辑与业务逻辑彻底分离，Implementation 可以是任意普通合约，无需继承任何 upgradeable 基类
  • admin / user 双轨 dispatch，函数选择器冲突由代理层解决，心智简单
  • 生态最成熟，OpenZeppelin / Hardhat / Foundry 工具链一等支持
  • 即使 Implementation 被破坏，只要 Proxy 本身安全仍可升级（升级入口不在实现里）
缺点
  • 每笔用户交易都要多一次 admin 身份判断（读 admin 槽 + 比较），gas 比 UUPS 略高
  • Proxy 字节码更重，部署 gas 更高
  • admin 地址不能调用任何业务函数（会被拦截并 revert），实战中必须用 ProxyAdmin 合约或第二个地址当 admin
  • 升级权限集中在 ProxyAdmin，仍是单点

4. UUPS 通用可升级代理（EIP-1822）

EIP-1822可升级UUPS（Universal upgradable proxy standard）的核心思想：把升级逻辑从 Proxy 移到 Implementation 里。Proxy 退化为一个极简的 EIP-1967 存储 + delegatecall 转发器，本身完全不知道"升级"是什么。

4.1 解决什么问题

  • 透明代理每笔交易都做 admin 检查，浪费 gas。UUPS 让 Proxy 只做纯转发，用户交易更便宜。
  • Proxy 字节码极小，部署成本低。
  • "通用"在于：任何实现合约只要包含 proxiableUUID() 并把升级函数写在自己里面，就能被同一个极简 Proxy 承载。

// === 极简 Proxy（OpenZeppelin ERC1967Proxy，没有任何升级代码）===
contract ERC1967Proxy {
    constructor(address impl, bytes memory data) payable {
        _upgradeToAndCall(impl, data);
    }
    fallback() external payable {
        address impl = _implementation(); // 读 EIP-1967 槽
        assembly {
            calldatacopy(0, 0, calldatasize())
            let result := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
            returndatacopy(0, 0, returndatasize())
            switch result
            case 0 { revert(0, returndatasize()) }
            default { return(0, returndatasize()) }
        }
    }
}

// === Implementation 侧（继承 UUPSUpgradeable）===
contract MyLogicV1 is Initializable, OwnableUpgradeable, UUPSUpgradeable {
    function initialize() external initializer {
        __Ownable_init();
        __UUPSUpgradeable_init();
    }
    // 关键：授权升级的钩子，必须重写，否则任何人都能升级
    function _authorizeUpgrade(address) internal override onlyOwner {}

    // proxiableUUID() 返回 EIP-1967 implementation 槽，
    // 升级前会 staticcall 新实现的此函数做兼容性校验
}
致命陷阱：如果某次升级把 Implementation 换成一个不含 UUPS 升级逻辑的合约，Proxy 就永远失去升级能力——因为升级函数本身在实现里。OpenZeppelin 的 UUPSUpgradeable 默认会在升级前调用新实现的 proxiableUUID() 做校验，防止这种"自杀式升级"，但自定义实现时必须自己保证。
优点
  • Proxy 极简，用户交易 gas 最低（无 admin 判断）
  • 部署 Proxy 的 gas 远低于透明代理
  • 同一个 ERC1967Proxy 可承载任意 UUPS 实现，通用性强
  • 升级权限可与业务权限用同一套 Ownable / AccessControl 管理，无需额外 ProxyAdmin
缺点
  • 升级逻辑在 Implementation 里，实现合约必须继承 UUPSUpgradeable，不能是任意普通合约
  • 若升级到不含升级函数的实现，永久锁死不可再升级
  • 函数选择器冲突需自己处理（实现里若有与升级函数同 selector 的函数会冲突）
  • 实现合约被破坏时，升级入口也可能一起被破坏
  • 必须用 initializer 代替 constructor，且不能有 immutable 变量（immutable 是部署时内联到字节码的，delegatecall 上下文读不到正确值）

5. 钻石代理 Diamond / Multi-Facet Proxy（EIP-2535）

EIP-2535可升级由 Nick Mudge 提出。前面几种代理都是 1 个 Proxy → 1 个 Implementation；Diamond 是 1 个 Diamond → N 个 Facet（切面），按 function selector 路由到不同的逻辑合约。

5.1 解决什么问题

  • 单合约 24KB 大小限制：复杂协议（如 Aave、Uniswap 级别）一个实现合约根本装不下。Diamond 把功能拆到多个 Facet，每个 Facet 独立部署，整体无上限。
  • 模块化升级：只需升级出问题的那个 Facet，不用重部署整个实现；不同模块可独立迭代、独立审计。
  • 统一地址 + 统一存储：用户只看到一个 Diamond 地址，所有 Facet 共享 Diamond 的存储（通过 Diamond Storage 模式按命名空间隔离）。

5.4 关键代码：diamondCut 与 fallback 路由

// === Diamond 的 fallback：按 selector 查 facet 再 delegatecall ===
fallback() external payable {
    address facet = _facetAddress(msg.sig); // 从映射表查
    require(facet != address(0), "Diamond: function does not exist");
    assembly {
        calldatacopy(0, 0, calldatasize())
        let result := delegatecall(gas(), facet, 0, calldatasize(), 0, 0)
        returndatacopy(0, 0, returndatasize())
        switch result
        case 0 { revert(0, returndatasize()) }
        default { return(0, returndatasize()) }
    }
}

// === diamondCut：原子增删替换（伪代码）===
struct FacetCut {
    address facetAddress;
    FacetCutAction action;   // Add = 0, Replace = 1, Remove = 2
    bytes4[] functionSelectors;
}
function diamondCut(FacetCut[] calldata _diamondCut, address _init, bytes calldata _calldata) external {
    enforceIsContractOwner();
    _diamondCut(_diamondCut);   // 更新 selector→facet 映射
    if (_init != address(0)) {
        _init.delegatecall(_calldata); // 可选初始化回调
    }
}

// === Diamond Storage：Facet 之间用命名空间隔离存储，避免槽冲突 ===
library LibERC20 {
    bytes32 constant POSITION = keccak256("diamond.storage.erc20");
    struct Data { mapping(address=>uint256) balances; uint256 totalSupply; }
    function data() internal pure returns(Data storage s) {
        bytes32 p = POSITION;
        assembly { s.slot := p }
    }
}
优点
  • 突破 24KB 合约大小限制，功能可无限扩展
  • 模块化升级：只替换出问题的 Facet，粒度细、风险小、gas 低
  • 不同 Facet 可独立开发、独立审计、独立部署团队
  • 统一地址对外，用户体验与单合约一致
  • Diamond Storage 命名空间天然避免存储冲突，比传统继承式存储更安全
  • 支持"不可变函数"（immutable functions）：可声明某些 selector 永远不可被替换/移除
缺点
  • 学习曲线陡峭，Diamond Storage、selector 管理、Loupe 内省等概念多
  • 调试复杂：一个调用到底进了哪个 Facet，需要查映射表
  • 生态工具支持不如透明/UUPS 成熟（虽有 hardhat-deploy、foundry 插件）
  • selector 冲突管理是负担：两个 Facet 不能注册同一个 selector
  • 安全审计成本高，攻击面随 Facet 数量增加
  • 普通中小项目过度设计，没必要

6. 信标代理 Beacon Proxy

基于 EIP-1967可升级引入一个中间层 Beacon 合约。Proxy 不直接存 implementation 地址，而是存 Beacon 地址；Beacon 里存真正的 implementation。升级 Beacon 一次，所有指向它的 Proxy 同时升级。

6.1 解决什么问题

  • 批量同质合约升级：典型场景是工厂模式——一个 Factory 部署出成百上千个相同逻辑的代理（如每个用户一个金库、每对交易对一个池子）。若用透明/UUPS，升级需要逐个调用每个代理的 upgradeTo，gas 爆炸且易遗漏。Beacon 只需升级一次。
  • 逻辑版本统一管理，避免不同实例跑不同版本造成状态不一致。

6.3 关键代码

// === BeaconProxy：fallback 里先读 Beacon，再从 Beacon 读 implementation ===
contract BeaconProxy {
    constructor(address beacon, bytes memory data) payable {
        _setBeacon(beacon);  // 写 EIP-1967 beacon 槽
        if (data.length > 0) _functionDelegateCall(_implementation(), data);
    }
    function _implementation() internal view override returns(address) {
        return IBeacon(_beacon()).implementation(); // 多一次外部调用
    }
    fallback() external payable {
        address impl = _implementation();
        assembly { /* 同标准 delegatecall 转发 */ }
    }
}

// === UpgradeableBeacon：被 owner 升级，所有代理立即生效 ===
contract UpgradeableBeacon is IBeacon {
    address private _implementation;
    constructor(address initialImpl) { _implementation = initialImpl; }
    function implementation() external view override returns(address) { return _implementation; }
    function upgradeTo(address newImpl) external onlyOwner {
        _setImplementation(newImpl);
        emit Upgraded(newImpl);
    }
}
优点
  • 一次升级，N 个同质代理同时生效，工厂模式的标准解法
  • 逻辑版本全局统一，不会出现部分实例未升级
  • 单个 Proxy 仍极简（比透明代理轻）
  • 可动态切换 Beacon，实现一组实例整体迁移到另一套逻辑
缺点
  • 每笔用户交易多一次外部调用（Proxy → Beacon.implementation()），gas 比 UUPS/透明都高
  • Beacon 是单点：Beacon 升级错误会同时影响所有实例，爆炸半径大
  • 无法单独升级某一个代理（要单独升级需先切换它的 Beacon）
  • 多一层间接，调试和区块浏览器验证更麻烦
  • 仅适合"大量同质实例"场景，单实例用它是过度设计

7. 最小代理 Minimal Proxy / Clone（EIP-1167）

EIP-1167不可升级前面四种都是"可升级"代理；最小代理是不可升级的极简克隆。它的运行时字节码只有 45 字节（含地址共 55 字节 init 描述），唯一功能就是把所有调用 delegatecall 到一个硬编码在字节码里的固定实现地址。

7.1 解决什么问题

  • 极致省 gas 部署大量同质合约：工厂模式下，每个实例如果完整部署一份逻辑合约，gas 极高。用最小代理，只需部署一次逻辑合约，之后每个实例只花 ~55 字节的部署 gas（约为完整部署的 1/10 甚至更低）。
  • 逻辑复用 + 状态隔离：所有 Clone 共享同一份实现代码，但每个 Clone 有独立存储和地址。
  • 典型场景：Uniswap V2/V3 交易对、每用户金库、NFT 碎片化合约、GameFi 中每个玩家/道具一个实例。

7.4 关键代码：工厂用 CREATE2 部署最小代理

// OpenZeppelin Clones 库的核心（简化）
library Clones {
    function cloneDeterministic(address implementation, bytes32 salt) internal returns(address instance) {
        bytes memory creationCode = _getCreationCode(implementation);
        assembly {
            instance := create2(0, add(creationCode, 0x20), mload(creationCode), salt)
        }
        require(instance != address(0), "ERC1167: create2 failed");
    }
    // creationCode = 10 字节前缀 + 20 字节地址 + 15 字节后缀，
    // 部署时把这段 runtime code 写入新合约
}

// === 工厂合约 ===
contract VaultFactory {
    address public immutable implementation;
    constructor(address _impl) { implementation = _impl; }
    function createVault(bytes32 salt) external returns(address vault) {
        vault = Clones.cloneDeterministic(implementation, salt);
        IVault(vault).initialize(msg.sender); // 必须用 initialize，不能用 constructor
    }
}
注意：EIP-1167 最小代理本身不可升级（实现地址硬编码在字节码里，没有存储槽可改）。如果需要"可升级的克隆"，有两种思路：① 让被 clone 的 Implementation 本身是一个 UUPS/透明代理（套娃）；② 使用 ERC-7760 Minimal Upgradeable Proxies（在 EIP-1167 基础上把实现地址改存到 EIP-1967 槽）。
优点
  • 部署 gas 极低（~55 字节，通常 10 万 gas 以内），大规模克隆场景成本优势巨大
  • 字节码极简，审计成本低，几乎无攻击面
  • CREATE2 可预先计算地址，支持反事实部署（counterfactual）
  • 逻辑合约只部署一次，代码复用率高
  • 每个 Clone 独立地址、独立存储，互不干扰
缺点
  • 不可升级：实现地址硬编码，发现 bug 无法修复（只能部署新 Clone 并迁移状态）
  • 实现合约必须用 initialize() 初始化，不能用 constructor
  • 不能用 immutable 变量（原因同 UUPS）
  • 区块浏览器默认不会把 Clone 识别为代理，需要特殊插件/手动验证
  • 所有 Clone 共享实现合约的代码，若实现合约有 bug 则全部受影响（且无法升级修复）

10. 升级安全陷阱清单

10.1 存储碰撞（Storage Collision）— 最常见漏洞

升级时新实现的状态变量顺序/类型必须与旧实现兼容。在旧变量中间插入新变量会导致所有后续变量槽位错位，状态错乱。

  • 透明/UUPS：用 OpenZeppelin @openzeppelin/contracts-upgradeable + storage-upgrade-core 插件在编译时检查。
  • Diamond：用 Diamond Storage 命名空间天然规避，但跨 Facet 共享 struct 时仍需谨慎。
  • 禁止在已有变量中间插入、修改变量类型、修改变量声明顺序。新变量只能追加在末尾。

10.2 未初始化的实现合约（Takeover 风险）

Implementation 合约本身如果有 initialize() 且未调用，攻击者可以直接调用它的 initialize() 夺取实现合约的 owner，然后在实现合约上自毁（selfdestruct）或做其他破坏。虽然 delegatecall 用的是 Proxy 状态，但实现合约被接管后仍有风险（如通过 selfdestruct 删除代码导致所有调用失败）。

防护：OpenZeppelin 的 Initializable 提供 _disableInitializers()，在实现合约的 constructor 中调用，永久禁用其直接初始化。

contract MyLogicV1 is Initializable {
    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }
}

10.3 UUPS 自杀式升级

升级到不含 UUPSUpgradeable 的实现 → 永久失去升级能力。OpenZeppelin 默认通过 proxiableUUID() 校验阻止，但自定义实现必须自己做。

10.4 函数选择器冲突

  • 透明代理：admin 调用 upgradeTo 时若实现里也有同 selector 函数，admin 走代理逻辑（不会 delegate），user 调用则走实现——这是设计如此，但要意识到 admin 永远调不到实现里的同名函数。
  • UUPS：实现里的业务函数不能与 upgradeTo / upgradeToAndCall 同 selector。
  • Diamond：两个 Facet 不能注册同一个 selector，diamondCut 会 revert。

10.5 升级权限中心化

所有可升级模式都意味着"拥有升级密钥的人可以任意更改合约逻辑"，这本质上是一个后门。生产环境必须：

  • 用多签（Gnosis Safe）或 Timelock 控制升级权限，避免单点私钥泄露
  • Timelock 给用户留出退出时间（升级延迟 24-48 小时）
  • 对不需要长期升级的合约，部署稳定后 renounceOwnership 或转移到零地址，永久锁死

10.6 constructor / immutable 陷阱

  • 实现合约的 constructor 只在部署实现时执行一次，不会在 Proxy 上下文执行。所以初始化必须用 initialize()。
  • immutable 变量在部署时被内联到实现合约的运行时字节码中。delegatecall 时代码来自实现合约，所以 immutable 实际上能读到值——但这个值是实现合约部署时确定的，对所有 Proxy 共享，不能用来存 Proxy 特有的值（如 owner）。OpenZeppelin upgradeable 合约因此禁用 immutable 存实例相关数据。

10.7 delegatecall 上下文与 msg.sender

delegatecall 中 msg.sender 是原始调用者（不是 Proxy），address(this) 是 Proxy 地址。实现合约里所有基于 address(this) 的逻辑（如计算 CREATE2 地址、域名分离器 EIP-712 domain）都会正确使用 Proxy 地址——这通常是期望的，但实现合约单独部署测试时要注意上下文差异。
