一、什么是 SIWE

SIWE（Sign-In with Ethereum） 是 EIP-4361（当前以 ERC-4361 形式登记）定义的一套标准化"用以太坊账户登录"协议。用户通过钱包（MetaMask 等）对一段符合 EIP-4361 的人类可读结构化文本进行链下签名，服务端验证签名及消息中的安全字段后，可以建立与该以太坊地址绑定的 Web 会话。整个签名过程不需要发起链上交易，因此不会产生登录本身的 Gas 消耗。

一句话类比：传统登录 = 你输入密码，服务器比对哈希；SIWE = 你用私钥在"挑战纸条"上签字，服务器用你的公钥（地址）验真。私钥永不离开钱包。
标准编号
EIP-4361（现登记为 ERC-4361）
签名方法
EOA 通常使用 personal_sign / ERC-191；SIWE 规范本身不是 EIP-712 typed-data 协议
验签算法
EOA：ERC-191 + ECDSA/secp256k1；合约钱包：按 EIP-1271 在对应 chain ID 上验证
是否上链
否，纯离线签名
常用库
siwe、ethers.js、viem

二、核心原理

1. 非对称加密基石

以太坊账户基于 secp256k1 椭圆曲线：

  • EOA 私钥：256 bit 标量，通常由安全随机数生成并由钱包持有，永不外泄。
  • EOA 公钥：由私钥通过 secp256k1 椭圆曲线运算派生；从公钥反推出私钥在计算上不可行。
  • EOA 地址：对未压缩公钥去掉前导 0x04 后做 Keccak-256，取最后 20 字节并加 0x；合约账户的地址并不由此规则“从公钥派生”。

对于 EOA，签名遵循 ERC-191：钱包对 SIWE 原文按 ERC-191 personal-sign 规则处理后使用 secp256k1 签名；服务端可从消息 + 签名恢复签名者地址，再与消息里的 address 比对。对于合约钱包，则应按 EIP-1271 在指定 chainId 对应网络上进行验证。

2. 挑战-响应（Challenge-Response）

为防止重放攻击，服务端每次下发一个随机 nonce（挑战值），用户签名必须包含该 nonce。服务端校验 nonce 未被使用过且在有效期内。

3. 域绑定（Domain Binding）

SIWE 消息必须包含 domain 和 uri。其中 domain 表示请求签名的站点 authority，uri 是签名所针对的资源 URI；服务端必须校验它们是否符合本站和本次请求的预期，钱包也应根据请求来源校验 scheme/domain，共同降低跨站和钓鱼风险。不是“签名天然只能在本站使用”，而是依赖钱包与服务端正确执行域绑定校验。

4. 会话签发

验签通过后，服务端签发传统 Session / JWT，后续请求走普通 Web 认证，不再每次签名。

三、EIP-4361 消息格式

SIWE 消息是一段人类可读的结构化文本，钱包会原样展示给用户确认：

example.com  wants you to sign in with your Ethereum account:
0xC02aaA39b223FE8D0A0e5C4F27eAD9083C756Cc2

I accept the ExampleOrg Terms of Service: https://example.com/tos

URI: https://example.com/login
Version: 1
Chain ID: 1
Nonce: 32891756
Issued At: 2021-09-30T16:25:24Z
Resources:
- ipfs://bafybeiemxf5abjwjbikoz4mc3a3dla6ual3jsgpdr4cjr3oz3evfyavhwq/
- https://example.com/my-web2-claim.json
字段必填作用
domain是请求签名的域名，防跨站
address是签名者以太坊地址
statement否人类可读声明；禁止换行，可用于说明登录目的或条款
uri是签名所针对资源的 RFC 3986 URI；不应简单等同于 Origin
version是固定为 1
chainId是链 ID（1=以太坊主网）
nonce是每次会话初始化使用的随机字符串，至少 8 个字母/数字字符，用于防重放
issuedAt是签发时间 ISO 8601
expirationTime否签名过期时间
notBefore否生效时间
requestId否系统内部请求 ID
resources否声明关联的资源 URI 列表

七、安全要点

攻击面防御措施
重放攻击nonce 一次性 + 短 TTL，验证后立即销毁
跨站 / 钓鱼服务端严格校验 domain（以及 scheme），并校验 uri；浏览器钱包也应做请求来源校验
链 ID 混淆严格校验 chainId 与服务端允许的网络；它用于把会话绑定到指定网络
签名过期可设置 expirationTime/notBefore，服务端验证时间窗口
statement 欺骗statement 只是用户可读声明，不应单独承担授权语义；对敏感操作应在服务端校验预期内容
会话劫持Cookie 使用 HttpOnly; Secure，并根据部署场景设置合适的 SameSite
CSRFCookie 会话应结合 SameSite 与 CSRF Token 或 Origin/Referer 校验；不要把“自定义 Header”本身当作完整 CSRF 防线
合约钱包对智能合约账户支持 EIP-1271；不能只依赖 ecrecover
SIWE ≠ 授权：它主要解决“证明某个 Ethereum account 控制权并建立会话”（Authentication），不定义你的业务权限（Authorization）。登录后权限体系仍由后端业务逻辑控制。

EOA 与合约钱包：不要只看 ecrecover

SIWE 规范区分两类账户：EOA 可按 ERC-191 验签；合约账户推荐按 EIP-1271 在消息指定的 chainId 对应网络上验证。也就是说，“SIWE 登录”不等于“所有钱包都能直接用本地 ecrecover 验签”。
