区块链扫链分叉回滚（Reorg）解决方案

一、问题本质

当前代码直接将链上事件写入 DB，但区块链存在链重组（Chain Reorg）现象：当分叉发生时，已确认的区块可能被废弃，对应事件也应回滚。代码无任何回滚机制，导致 DB 数据与最终链状态不一致。

核心矛盾：区块链是"最终一致性"系统，而 DB 写入是"立即持久化"。扫链程序把"可能被回滚的临时状态"当成了"最终状态"写入。
图1：链分叉与回滚示意

二、方案总览

方案 核心思路 适用场景 实现复杂度 数据一致性
确认数延迟写入 等 N 个区块确认后再写 DB 对实时性要求不高 低 高（N足够大时）
回滚检测 + 重放 实时写入，检测到分叉就回滚并重放 需要实时性 + 一致性 中 最终一致
事件溯源（Event Sourcing） 只存原始事件，状态按需计算 状态复杂、需审计追溯 高 极强
影子表 + 原子切换 后台重算，完成后切换表 数据量不大、可接受延迟 中 高

三、推荐方案：确认数 + 回滚检测 混合模式

这是业界（The Graph、Etherscan、Dune Analytics 等）最常用的生产级方案，兼顾实时性与一致性。

3.2 确认数机制（第一道防线）

3.2.1 原理：为什么等待确认能防回滚

区块链的共识机制（最长链原则 / GHOST 协议）决定了：区块后面堆叠的子区块越多，这条链成为最终共识的概率越大。等待 N 个确认，本质上是在等"概率收敛"——区块被推翻的概率随确认数指数级下降。

图2-1：确认数与回滚概率的关系

PoW 链（如旧版以太坊、BTC）：回滚概率遵循公式 P = (q/p)^N，其中 q 是攻击者算力，p 是诚实算力。N 足够大时概率趋近于零。

PoS 链（如以太坊信标链）：有更明确的"最终性"概念——2 个 epoch（≈12.8 分钟）后区块被认为"经济最终确认"，回滚需要销毁海量质押 ETH，实际不可能发生。

链类型推荐确认数说明
以太坊主网（PoS）12 ~ 322 个 epoch（≈12.8 min）基本不可逆；32 个为安全冗余
BSC / Polygon15 ~ 30出块快（2~3s），分叉概率略高，需更多确认
Arbitrum / Optimism64 ~ 128L2 区块需等 L1 最终确认，延迟更高
测试网3 ~ 5算力/验证节点少，仅供开发调试

3.2.2 实现：滑动窗口确认队列

核心思路：维护一个按区块号排序的待确认事件队列，每当新区块到来时，将队列中"年龄"超过 N 的事件批量写入 DB。

图2-2：滑动窗口确认队列示意
package scanner

import (
    "sort"
    "github.com/ethereum/go-ethereum/core/types"
)

// ConfirmationQueue 确认数等待队列
// 线程安全：生产环境建议加 mutex 或用 channel
type ConfirmationQueue struct {
    confirmations int            // 需要的确认数
    items         []PendingEvent // 按区块号升序排列
}

type PendingEvent struct {
    BlockNumber uint64
    BlockHash   string
    Log         types.Log
    // 预解析的事件数据，避免写入时重复解析
    EventData interface{}
}

func NewConfirmationQueue(n int) *ConfirmationQueue {
    return &ConfirmationQueue{
        confirmations: n,
        items:         make([]PendingEvent, 0, 1024),
    }
}

// Push 批量追加新事件（保持有序）
func (q *ConfirmationQueue) Push(events []PendingEvent) {
    q.items = append(q.items, events...)
    // 按 (区块号, 交易序号, 日志序号) 排序，保证写入顺序与链上一致
    sort.Slice(q.items, func(i, j int) bool {
        if q.items[i].BlockNumber != q.items[j].BlockNumber {
            return q.items[i].BlockNumber < q.items[j].BlockNumber
        }
        if q.items[i].Log.TxIndex != q.items[j].Log.TxIndex {
            return q.items[i].Log.TxIndex < q.items[j].Log.TxIndex
        }
        return q.items[i].Log.Index < q.items[j].Log.Index
    })
}

// Flush 取出所有已获得足够确认的事件
// currentBlock: 当前最新区块号
func (q *ConfirmationQueue) Flush(currentBlock uint64) []PendingEvent {
    if currentBlock < uint64(q.confirmations) {
        return nil
    }
    cutoff := currentBlock - uint64(q.confirmations)

    // 二分查找第一个超过 cutoff 的位置
    idx := sort.Search(len(q.items), func(i int) bool {
        return q.items[i].BlockNumber > cutoff
    })

    ready := q.items[:idx]
    q.items = q.items[idx:]
    return ready
}

// Rollback 回滚到指定区块（删除该区块及之后的所有待确认事件）
// 当检测到链重组时调用
func (q *ConfirmationQueue) Rollback(toBlock uint64) {
    idx := sort.Search(len(q.items), func(i int) bool {
        return q.items[i].BlockNumber >= toBlock
    })
    q.items = q.items[:idx]
}

// Len 返回队列长度，用于监控
func (q *ConfirmationQueue) Len() int {
    return len(q.items)
}

3.2.3 集成到扫描器

func (s *Scanner) Start() error {
    // 初始化确认队列
    s.confQueue = NewConfirmationQueue(s.Config.Confirmations)

    // 订阅新区块头（实时驱动确认窗口滑动）
    headers := make(chan *types.Header, 16)
    sub, err := s.Client.SubscribeNewHead(context.Background(), headers)
    if err != nil {
        return err
    }
    defer sub.Unsubscribe()

    for {
        select {
        case header := <-headers:
            currentBlock := header.Number.Uint64()

            // 1. 扫描新区块的事件，加入确认队列
            events, err := s.scanBlock(currentBlock)
            if err != nil {
                log.Printf("scan block %d failed: %v", currentBlock, err)
                continue
            }
            s.confQueue.Push(events)

            // 2. 刷新已确认的事件到 DB
            ready := s.confQueue.Flush(currentBlock)
            if len(ready) > 0 {
                if err := s.writeBatchToDB(ready); err != nil {
                    log.Printf("write batch failed: %v", err)
                    // 写入失败的事件保留在队列中下次重试
                    // 实际实现需要更精细的错误处理
                }
            }

            // 3. 更新扫描进度
            s.updateLastScanned(currentBlock, header.Hash())

        case err := <-sub.Err():
            return err
        }
    }
}
优点：实现简单，绝大多数场景下（N 足够大）不会遇到回滚；写入 DB 的数据都是"高置信度"的。
缺点：数据有 N 个区块的延迟，不适合需要实时展示的场景；极端深回滚仍需配合回滚检测机制。

3.3 types.Log.Removed — 原生回滚通知（第二道防线）

3.3.1 字段定义与含义

go-ethereum 的 types.Log 结构体中有一个常被忽略的字段 Removed bool，它是以太坊 JSON-RPC 协议中 eth_getLogs / eth_subscribe 的标准字段，专门用于通知链重组。

// go-ethereum/core/types/log.go
type Log struct {
    Address     common.Address  // 合约地址
    Topics      []common.Hash   // 事件主题（含 event signature）
    Data        []byte          // 非索引参数
    BlockNumber uint64          // 区块号
    TxHash      common.Hash     // 交易 hash
    TxIndex     uint            // 交易在区块中的序号
    BlockHash   common.Hash     // 区块 hash
    Index       uint            // 日志在区块中的序号
    Removed     bool            // ⭐ 该日志是否因链重组而被移除
}
关键含义：
• Removed = false（默认）：这条日志是正常的、新产生的事件。
• Removed = true：这条日志对应的区块因链分叉被废弃，事件已从链上移除，需要回滚。

3.3.2 触发场景

Removed=true 的日志只会在订阅模式（eth_subscribe）下出现，不会在一次性查询（eth_getLogs / FilterLogs）中出现。原因是：

  • FilterLogs：查询的是"当前链状态下"的历史日志，返回的都是当前有效链上的日志，不存在"被移除"的概念。
  • Subscribe：是持续推送的流，当链重组发生时，节点会主动推送 Removed=true 的日志来通知客户端"之前推过的那条日志现在无效了"。
图3-1：Removed 日志的产生时机

3.3.3 使用方式：订阅模式下的事件处理

当前代码用的是 FilterLogs（拉模式），不会收到 Removed 通知。如果改用 SubscribeFilterLogs（推模式），就能实时感知回滚。

func (s *Scanner) subscribeLogs() error {
    query := ethereum.FilterQuery{
        Addresses: []common.Address{poolManagerAddr, positionManagerAddr},
        Topics:    [][]common.Hash{{SigPoolCreated, SigTransfer}},
    }

    logs := make(chan types.Log, 256)
    sub, err := s.Client.SubscribeFilterLogs(context.Background(), query, logs)
    if err != nil {
        return err
    }
    defer sub.Unsubscribe()

    for {
        select {
        case vLog := <-logs:
            if vLog.Removed {
                // ⭐ 事件被回滚，执行反向操作
                log.Printf("🔄  Log removed due to reorg: tx=%s, block=%d",
                    vLog.TxHash.Hex(), vLog.BlockNumber)
                s.handleLogRemoved(vLog)
            } else {
                // 正常事件，加入确认队列或直接处理
                s.handleLog(vLog)
            }
        case err := <-sub.Err():
            return err
        }
    }
}

// handleLogRemoved 处理被回滚的日志（反向操作）
func (s *Scanner) handleLogRemoved(vLog types.Log) {
    switch vLog.Topics[0] {
    case SigSwap:
        // 回滚 Swap：从 DB 删除该交易，反向更新池子状态
        s.rollbackSwap(vLog.TxHash, vLog.BlockNumber)
    case SigMint:
        s.rollbackMint(vLog.TxHash, vLog.BlockNumber)
    case SigBurn:
        s.rollbackBurn(vLog.TxHash, vLog.BlockNumber)
    case SigPoolCreated:
        // 注意：池子创建被回滚比较危险，要确保没有依赖数据
        s.rollbackPoolCreated(vLog)
    case SigTransfer:
        s.rollbackPositionTransfer(vLog)
    }
}
重要注意事项：
  • 只有订阅模式才有 Removed：FilterLogs / GetLogs 不会返回 Removed=true 的日志，因为它们查询的是当前链状态。
  • Removed 日志可能乱序到达：不要假设 Removed 一定在事件之后很久才到，也可能很快。处理时必须幂等。
  • 不能完全依赖 Removed：如果订阅断开重连，期间的回滚事件会丢失。必须配合区块 hash 比对做兜底。
  • FilterLogs 模式怎么办：像当前代码这样用 FilterLogs 批量扫描，无法收到 Removed 通知，必须自己通过区块 hash 比对检测回滚（见 3.4 节）。

3.3.4 Removed vs 区块 Hash 比对：两种回滚检测方式对比

维度 Removed 字段（订阅模式） 区块 Hash 比对（拉模式）
触发方式 节点主动推送 扫描器主动检测
实时性 实时（毫秒级） 延迟（下一次扫描时才发现）
粒度 单条日志级别 区块级别
可靠性 依赖订阅连接不断开 不依赖长连接，更可靠
适用场景 实时性要求高、有 WebSocket 连接 批量扫描、对实时性要求不高
实现复杂度 低（直接读字段） 中（需回溯找分叉点）
最佳实践：两者结合
生产环境建议订阅模式 + 确认数队列 + 区块 hash 比对三重保障：
1. Removed 用于实时感知浅回滚，快速修正内存状态
2. 确认数队列过滤大部分浅分叉，减少 DB 写入
3. 区块 hash 比对做兜底，防止订阅断开或深回滚导致数据不一致

3.4 回滚检测与重放（第三道防线）

即使有确认数和 Removed 通知，极端情况下仍可能发生深回滚或订阅断开丢失回滚事件。需主动检测链重组并回滚 DB 数据。

检测方式

  1. 区块 Hash 比对：每次扫描新区块时，校验前一个区块的 hash 是否与 DB 中记录的一致
  2. 订阅 newHeads：通过 WebSocket 监听区块头，实时比对

回滚检测核心代码

func (s *Scanner) detectReorg(currentBlock *types.Header) (uint64, error) {
    // 1. 从 DB 读取上一个已处理区块的 hash
    var storedHash string
    err := s.DB.QueryRow(
        "SELECT block_hash FROM block_tracker WHERE block_number = $1",
        currentBlock.Number.Uint64()-1,
    ).Scan(&storedHash)
    if err != nil {
        return 0, err
    }

    // 2. 比对 parent hash
    if storedHash == currentBlock.ParentHash.Hex() {
        return 0, nil // 无回滚
    }

    // 3. 发生回滚，回溯找共同祖先
    forkBlock := currentBlock.Number.Uint64() - 1
    chainHash := currentBlock.ParentHash

    for forkBlock > 0 {
        var dbHash string
        err := s.DB.QueryRow(
            "SELECT block_hash FROM block_tracker WHERE block_number = $1",
            forkBlock,
        ).Scan(&dbHash)
        if err != nil {
            return 0, err
        }
        if dbHash == chainHash.Hex() {
            break // 找到分叉点
        }
        // 继续往前找
        block, err := s.Client.BlockByNumber(context.Background(), big.NewInt(int64(forkBlock)))
        if err != nil {
            return 0, err
        }
        chainHash = block.ParentHash()
        forkBlock--
    }

    log.Printf("⚠️  Reorg detected! Fork at block %d", forkBlock)
    return forkBlock, nil
}

func (s *Scanner) rollbackTo(forkBlock uint64) error {
    // 在一个事务中回滚所有表
    tx, err := s.DB.Begin()
    if err != nil {
        return err
    }
    defer tx.Rollback()

    tables := []string{"swaps", "mints", "burns", "positions", "pool_states"}
    for _, table := range tables {
        _, err := tx.Exec(
            fmt.Sprintf("DELETE FROM %s WHERE block_number > $1", table),
            forkBlock,
        )
        if err != nil {
            return err
        }
    }

    // 更新扫描进度
    _, err = tx.Exec(
        "UPDATE block_tracker SET last_scanned_block = $1 WHERE id = 1",
        forkBlock,
    )
    if err != nil {
        return err
    }

    return tx.Commit()
}

3.5 内存缓存的实时数据（可选增强）

如果业务需要实时展示（如前端页面），可以维护一个内存/Redis 缓存层：

  • 实时写入缓存：事件一扫描到就写入缓存，供前端实时查询
  • 延迟写入 DB：确认数满足后写入持久化 DB
  • 回滚时清缓存：检测到回滚，清空缓存对应区块的数据，重新填充

四、事件溯源方案（进阶）

如果系统状态计算复杂（如 Uniswap 头寸、池子状态），推荐采用事件溯源模式：

图4：事件溯源架构
  • 事件表：只追加，存原始链上事件（带 block_number、tx_hash、log_index）
  • 状态表：由事件投影计算而来，可以随时丢弃重建
  • 回滚：删除分叉点后的事件 → 重新投影状态即可
-- 事件表（只追加，永不修改）
CREATE TABLE events (
    id            BIGSERIAL PRIMARY KEY,
    block_number  BIGINT NOT NULL,
    block_hash    VARCHAR(66) NOT NULL,
    tx_hash       VARCHAR(66) NOT NULL,
    log_index     INTEGER NOT NULL,
    event_type    VARCHAR(32) NOT NULL,  -- Swap / Mint / Burn / ...
    address       VARCHAR(42) NOT NULL,
    data          JSONB NOT NULL,        -- 原始事件数据
    created_at    TIMESTAMPTZ DEFAULT NOW(),
    UNIQUE (tx_hash, log_index)
);

-- 回滚：删除分叉点后的事件，状态表可重建
DELETE FROM events WHERE block_number > $1;
-- 然后重新投影状态
SELECT project_state_from_events($1);

五、针对当前代码的改造建议

5.1 最小改动方案（确认数 + 回滚检测）

改造优先级（从易到难）：
  1. 所有表加 block_number + block_hash 字段
  2. 新增 block_tracker 表记录每个已处理区块的 hash
  3. 扫描前校验前一区块 hash 是否一致，不一致则触发回滚（DELETE + 重扫）
  4. 引入确认数机制，延迟写入 DB，减少回滚触发频率
  5. （可选）改用 SubscribeFilterLogs 订阅模式，利用 Removed 字段实时感知回滚

5.2 改造后的 scanRange 伪代码

func (s *Scanner) scanRange(start, end uint64) error {
    // ===== 新增：回滚检测 =====
    if start > 0 {
        forkBlock, err := s.detectReorgAt(start)
        if err != nil {
            return err
        }
        if forkBlock > 0 {
            log.Printf("Reorg detected at block %d, rolling back...", forkBlock)
            if err := s.rollbackTo(forkBlock); err != nil {
                return err
            }
            start = forkBlock + 1 // 从分叉点后重新扫描
        }
    }

    // ===== 原有逻辑：扫描事件 =====
    infraLogs, poolLogs, err := s.scanEvents(start, end)
    if err != nil {
        return err
    }

    // ===== 合并排序（原有逻辑不变）=====
    logs := mergeAndSort(infraLogs, poolLogs)

    // ===== 新增：写入确认队列而非直接写 DB =====
    for _, vLog := range logs {
        s.pendingQueue = append(s.pendingQueue, PendingEvent{
            BlockNumber: vLog.BlockNumber,
            Log:         vLog,
        })
    }

    // ===== 新增：将已确认的事件写入 DB =====
    cutoff := end - s.Config.Confirmations
    s.flushConfirmed(cutoff)

    // ===== 新增：记录区块 hash 用于下次校验 =====
    s.trackBlockHashes(start, end)

    return nil
}

七、总结

推荐落地路径：
  1. 第一步：所有表加 block_number + block_hash，实现区块 hash 比对 + DELETE 回滚（1~2 天）
  2. 第二步：引入确认数延迟写入队列，过滤 99% 浅分叉，减少 DB 回滚频率（半天~1 天）
  3. 第三步：（可选）改用 SubscribeFilterLogs 订阅模式，利用 Removed 字段实时感知回滚，快速修正内存状态（1~2 天）
  4. 第四步：如状态计算复杂，重构为事件溯源模式，状态可随时从原始事件重投影（视复杂度 1~2 周）

核心原则：永远不要假设链上数据是立即最终的，所有写入都要可追溯、可回滚。三道防线层层兜底：确认数过滤 → Removed 实时感知 → Hash 比对兜底重放。
