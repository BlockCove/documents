1. 核心结论 (TL;DR)

MasterChef 是 SUSHI 代币的按区块铸造 + 按 LP 份额分配的流动性挖矿合约。它不逐个用户记账奖励，而是维护一个池子级的累积变量 accSushiPerShare（每份额累计 SUSHI，放大 1e12 倍），用户每次操作时用「当前累积值 × 质押量 − 已记账债务 rewardDebt」一次性结算应得奖励。

这种设计的本质是 O(1) 结算：无论池子里有多少用户，每次存取只更新当前用户一条记录，无需遍历所有人。

2. 系统架构与角色

MasterChef 处于整个挖矿体系的中心，向上接收用户质押的 LP Token，向下铸造 SUSHI 并分配给用户和开发者地址。

graph LR U[用户 User] -- 1. 质押 LP Token --> MC[MasterChef] MC -- 2. 划转 LP --> LP[(LP Token 合约)] MC -- 3. mint SUSHI --> ST[SushiToken] ST -- 4. 奖励 SUSHI --> U ST -- 5. 10% dev 分成 --> DEV[Dev Address] OW[Owner / Governance] -- add / set / migrate --> MC MG[MigratorChef] -- 迁移 LP --> MC

核心角色

  • 用户：存入 LP Token，领取 SUSHI 奖励
  • MasterChef：托管 LP、铸造并分配 SUSHI
  • SushiToken：可 mint 的 ERC20，由 MasterChef 调用 mint()
  • Dev Address：每区块奖励的 10% 直接 mint 给开发者

管理角色

  • Owner：增删池、调整 allocPoint、设置 migrator
  • MigratorChef：将 Uniswap V2 LP 迁移为 SushiSwap LP（需授权）
  • Dev：可自行更换 devaddr

4. 核心算法：累积份额与债务

整个算法围绕两个变量展开：池子级的 accSushiPerShare 和用户级的 rewardDebt。合约注释中给出了核心公式：

pending reward = (user.amount × pool.accSushiPerShare) / 1e12 − user.rewardDebt

4.1 为什么需要 accSushiPerShare？

如果逐个用户记录「已领取奖励」，每次有新奖励产生时都要遍历所有用户更新，Gas 不可接受。MasterChef 的做法是：

  • 池子只维护一个全局累积值 accSushiPerShare，表示「每 1 份 LP 从挖矿开始到现在累计应得多少 SUSHI」。
  • 用户不存「已领多少」，而是存一个快照债务 rewardDebt，表示「上次操作时，按当时的累积值我已经结算到哪里了」。
  • 当前应得 = 按当前累积值算出的总额 − 上次已结算的债务。

4.2 为什么放大 1e12？

Solidity 不支持小数。sushiReward / lpSupply 通常小于 1（每份额奖励），直接整除会丢失精度。因此先乘以 1e12 再除，把累积值存为放大后的整数，使用时再除回来。这是 DeFi 中标准的 fixed-point 精度放大手法。

accSushiPerShare += sushiReward × 1e12 / lpSupply

4.3 rewardDebt 的重置时机

每次用户 deposit 或 withdraw 后，rewardDebt 被重置为当前累积值下的总额：

user.rewardDebt = user.amount × pool.accSushiPerShare / 1e12

这意味着「操作前产生的奖励已经结算给用户」，操作后新产生的奖励将从 0 开始累积，直到下一次操作。

5. 奖励累积：updatePool 与 Bonus 机制

updatePool(pid) 是所有写操作的入口前置步骤，负责把池子的累积值更新到当前区块。

5.1 getMultiplier — Bonus 倍数

早期挖矿有 10 倍奖励，getMultiplier(from, to) 计算两个区块之间的「有效区块数」：

区间情况返回值
to <= bonusEndBlock（全在 bonus 期内）(to - from) × 10
from >= bonusEndBlock（全在 bonus 期后）to - from
跨 bonusEndBlock(bonusEndBlock - from) × 10 + (to - bonusEndBlock)
graph TD A[getMultiplier from, to] --> B{to <= bonusEndBlock?} B -- 是 --> C[返回 to-from × 10] B -- 否 --> D{from >= bonusEndBlock?} D -- 是 --> E[返回 to - from] D -- 否 --> F[分段计算: bonus段×10 + 普通段] F --> G[返回 bonusEndBlock-from×10 + to-bonusEndBlock]

5.2 updatePool 完整流程

graph TD S[updatePool pid] --> C1{block.number <= lastRewardBlock?} C1 -- 是 --> R1[直接 return 无需更新] C1 -- 否 --> C2{lpSupply == 0?} C2 -- 是 --> R2[lastRewardBlock = block.number, return] C2 -- 否 --> M[multiplier = getMultiplier lastRewardBlock, block.number] M --> RW[sushiReward = multiplier × sushiPerBlock × allocPoint / totalAllocPoint] RW --> MD[mint devaddr, sushiReward / 10] MD --> MC[mint MasterChef, sushiReward] MC --> ACC[accSushiPerShare += sushiReward × 1e12 / lpSupply] ACC --> LB[lastRewardBlock = block.number]
注意 Dev 分成：每区块实际铸造量是 sushiReward（给池子）+ sushiReward / 10（给 dev）= 1.1 × sushiReward。也就是说 SUSHI 的实际通胀率比 sushiPerBlock 名义值高 10%。

5.3 massUpdatePools

遍历所有池调用 updatePool。在 add / set 时可选调用（_withUpdate 参数），用于在调整权重前先把所有池结算干净。Gas 消耗随池数线性增长，池多时需谨慎。

6. 用户操作：deposit / withdraw / pending

6.1 deposit — 质押 LP 并领取累计奖励

graph TD D[deposit pid, amount] --> UP[updatePool pid 更新累积值] UP --> C{user.amount > 0?} C -- 是 --> P[pending = amount × accSushiPerShare / 1e12 - rewardDebt] P --> T[safeSushiTransfer msg.sender, pending 发放奖励] C -- 否 --> TF[safeTransferFrom 用户 LP 到合约] T --> TF TF --> UA[user.amount += amount] UA --> UR[user.rewardDebt = user.amount × accSushiPerShare / 1e12 重置债务] UR --> E[emit Deposit]
关键点：存款时会先把之前累积的奖励全部发放，再更新质押量和债务。这意味着每次 deposit 都是一次「结算 + 追加质押」的组合操作。

6.2 withdraw — 取出 LP 并领取奖励

与 deposit 对称，但多了一个余额校验 require(user.amount >= _amount)。流程：

  1. updatePool(_pid) 更新累积值
  2. 计算 pending 并 safeSushiTransfer 给用户
  3. user.amount -= _amount
  4. 重置 rewardDebt
  5. 把 LP Token 转回用户

6.3 pendingSushi — 前端查询视图

external view 函数，不修改状态，供前端显示「待领取奖励」。它在内存中模拟一次 updatePool 的计算（不写回），再套用 pending 公式：

function pendingSushi(uint256 _pid, address _user) external view returns (uint256) {
    PoolInfo storage pool = poolInfo[_pid];
    UserInfo storage user = userInfo[_pid][_user];
    uint256 accSushiPerShare = pool.accSushiPerShare;
    uint256 lpSupply = pool.lpToken.balanceOf(address(this));
    if (block.number > pool.lastRewardBlock && lpSupply != 0) {
        uint256 multiplier = getMultiplier(pool.lastRewardBlock, block.number);
        uint256 sushiReward = multiplier.mul(sushiPerBlock).mul(pool.allocPoint).div(totalAllocPoint);
        accSushiPerShare = accSushiPerShare.add(sushiReward.mul(1e12).div(lpSupply));
    }
    return user.amount.mul(accSushiPerShare).div(1e12).sub(user.rewardDebt);
}

7. 池管理与迁移

7.1 add — 新增挖矿池

function add(uint256 _allocPoint, IERC20 _lpToken, bool _withUpdate) public onlyOwner
  • 可选先 massUpdatePools() 结算所有池
  • totalAllocPoint += _allocPoint
  • 新池的 lastRewardBlock 取 max(block.number, startBlock)
  • accSushiPerShare 从 0 开始
合约警告：注释明确写道「DO NOT add the same LP token more than once. Rewards will be messed up if you do.」同一个 LP 重复添加会导致奖励计算混乱，因为两个池共享同一个 LP 合约的 balanceOf，但 accSushiPerShare 各自独立。

7.2 set — 调整池权重

function set(uint256 _pid, uint256 _allocPoint, bool _withUpdate) public onlyOwner

先从 totalAllocPoint 减去旧 allocPoint，再加新值，最后更新池的 allocPoint。

7.3 migrate — LP 迁移

将池中的 Uniswap V2 LP 迁移为 SushiSwap LP。任何人可调用，但必须先由 owner 设置 migrator：

  1. 读取合约持有该 LP 的余额 bal
  2. 授权 migrator 花费全部 bal
  3. 调用 migrator.migrate(lpToken) 返回新 LP
  4. 校验新 LP 余额 == bal（防止 migrator 偷币）
  5. 替换 pool.lpToken 为新 LP
权限风险：migrator 被授权花费合约持有的全部该类 LP，且注释承认「It has a lot of power」。虽然有余额校验，但恶意 migrator 仍可能在迁移过程中造成损失，需治理谨慎设置。

8. 安全兜底机制

emergencyWithdraw

紧急提款，放弃所有未领取奖励，只取回质押的 LP。

  • 不调用 updatePool，不计算 pending
  • 直接 safeTransfer 用户全部 amount
  • 清零 user.amount 和 user.rewardDebt
  • 用于合约奖励逻辑异常时的资金逃生通道

safeSushiTransfer

内部转账函数，防止舍入误差导致余额不足而 revert。

  • 读取合约 SUSHI 余额 sushiBal
  • 若 _amount > sushiBal，只转 sushiBal
  • 否则转 _amount
  • 本质是「有多少转多少」的容错降级
dev 地址更换：dev(address _devaddr) 只能由当前 devaddr 调用，将开发者地址迁移到新地址。这是一个独立于 owner 的权限，确保 dev 分成可自主转移。

10. 设计要点与风险

类别要点说明
精度 1e12 fixed-point accSushiPerShare 放大 1e12 避免整除丢精度；lpSupply 极小时仍可能有微小舍入
通胀 Dev 10% 分成 实际每区块铸造 1.1× sushiReward，名义 sushiPerBlock 不含 dev 部分
权重 totalAllocPoint 同步 add/set 必须同步更新 totalAllocPoint，否则分配比例错乱；合约已正确处理
重复添加 同一 LP 不可重复 add 两池共享 balanceOf 但 accSushiPerShare 独立，会导致奖励计算错误（合约仅注释警告，无代码校验）
权限 Owner 权力极大 可增池、调权重、设 migrator；注释承诺后续转移给治理合约
权限 Migrator 高权限 可花费合约全部某类 LP，虽有余额校验仍需治理审慎
Gas massUpdatePools 线性增长 池数多时调用成本高，add/set 的 _withUpdate 需权衡
安全 emergencyWithdraw 逃生 奖励逻辑异常时用户可放弃奖励取回本金，保护资金安全
容错 safeSushiTransfer 余额不足时降级转账而非 revert，防止舍入误差卡死用户操作
重入 无 ReentrancyGuard deposit/withdraw 中先外部转账（safeTransferFrom / safeSushiTransfer）后改状态，理论上若 LP 或 SUSHI 代币有回调可被重入；但标准 ERC20 无回调，实际风险低
算法地位：MasterChef 的「累积份额 + 债务」模式后来被 PancakeSwap、Biswap、SpookySwap 等几乎所有 DEX 挖矿合约直接复用或微调，成为 DeFi 流动性挖矿的事实标准范式。后续的 MasterChef V2 主要优化了多奖励代币和委托投票，核心结算逻辑未变。
