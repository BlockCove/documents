1解决什么问题

Permit2 解决的核心问题是：把 ERC20 授权能力从“每个 Token 各自实现”提升为一个统一的授权层，从而降低重复 approve 的 UX/Gas 摩擦，同时提供更细粒度的签名授权。

传统 ERC20 approve 的痛点

  • 重复授权：用户第一次与某个 Token + DApp 组合交互时，通常需要先执行 approve()，换新的 spender 往往还要再次授权。
  • 链上交易成本：approve 是链上状态变更，用户需要为该交易支付 Gas。
  • 无限授权风险：DApp 常要求 approve(spender, type(uint256).max)，若 spender 合约存在严重漏洞，长期授权会扩大潜在损失面。
  • 授权残留：approve 不会自动过期，用完后如果用户不主动 revoke，授权仍然存在。
  • 缺少统一层：ERC20 是否原生支持签名授权取决于 Token 自己的实现。

EIP-2612 的边界

  • 需要 Token 原生支持：只有实现了 permit() 的 Token 才能直接使用 EIP-2612。
  • 授权仍然绑定 Token 合约：permit 的验证逻辑位于 Token 本身，生态层面没有统一的中间授权合约。
  • 单项授权模型：标准 permit 主要解决 owner → spender → value 的签名授权；复杂的批量/一次性消费/业务意图绑定通常要额外设计。
  • nonce 通常是单调递增：典型实现使用递增 nonce，不适合所有高并发授权场景。
需要特别澄清：Permit2 不是“天然无 Gas 的 Meta-Transaction 系统” 用户签名本身不需要 Gas，但真正把签名提交到链上的交易仍然需要 Gas。只有搭配 relayer / paymaster / bundler 等机制，才能进一步实现“用户不支付原生 Token Gas”的体验。

2为什么会有这个合约

2.1 诞生背景

Permit2 由 Uniswap Labs 推出，核心思路受到 permit-everywhere 等早期方案启发：不要要求每一种 ERC20 都重新实现一套签名授权接口，而是在 Token 与 DApp 之间增加一个统一授权层。

因此 Permit2 的设计目标可以概括为：

  • 让没有 EIP-2612 的存量 ERC20，也可以进入统一的签名授权流程；
  • 将授权的 Token / amount / spender / deadline 等条件结构化；
  • 支持一次性签名转账、可重复消费的额度授权以及批量操作；
  • 把公共授权基础设施做成固定地址、无 Owner、不可升级的基础组件，降低生态集成成本。

2.2 核心设计理念

🔑

一次 Token approve，多次使用

用户只需先让 Token 授权 Permit2 调用 transferFrom。之后，集成 Permit2 的协议可以通过用户签名来驱动转账，而不必让每个 DApp 都单独成为 Token spender。

🛡️

细粒度签名授权

签名可以限制 Token、最大金额、deadline、nonce，并通过 Witness 进一步绑定业务数据。

⚡

把授权与业务交易组合

SignatureTransfer 可以在同一笔业务交易中完成签名验证与 Token 转移；但提交该交易本身依旧需要由某个地址承担 Gas。

🌐

统一中间层

Permit2 不要求 Token 修改代码，适用于大量具备标准 transferFrom 语义的 ERC20 / ERC20-compatible Token。

关键边界 Permit2 在常规路径下不托管用户 Token。它调用 Token 的 transferFrom(owner, to, amount)，通常直接把 Token 从 owner 转给指定 recipient。所谓“Permit2 是中间层”，主要是指授权验证与转账调用被集中到了 Permit2，而不是指 Token 先进入 Permit2 再转出去。

4核心数据结构

4.1 PackedAllowance — 紧凑存储

struct PermitDetails {
    address token;
    uint160 amount;
    uint48  expiration;
    uint48  nonce;
}

// 逻辑上对应一个 owner + token + spender 的额度记录
// amount / expiration / nonce 的总位宽：160 + 48 + 48 = 256

AllowanceTransfer 将这三个数值压缩到一个 256-bit storage slot，使一条额度记录可以紧凑存放。它对应的访问维度是：

allowance[owner][token][spender]

其中 expiration 过期后，该额度不能继续用于转账；nonce 用于失效/更新签名授权。

4.2 PermitSingle — 单条额度授权

struct PermitSingle {
    PermitDetails details;
    address spender;
    uint256 sigDeadline;
}

这里有两个容易混淆的时间概念：

  • expiration：链上额度本身还能使用多久；
  • sigDeadline：这份 permit 签名最晚什么时候可以被提交验证。

4.3 PermitTransferFrom — 一次性签名转账

struct TokenPermissions {
    address token;
    uint256 amount;     // 最大允许消费金额
}

struct PermitTransferFrom {
    TokenPermissions permitted;
    uint256 nonce;
    uint256 deadline;
}

struct SignatureTransferDetails {
    address to;
    uint256 requestedAmount;
}
这是本报告原稿中最重要的一处修正 PermitTransferFrom Solidity struct 本身没有 spender 字段。在当前 Permit2 实现里，spender 会通过执行 permitTransferFrom 时的 msg.sender 被写入 EIP-712 哈希，因此“谁来消费这份签名”仍然会被签名约束，但不能把它误写成 Solidity struct 的字段。官方 PermitHash 中的 typehash 明确包含 address spender，并使用 msg.sender 参与哈希计算。

4.4 Nonce Bitmap — 非单调 nonce

mapping(address => mapping(uint256 => uint256)) public nonceBitmap;

一个 nonce 是 256-bit 整数，其中：

wordPos = uint248(nonce >> 8); // 前 248 bit：定位 bitmap word
bitPos  = uint8(nonce);        // 最后 8 bit：定位 word 中的 bit

因此，一个 word 对应 256 个可独立消费的 nonce。某个 bit 被置为已使用后，该 nonce 就不能再次用于签名消费。

为什么不是简单的 ++nonce？ 递增 nonce 要求签名按序消费；Permit2 的 unordered nonce 允许不同签名并发生成、乱序上链，更适合聚合器、路由器和高并发交易场景。

5完整交互流程

5.1 前置：Token → Permit2 的一次性 approve

IERC20(token).approve(PERMIT2_ADDRESS, type(uint256).max);

这一步是传统 ERC20 allowance 模型中的链上授权。它不会因为某一次 Permit2 签名消费而自动减少，因此可以被多个 Permit2 场景复用。

“一次 approve”并不等于“风险为零” 如果 Permit2 存在致命漏洞，Token 对 Permit2 的长期授权可能带来严重影响。因此正确的表述不是“完全安全”，而是：把原本分散在大量 spender 合约上的无限授权，集中到一个固定的公共基础设施上，并通过签名层继续限制具体消费条件。

5.2 模式 A：SignatureTransfer

这是 Permit2 最容易理解的模式：用户签一张“coupon”，允许某个明确的 spender 在 deadline 前消费指定 Token 的不超过某个上限的金额；该 nonce 消费后即失效。

sequenceDiagram participant U as 用户钱包 participant D as DApp 前端 participant C as DApp/Router participant P as Permit2 participant T as ERC20 Note over U,T: 前置：Token 已 approve(Permit2, max) U->>D: 发起操作 D->>U: 请求 EIP-712 签名 U-->>D: 返回签名 D->>C: 提交 permit + signature + 业务参数 C->>P: permitTransferFrom(...) P->>P: 检查 deadline / nonce / signature / requestedAmount P->>T: transferFrom(owner, to, requestedAmount) T-->>P: Token 转移成功 P-->>C: 返回 C->>C: 执行 Swap / 结算等业务
一个容易被忽略的安全点 SignatureTransfer 默认并不会把 SignatureTransferDetails.to 放进基础签名。也就是说，集成协议如果让攻击者自由指定 recipient，就可能出现“签名本身是真的，但钱被送到了错误地址”的问题。要么让接收方固定为路由器/指定地址，要么把 recipient 等关键业务约束放入 Witness 并在合约中严格校验。

5.3 模式 B：AllowanceTransfer

sequenceDiagram participant U as 用户 participant C as DApp/Router participant P as Permit2 participant T as ERC20 Note over U,T: 阶段一：签名设置额度 U->>C: EIP-712 PermitSingle C->>P: permit(owner, permitSingle, signature) P->>P: 检查 sigDeadline / signature / nonce P->>P: 写入 allowance(owner, token, spender) Note over U,T: 阶段二：多次消费 C->>P: transferFrom(owner, to, amount, token) P->>P: 检查 msg.sender / remaining amount / expiration P->>T: transferFrom(owner, to, amount) T-->>P: 转移完成

这个模式与普通 allowance 更接近，只是授权状态统一由 Permit2 保存。它适合需要多次消费同一授权额度的协议。

5.4 批量操作

  • permit(PermitBatch)：一次签名设置多个 Token 的额度，前提是这些额度属于同一个 spender。
  • permitTransferFrom(PermitBatchTransferFrom)：一个签名可以覆盖多个 Token，再按数组逐项指定 recipient 和 requestedAmount。
  • invalidateUnorderedNonces(wordPos, mask)：一次作废 bitmap 中的一组 nonce。

6技术原理

6.1 EIP-712 结构化签名

Permit2 使用 EIP-712 对 typed data 做签名。对于 SignatureTransfer，核心签名类型逻辑可以概括为：

PermitTransferFrom(
    TokenPermissions permitted,
    address spender,
    uint256 nonce,
    uint256 deadline
)
TokenPermissions(address token,uint256 amount)

注意：这里的 spender 是签名哈希的一部分，但不是 PermitTransferFrom Solidity struct 的字段；Permit2 在 hash 时取当前执行上下文里的 msg.sender。

const domain = {
  name: "Permit2",
  chainId,
  verifyingContract: PERMIT2_ADDRESS,
};

const types = {
  PermitTransferFrom: [
    { name: "permitted", type: "TokenPermissions" },
    { name: "spender", type: "address" },
    { name: "nonce", type: "uint256" },
    { name: "deadline", type: "uint256" },
  ],
  TokenPermissions: [
    { name: "token", type: "address" },
    { name: "amount", type: "uint256" },
  ],
};

6.2 EIP-1271：合约钱包签名

签名主体验证方式说明
EOAECDSA / ecrecover从签名恢复 signer，与 owner 比较。
合约钱包EIP-1271由合约钱包通过 isValidSignature(hash, signature) 判断签名是否合法。

因此 Permit2 的 owner 不应简单理解成“必须是 EOA”。支持 EIP-1271 是合约账户集成的重要组成部分。

6.3 Witness：把业务意图带进签名

permitWitnessTransferFrom(
    permit,
    transferDetails,
    owner,
    witness,
    witnessTypeString,
    signature
)

Witness 允许集成协议把额外结构化数据加入 EIP-712 digest，例如：

  • 最终 recipient；
  • Swap 的 minOut / slippage 参数；
  • 交易路径、订单 ID、手续费参数；
  • 任何必须与用户签名形成强绑定的业务条件。
Witness 不是“自动防滥用”开关 必须由集成协议选择正确的 witness schema，并在合约中使用这些字段约束业务逻辑。若 recipient 等关键条件没有放进签名，攻击者仍可能利用一个合法签名修改未被签名约束的参数。

6.4 EIP-712 Domain 与确定性地址

Permit2 的 EIP-712 domain 会绑定 name、chainId、verifyingContract，从而把签名限制在特定链和特定合约上下文中，降低跨链/跨合约重放风险。

Canonical Permit2 地址为：

0x000000000022D473030F116dDEE9F6B43aC78BA3

在官方支持并完成部署的链上，该地址被设计为统一的 Permit2 地址。应注意：“同地址”不等于“所有 EVM 链自动存在”，集成时仍应确认目标网络已经部署官方 Permit2。

7优化了什么

7.1 正确理解 Gas 优化

场景传统模型Permit2结论
首次 Token + Permit2需要 Token → Permit2 的 approve 交易同样需要一次性成本没有凭空消失
之后切换到另一个 Permit2 集成协议通常还要给新的 spender approve可以改用新的签名授权减少重复 approve
链下签名传统 approve 不涉及签名签名本身不消耗链上 Gas用户体验更好
真正提交链上业务交易需要 Gas仍然需要 Gas不能称为“0 Gas 交易”
批量授权/转账多次 approve 或多次调用可批量处理通常可减少交易次数，但实际 Gas 取决于数据量和存储变化

因此，不建议把 Permit2 描述成“节省固定 80% / 100% Gas”。更准确的表述是：Permit2 主要减少重复授权交易和交互次数；签名验证本身也会产生链上计算成本，最终 Gas 需要按具体调用路径、Token 实现和链来测量。

8安全考量与风险

8.1 Permit2 本身

  • 固定基础设施：Permit2 的目标是作为公共授权层，而不是允许业务方自行升级的可变代理。
  • 不托管资产：正常转账路径直接让 Token 从 owner 转给目标地址。
  • 经过多方安全审查和公开 Bug Bounty：但这只能降低风险，不能证明“绝对安全”。

8.2 风险一：用户签了恶意 Permit

签名没有 Gas ≠ 签名没有资产风险。一份合法的 Permit2 签名可以授权 spender 在 deadline 前消费指定 Token / amount。用户如果在钓鱼网站签了不符合预期的 typed data，攻击者可能利用该签名转走资产。

至少应检查：

  • spender：实际会调用 Permit2 的合约地址是否可信；
  • token：是否为预期 Token；
  • amount：是否超过本次业务所需；
  • deadline / expiration：是否过长；
  • nonce：是否为本次签名独立使用的 nonce。

8.3 风险二：集成合约没有绑定业务参与者

这是开发者更容易忽略的一层：即使 Permit2 验证签名成功，集成 DApp 自己也必须正确约束调用者、recipient、订单参数等业务字段。

经典错误 Router 收到 owner 的合法 Permit2 签名后，没有验证是谁提交交易，也允许调用者自由填写 recipient。此时签名虽然有效，但 Token 可能被送到攻击者地址。解决方法包括绑定 msg.sender == owner、固定 transfer recipient，或者把 recipient / 订单条件纳入 Witness。

8.4 风险三：Permit2 的无限 Token approval

用户给 Token → Permit2 的无限授权本身仍然是一个真实的信任边界。Permit2 的设计是把大量 DApp spender 收敛到一个公共 spender，但这并不意味着该风险被数学上消除。

8.5 其他注意事项

风险点说明工程建议
SignatureTransfer recipient 未签名基础 permit 不自动锁定 to固定 recipient 或使用 Witness 绑定关键业务数据
过长 deadline签名在有效期内可能被消费根据业务采用尽可能短的期限
nonce 复用同一 nonce 的签名消费存在竞争，成功使用后再次使用会失败每份签名使用独立 nonce，并避免应用层复用
Token 非标准行为fee-on-transfer、rebasing、奇异 ERC20 行为可能影响金额假设按照具体 Token 语义测试，不要假设所有 ERC20 都完全等价

9集成示例

9.1 Solidity：SignatureTransfer 安全集成骨架

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.17;

import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";
import {ISignatureTransfer} from "@uniswap/permit2/src/interfaces/ISignatureTransfer.sol";

contract SwapRouter {
    ISignatureTransfer public immutable permit2;

    constructor(address permit2Address) {
        permit2 = ISignatureTransfer(permit2Address);
    }

    function swapWithPermit(
        ISignatureTransfer.PermitTransferFrom calldata permit,
        ISignatureTransfer.SignatureTransferDetails calldata transferDetails,
        address owner,
        bytes calldata signature,
        address recipient,
        uint256 minOut
    ) external {
        // 教学示例：先要求交易提交者就是资产 owner。
        // 真正的 relayer 场景可以不做这个约束，但必须用其他机制绑定业务意图。
        require(msg.sender == owner, "caller != owner");

        // Permit2 的 SignatureTransfer 不应让业务调用者随意把输入 Token 送到任意地址。
        require(transferDetails.to == address(this), "invalid transfer recipient");

        // permit.permitted.spender 在签名哈希中由 Permit2 绑定为当前 msg.sender。
        // 注意：这里的 msg.sender 是本 Router 合约，而不是最终用户。
        permit2.permitTransferFrom(permit, transferDetails, owner, signature);

        // 输入 Token 此时已经进入 Router。
        uint256 out = _executeSwap(permit.permitted.token, transferDetails.requestedAmount, minOut);
        IERC20(_outputToken()).transfer(recipient, out);
    }

    function _executeSwap(address tokenIn, uint256 amountIn, uint256 minOut)
        internal
        returns (uint256 amountOut)
    {
        // ...实际 Swap 逻辑...
        tokenIn; amountIn; minOut;
        return 0;
    }

    function _outputToken() internal view returns (address) {
        // ...实际项目中应由路由/池子逻辑确定...
        return address(0);
    }
}
集成重点这个示例特意加入了 msg.sender == owner 与 transferDetails.to == address(this) 两层约束，用来展示安全边界。真实生产 Router 如果需要 relayer / meta-tx，应把 recipient、订单参数、调用者授权等条件放入更完整的业务校验或 Witness，而不是简单删除检查。

  ],
  TokenPermissions: [
    { name: "token", type: "address" },
    { name: "amount", type: "uint256" },
  ],
};

// 用安全的 256-bit 随机数生成 unordered nonce，
// 不要使用 Math.random() + 2**160，因为 JS Number 无法精确表示这么大的整数。
const nonce = BigInt(ethers.hexlify(ethers.randomBytes(32)));

const message = {
  permitted: {
    token: USDC_ADDRESS,
    amount: ethers.parseUnits("1000", 6),
  },
  spender: SWAP_ROUTER_ADDRESS,
  nonce,
  deadline: BigInt(Math.floor(Date.now() / 1000) + 30 * 60),
};

const signature = await signer.signTypedData(domain, types, message);

9.3 一个非常重要的前端细节

SignatureTransfer 的 EIP-712 typed data 中必须包含 spender，但 Solidity 的 PermitTransferFrom struct 不含该字段。这是 Permit2 通过 PermitHash.hash() 将 msg.sender 注入签名摘要的结果。不要把 Solidity ABI struct 与 EIP-712 typed-data schema 机械地视为完全相同。

9.4 生态集成

Permit2 已被 Uniswap 生态及大量 DeFi / 聚合器项目采用。具体项目是否在某条链、某个版本、某个 Router 路径使用 Permit2，应以该项目当前官方文档与合约为准，不建议写死成“所有版本都默认使用”。

10总结

维度修订后的结论
核心问题减少重复 Token approve，并把签名授权能力统一到一个公共层，同时改善授权粒度。
核心架构Permit2 = SignatureTransfer + AllowanceTransfer。
SignatureTransfer一次性签名消费，使用 unordered nonce；签名哈希包含 spender，但 Solidity permit struct 本身不含 spender 字段。
AllowanceTransfer先通过 permit 设置额度，再由 spender 在 expiration 前多次消费。
安全不要只看 Permit2 是否验签成功，还必须约束 owner / caller / recipient / order / witness 等业务关系。
Gas签名本身不需要 Gas，但提交链上交易仍然需要 Gas；Permit2 主要减少重复 approve 和交易次数，不应承诺固定百分比 Gas 节省。
地址0x000000000022D473030F116dDEE9F6B43aC78BA3 是 canonical Permit2 地址；具体网络仍应确认已部署官方版本。
一句话概括 Permit2 不是简单的“把 approve 改成签名”，而是把 Token 授权拆成两层：Token → Permit2 的长期授权 + 用户对具体消费条件的短期签名授权。其中 SignatureTransfer 解决“一次签名、一次消费”，AllowanceTransfer 解决“签名设置额度、多次消费”，而 EIP-712、unordered nonce、EIP-1271 与 Witness 则分别解决可验证性、防重放、合约钱包与业务意图绑定问题。
