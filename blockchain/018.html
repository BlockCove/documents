2. 方案一：approve + 购买（经典两步法）

核心思想：买家先调用 ERC20 的 approve()，授权 NFTMarket 花费指定额度，再调用市场合约的 buyNFT()。市场内部通过 transferFrom() 扣款；如果 NFT 仍由卖家持有，则卖家还必须提前通过 approve() 或 setApprovalForAll() 授权 NFTMarket。
sequenceDiagram autonumber participant S as 卖家 participant U as 买家 (EOA) participant E20 as ERC20 Token participant M as NFTMarket participant E721 as ERC721 NFT participant C as 创作者/平台 Note over S,E721: 上架前置条件：NFTMarket 必须有权转移 NFT S->>E721: approve(NFTMarket, tokenId)
或 setApprovalForAll(NFTMarket, true) E721-->>S: Approval / ApprovalForAll Note over U,E20: 第一笔交易：ERC20 授权 U->>E20: approve(NFTMarket, price) E20-->>U: Approval 事件 (授权成功) Note over U,M: 第二笔交易：购买 U->>M: buyNFT(tokenId) M->>M: 校验 NFT 已上架、价格与状态 M->>E20: transferFrom(buyer, seller/market, price) E20-->>M: Transfer 事件 (扣款成功) M->>E721: safeTransferFrom(seller, buyer, tokenId) E721-->>M: Transfer 事件 (NFT 过户) M->>C: 按协议分配创作者版税 / 平台费 M-->>U: NFTBought 事件 (购买完成)
✅ 优点
  • 兼容性最好，所有 ERC20 都支持
  • 逻辑简单，审计风险低
  • 授权额度可精确控制
⚠️ 缺点
  • 需要两笔交易，用户体验差
  • 无限授权 (approve max) 有安全隐患
  • 两次 Gas 费，成本较高

3. 方案二：Multicall / Router —— 为什么不能用 delegatecall 把 approve + 购买合并

结论：对于普通 EOA + 标准 ERC20，不能通过“一个 Multicall 合约对 ERC20 使用 delegatecall，然后再调用 NFTMarket”的方式，把 approve() 和购买可靠地合并成一笔交易。原理上这是错误的用法。
为什么：delegatecall 会让目标合约代码在“调用者”的存储上下文中执行。ERC20 的 approve() 需要修改的是 ERC20 合约自己的 allowance 存储；如果把 ERC20 代码 delegatecall 到 Multicall，写入的却是 Multicall 的存储，而不是 ERC20 的存储，因此不能达到给 NFTMarket 授权 ERC20 的目的。同理，直接 delegatecall 一个有状态的 NFTMarket 也会把其状态读写指向错误的存储上下文。
sequenceDiagram autonumber participant U as 买家 (EOA) participant MC as Multicall / Router participant E20 as ERC20 Token participant M as NFTMarket Note over U,MC: 看似想用一笔交易完成 approve + buy U->>MC: multicall([approveData, buyData]) Note over MC,E20: 错误做法：delegatecall ERC20.approve MC->>E20: delegatecall approve(NFTMarket, price) Note right of MC: ERC20 代码在 MC 的 storage 上执行 Note right of MC: ❌ 不会修改 ERC20.allowance MC-->>U: 该方案无法产生有效的 ERC20 授权 Note over U,M: 正确的“一笔交易”路径 U->>M: buyWithPermit(...signature) M->>E20: permit(owner, NFTMarket, value, deadline, ...) E20-->>M: allowance 写入 ERC20 自身存储 M->>E20: transferFrom(buyer, ...) M->>M: 完成购买逻辑
正确的替代方案：
  • Permit / EIP-2612：用户链下签名，市场合约在同一笔交易里调用 permit + transferFrom。
  • ERC-1363：若代币支持 approveAndCall / transferAndCall，可以使用代币扩展定义的一笔交易模式。
  • 智能合约钱包 / Account Abstraction：账户本身可以在一次 UserOperation 中执行多个动作，但这已经不是“EOA 直接通过 delegatecall 完成 approve + buy”。
✅ Multicall 真正适合做什么
  • 批量读取多个合约状态
  • 批量执行已经拥有权限的多个操作
  • 批量购买多个 NFT（前提是授权已经存在）
  • 作为 Permit / Account Abstraction 之后的编排层
⚠️ 不应这样理解
  • 不能用 delegatecall 伪造“买家的 ERC20 approve”
  • 不能因为 msg.sender 保持不变，就认为所有目标合约状态都会写到目标合约自己
  • 一个普通 EOA 不能仅靠 Multicall 把两个需要分别授权的外部合约操作神奇地变成一个标准 ERC20 approve + buy 流程

4. 方案三：Merkle Tree 白名单 50% 优惠购买

核心思想：项目方将白名单地址（或“地址 + 限购额度”等业务字段）生成 Merkle Tree，仅将 Merkle Root 存储在链上。买家购买时提交自己的 Merkle Proof，合约验证通过后按白名单规则结算，例如 50% 折扣。Merkle 白名单本身不是授权机制，可与 approve / Permit 等支付方式组合；仅做地址存在性证明时，若业务要求“每地址只能使用一次”，仍需额外记录 claimed 状态或消耗额度。

🔍 Merkle Proof 验证原理
// 叶子节点的构造必须与链下建树方式完全一致 // 下面仅示意“地址白名单”的一种常见编码 leaf = keccak256(bytes.concat(keccak256(abi.encode(msg.sender)))) // 沿 proof 路径逐层哈希 hash = leaf for each sibling in proof: if hash < sibling: hash = keccak256(abi.encodePacked(hash, sibling)) else: hash = keccak256(abi.encodePacked(sibling, hash)) // 最终比对 require(hash == merkleRoot, "Invalid whitelist proof")
关键特性：链上通常只需存 1 个 Root（32 bytes），白名单规模增长不会线性增加 Root 的存储空间。买家提交的 proof 通常为 O(log n) 个兄弟节点，但实际 Gas 仍取决于 proof 长度、哈希实现和其他业务逻辑。
✅ 优点
  • 链上存储成本极低（仅 32 bytes Root）
  • 白名单可动态更新（更换 Root）
  • 验证 Gas 与白名单规模无关
  • 可叠加任意授权方式
⚠️ 注意事项
  • Merkle Proof 本身不等于“防重放”：若同一地址允许多次购买，proof 可以反复使用；若要求一次性领取，需额外记录 claimed / nonce / 已用额度
  • 白名单生成需链下工具配合
  • 折扣资格应与明确的价格、限购与领取规则绑定，避免仅凭前端传入价格
  • Root 更新权限需治理（多签/时间锁）

5. 方案四：ERC20 Permit 签名授权（EIP-2612）

核心思想：对于实现 EIP-2612 的 ERC20，买家离线签名一份 EIP-712 Permit 消息（包含 owner、spender、value、nonce、deadline 等字段）。签名不消耗链上 Gas；随后市场合约在一笔交易中调用 ERC20 的 permit() 建立 allowance，再调用 transferFrom() 完成扣款。这里节省的是“单独的 approve 交易”，但真正提交购买交易的账户仍需要承担这笔交易的 Gas，除非结合 relayer / meta-transaction / Account Abstraction 等方案。

📝 EIP-712 签名消息结构
Permit( owner: 0xBuyerAddress, // 授权者 spender: 0xNFTMarket, // 被授权者 value: 1000000000, // 授权额度（建议按实际需求限制） nonce: 5, // 必须等于 token.nonces(owner) deadline: 1714521600 // 签名有效截止时间 ) // EIP-712 Domain（示意；具体字段必须以 token 的实现为准） EIP712Domain( name: "MyToken", version: "1", chainId: 1, verifyingContract: 0xTokenAddress )
✅ 优点
  • 仅一笔交易，用户体验最佳
  • 可把授权额度精确限制在购买金额或所需额度；但 Permit 若签署过大的 value，仍然存在授权风险
  • 签名可设 deadline，过期自动失效
  • nonce 机制天然防重放
  • 通常比“approve + purchase”少一笔独立的链上授权交易
⚠️ 缺点
  • ERC20 必须实现 EIP-2612（非所有代币）
  • 前端需集成 EIP-712 签名逻辑
  • 签名过期需用户重新签名
  • 钱包 / 智能合约账户的签名能力存在差异，生产环境需确认 EIP-712 与具体 Permit 方案的兼容性

💡 推荐组合策略
  • 最佳通用 UX：若 ERC20 支持 EIP-2612，可采用 Permit + NFTMarket 购买；若同时有白名单，再叠加 Merkle Proof。
  • 最大兼容性：标准 ERC20 采用 approve + 购买；Multicall 只作为已有权限下的批量编排层，不应被当成“替代 approve”的机制。
  • 白名单设计：把“资格证明”和“支付授权”分开理解：Merkle 解决“你有没有资格”，approve / Permit 解决“市场能不能扣你的 ERC20”。
  • 生产建议：NFTMarket 至少明确区分 ERC20 授权、ERC721 授权、白名单证明和购买逻辑；前端根据 token 能力选择 approve 或 Permit，并对 Permit 的 domain / nonce / deadline 做链上状态校验。
技术边界说明：本文中的 Permit 以 EIP-2612 为准；DAI 等历史 Permit 实现存在不同接口语义，不能仅凭函数名 permit 就认为它符合 EIP-2612。Merkle Leaf 的编码方式也必须与链下建树实现完全一致。NFTMarket 若从卖家地址直接调用 ERC721 safeTransferFrom，还必须满足卖家已授权市场合约或 NFT 已托管到市场的前置条件。
