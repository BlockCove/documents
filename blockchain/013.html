1合约概述

CreateX 是由 pcaversaccio 与 Matt Solomon 共同开发的开源智能合约部署工厂，基于 Solidity 编写，开源协议为 AGPL-3.0-only。CreateX 已部署到多条 EVM 网络，并使用统一的规范地址 0xba5Ed099633D3B313e4D5F7bdc1305d3c28ba5Ed；具体网络是否已部署、以及部署代码是否与官方版本一致，应以官方 deployments 列表和链上代码哈希为准。

CreateX 的核心价值在于：将 EVM 的 CREATE、CREATE2 以及基于代理模式的 CREATE3 三种合约创建方式封装为一个无需许可（permissionless）、无需信任（trustless）的通用工厂，同时内置权限部署保护、跨链重新部署保护、地址预计算等高级特性。

2解决什么问题

问题 1：CREATE 地址不可预测

传统 CREATE opcode 的合约地址由 keccak256(rlp([deployer, nonce])) 计算，依赖部署者的 nonce。跨链部署时 nonce 很难保持一致，导致同一合约在不同链上地址不同，增加跨链协议的配置和维护成本。

问题 2：CREATE2 地址依赖 initCode

CREATE2 虽然支持确定性地址，但其地址计算包含 keccak256(initCode)。一旦构造函数参数不同（如跨链时 WETH 地址、链 ID 不同），initCode 就不同，最终地址也不同，无法实现真正的"同地址跨链"。

问题 3：缺乏统一的部署工厂

每个项目各自实现部署逻辑，代码重复、审计成本高。没有一个被广泛采用的、在所有链上同地址部署的标准工厂，导致生态碎片化。

问题 4：部署与初始化分离

AndInit 系列可在同一笔交易内完成“部署 + 初始化”。如果部署和初始化拆成两笔独立交易，中间会存在可被其他交易插入的窗口；原子化执行可以消除这个窗口。

问题 5：跨链部署的 frontrun 攻击

在公链上，任何人都可以用相同的 salt 和 initCode 抢先部署合约到目标地址，劫持合约部署。跨链场景下这个风险尤为突出。

问题 6：地址预计算不便

开发者需要自己实现地址计算逻辑，容易出错。尤其是 CREATE3 模式涉及代理合约的中间地址计算，手动计算非常繁琐。

CreateX 的解决方案

统一工厂 + 同地址部署

CreateX 通过确定性部署方式在多条 EVM 网络使用同一规范地址，所有项目可以共享同一个工厂入口，从而降低生态碎片化。

CREATE3：地址与 initCode 解耦

通过“先用 CREATE2 部署固定字节码的代理 → 代理再用 CREATE 部署最终合约”的两步模式，使最终地址计算不再包含最终合约的 initCode 哈希；但在 CreateX 中，实际地址还取决于经过 _guard 处理后的 salt。若启用跨链重新部署保护（salt 第 21 字节为 0x01），chainid 会进入 guardedSalt，因此不同链的地址反而会不同。要实现权限保护下的跨链同地址部署，应使用第 21 字节为 0x00 的模式。

部署+初始化原子化

提供 CREATE / CREATE2 / CREATE3 的 AndInit 系列函数，在单笔交易内完成合约部署和初始化调用，并支持 ETH 转账和多余 ETH 退款，消除 frontrun 窗口。

Salt 编码安全保护

在 32 字节 salt 中编码部署者地址（权限保护）和跨链重放标志，通过内部 _guard 函数重新哈希，有效防止 frontrun 和跨链重放攻击。

内置地址预计算

提供 computeCreateAddress、computeCreate2Address、computeCreate3Address 等只读函数，支持任意部署者地址的地址预计算。

支持 EIP-1167 最小代理克隆

内置 deployCreateClone / deployCreate2Clone，支持低成本部署 EIP-1167 代理克隆并在同一笔交易中初始化，适合工厂模式和批量实例化；注意 EIP-1167 clone 本身并不等于“可升级代理”，clone 的 implementation 地址通常在代理字节码中固定。

3核心原理：CREATE / CREATE2 / CREATE3

3.1 三种 Opcode 地址计算公式

CREATE（0xF0）—— 地址依赖部署者 nonce：

address = keccak256( rlpEncode([deployerAddress, deployerNonce]) )[12:]

CREATE2（0xF5，EIP-1014）—— 地址依赖 salt + initCode 哈希：

address = keccak256( 0xff || deployerAddress || salt || keccak256(initCode) )[12:]

CREATE3—— 非 EVM 原生 opcode，而是一种设计模式。地址仅依赖 salt：

proxyAddress = keccak256( 0xff || CreateX || guardedSalt || keccak256(proxyBytecode) )[12:]
finalAddress = keccak256( rlpEncode([proxyAddress, 0x01]) )[12:]

注：固定的代理字节码使 proxyAddress 不受最终 initCode 影响；代理随后通过 CREATE 创建最终合约，因此 finalAddress 只由 proxyAddress 决定。对 CreateX 而言，更准确地说，它依赖 CreateX 地址与经过 _guard 处理后的 salt，而不是裸 salt 本身。

6Salt 安全保护机制

CreateX 的核心安全创新在于对 32 字节 salt 的结构化编码。通过在 salt 中嵌入部署者地址和跨链重放标志，再经内部 _guard 函数重新哈希，实现了两种关键保护。

6.1 Salt 字节结构

Sender Address bytes 0-19 (20 bytes)
Flag byte 20
Entropy bytes 21-31 (11 bytes)
字段字节范围取值作用
Sender Address0-19msg.sender 或 address(0)权限部署保护：设为 msg.sender 时，只有该地址能成功部署
Redeploy Flag200x00 / 0x01（>0x01 直接 revert）跨链重新部署保护：设为 0x01 时，guardedSalt 包含 chainid，不同链地址不同；设为 0x00 则不加入 chainid
Entropy21-31任意 11 字节提供 88 bits 熵，用于盐值挖矿（vanity address）

6.3 两种保护模式详解

权限部署保护（Permissioned Deploy Protection）

将 salt 前 20 字节设为 msg.sender，_guard 会将 msg.sender 混入哈希。由于攻击者的 msg.sender 不同，计算出的 guardedSalt 不同，无法部署到同一地址。这有效防止了 frontrun 攻击。

跨链重新部署保护（Cross-Chain Redeploy Protection）

将第 21 字节设为 0x01，_guard 会将 block.chainid 混入哈希。同一原始 salt 在不同链上会产生不同的 guardedSalt，因此最终地址不同；这正是“跨链重新部署保护”，而不是“跨链同地址”。如果目标是权限保护下的跨链同地址部署，应使用第 21 字节 0x00。

⚠️ 注意：使用只读函数 computeCreate2Address / computeCreate3Address 时，必须传入经过 _guard 处理后的 guardedSalt；这些只读函数不会替你再次执行 _guard。

7.4 Values 结构体

所有 AndInit 函数都接收一个 Values 结构体，用于精细控制 ETH 的分配：

struct Values {
    uint256 constructorAmount;  // 部署时随 CREATE/CREATE2/CREATE3 发送的 ETH
    uint256 initCallAmount;     // 初始化调用时发送的 ETH
}

调用时 msg.value 必须 ≥ constructorAmount + initCallAmount，多余的 ETH 会退还给 refundAddress（默认 msg.sender）。

8代码示例

8.1 使用 ethers.js 通过 CreateX 部署合约（CREATE2）

import { ethers } from "ethers";
import ICreateX from "./ICreateX.json";

const CREATEx_ADDRESS = "0xba5Ed099633D3B313e4D5F7bdc1305d3c28ba5Ed";

const provider = new ethers.JsonRpcProvider("https://eth.llamarpc.com");
const wallet = new ethers.Wallet(PRIVATE_KEY, provider);
const createx = new ethers.Contract(CREATEx_ADDRESS, ICreateX.abi, wallet);

// 1. 构造 initCode（creationCode + 构造参数）
const factory = new ethers.ContractFactory(MyContract.abi, MyContract.bytecode, wallet);
const initCode = ethers.concat([
  factory.bytecode,
  ethers.AbiCoder.defaultAbiCoder().encode(["address"], [constructorArg])
]);

// 2. 构造 salt。
//    这里选择 0x00：权限保护 + 跨链同地址。
//    如果改成 0x01，则会启用跨链重新部署保护，使不同链的地址不同。
const salt = ethers.concat([
  wallet.address,                          // bytes 0-19: 权限保护
  "0x00",                                  // byte 20: 不加入 chainid
  ethers.randomBytes(11)                   // bytes 21-31: 88 bits entropy
]);

// 3. _guard：CreateX 的 compute* 函数不会自动执行 _guard。
//    对“msg.sender + 0x00”模式，guardedSalt = keccak256(abi.encode(msg.sender, salt))
const coder = ethers.AbiCoder.defaultAbiCoder();
const guardedSalt = ethers.keccak256(
  coder.encode(["address", "bytes32"], [wallet.address, salt])
);

const initCodeHash = ethers.keccak256(initCode);
const predictedAddr = await createx.computeCreate2Address(guardedSalt, initCodeHash);
console.log("预测地址:", predictedAddr);

// 4. 部署
const tx = await createx.deployCreate2(salt, initCode);
const receipt = await tx.wait();
console.log("部署成功，交易:", receipt.hash);

8.4 _guard 函数核心逻辑（Solidity 源码摘要）

function _guard(bytes32 salt) internal view returns (bytes32 guardedSalt) {
    (SenderBytes senderBytes, RedeployProtectionFlag redeployProtectionFlag) = _parseSalt(salt);

    if (senderBytes == SenderBytes.MsgSender && redeployProtectionFlag == RedeployProtectionFlag.True) {
        // 权限保护 + 跨链重新部署保护
        guardedSalt = keccak256(abi.encode(msg.sender, block.chainid, salt));
    } else if (senderBytes == SenderBytes.MsgSender && redeployProtectionFlag == RedeployProtectionFlag.False) {
        // 仅权限保护
        guardedSalt = _efficientHash(bytes32(uint256(uint160(msg.sender))), salt);
    } else if (senderBytes == SenderBytes.ZeroAddress && redeployProtectionFlag == RedeployProtectionFlag.True) {
        // 仅跨链重新部署保护
        guardedSalt = _efficientHash(bytes32(block.chainid), salt);
    } else {
        // 普通情况：非伪随机 salt 则哈希，防止保护机制被绕过
        guardedSalt = (salt != _generateSalt()) ? keccak256(abi.encode(salt)) : salt;
    }
}

9总结

CreateX 是目前 EVM 生态中最完善的通用合约部署工厂，其设计亮点可归纳为：

设计亮点实现方式解决的痛点
统一部署入口多链同一规范地址部署生态碎片化、重复造轮子
三种部署模式CREATE / CREATE2 / CREATE3 全覆盖不同场景的地址确定性需求
CREATE3 模式代理中转，地址与 initCode 解耦跨链同地址部署（构造参数不同时）
原子化部署+初始化AndInit 系列函数 + Values 结构体多笔交易的 frontrun 风险
Salt 结构化编码前20字节地址 + 第21字节标志 + 11字节熵权限部署保护 + 跨链重新部署保护
地址预计算computeCreateAddress / computeCreate2Address / computeCreate3Address手动计算地址易出错
EIP-1167 代理克隆deployCreateClone / deployCreate2Clone低成本批量部署相同 implementation 的代理实例
伪随机 Salt_generateSalt 基于区块属性开发者无需自行管理 salt

对于需要确定性地址、跨链部署、工厂化实例部署或 EIP-1167 clone 的 DeFi / 基础设施项目，CreateX 是常用的通用部署工厂之一。Safe 生态存在通过 CreateX 部署 Safe 的实践，但这不意味着 CreateX 取代了 SafeProxyFactory；具体项目仍应根据部署方案选择合适的工厂。
