以太坊执行层EL与共识层CL架构交互调研报告

报告时间：2026‑08‑18

调研对象：go‑ethereum(Geth)执行层、信标链共识层CL、Engine API交互

摘要：以太坊合并(The Merge)之后拆分为执行层EL + 共识层CL双层架构。Geth仅为执行层客户端，不包含PoS共识逻辑；共识层使用独立信标链客户端(Prysm/Lighthouse等)。两者通过Engine API私有RPC（JWT密钥鉴权）通信，共同完成区块生产、共识、状态落地。本报告涵盖背景演进、两层职责、Engine API（V1→V5）与ExecutionPayload、存储与进程模型。

一、背景：从PoW一体机到EL+CL双层架构

合并之前，Geth一个程序包办全部工作：交易执行、EVM、世界状态、PoW挖矿出块，共识与执行耦合在同一进程里。

拆分是分两步走的：2020‑12‑01 信标链（Beacon Chain）先行创世——一条只有验证者、没有交易和账户的纯PoS共识链，独立运行近两年、积累验证者生态；2022‑09‑15 全网总难度达到预设的TTD后，The Merge（巴黎升级，块高15537394）把两条链合体：PoW挖矿永久关闭，信标链接管共识，Geth退化为纯执行层。

为什么拆成两层

  • 节能与安全：PoS用质押代替算力，能耗下降约99.95%；攻击共识需要质押巨量ETH，且违规会被slash罚没本金。
  • 职责解耦：共识规则（时隙、投票、分叉选择）与执行规则（EVM、状态）各自独立演进——升级blob、提款等共识层能力时不必大改EVM。
  • 客户端多样性：任意EL可以搭配任意CL（Geth×Prysm、Nethermind×Lighthouse……），形成客户端矩阵，单一客户端出bug不再一票否决全网。
  • 最小接口：两层之间只需要一个Engine API契约，两边实现可以自由替换、独立升级。

二、架构总览

合并之后彻底解耦为两层：

  • 执行层 EL Execution Layer：处理交易、EVM执行、世界状态、生成ExecutionPayload；代表客户端：Geth(go‑ethereum)、Erigon、Besu、Nethermind。
  • 共识层 CL Consensus Layer：信标链，PoS质押、验证者管理、时隙调度、投票、区块终局确认；代表客户端：Prysm(Go)、Lighthouse(Rust)、Teku、Nimbus。

执行层 EL Erigon / Besu / Nethermind Go / Java / C# 备选执行客户端（曾经的C++客户端Aleth已停止维护）

三、执行层 EL(Geth)职责

  • 维护txpool交易池，校验交易签名、nonce、gas、余额；通过eth/68等P2P协议在EL节点间传播交易
  • EVM虚拟机执行，维护Merkle‑Patricia世界状态树（账户、合约、存储、收据）
  • 收到CL指令后组装 ExecutionPayload 执行负载
  • 对外暴露 eth_*、debug_* 等公开RPC给dApp/钱包
  • 对内暴露Engine API(engine_*)供CL调用

EL不做：信标链、质押验证者、attestation投票、时隙调度，不能独立出块——合并后EL自己不知道哪个是链头，没有CL驱动就无法生产新区块。

四、共识层 CL（信标链）职责

  • 质押管理：验证者激活/退出队列、奖励惩罚、slash罚没（双重提案、双重投票、环绕投票）；Pectra(2025‑05)前每验证者固定32 ETH，之后有效余额上限提高到2048 ETH
  • 时钟与随机：时隙Slot(12s)、纪元Epoch(32个slot，6.4分钟)调度；每slot提议者揭示RANDAO随机数，混入种子后选出下一轮区块提议者与证明委员会
  • 提议：被选中时通过Engine API驱动EL生成payload，组装信标区块签名后全网广播
  • 验证与分叉选择：区块到达后调用newPayload执行校验、fcu更新链头；LMD‑GHOST做分叉选择
  • 最终性finality：attestation同时投"链头票"和"检查点票"，连续两个Epoch超2/3质押确认后经Casper‑FFG完成最终确认（最快约12.8分钟）

CL不做：不执行EVM，看不懂交易，不维护账户状态，没有交易池。

三大核心Engine API说明

API 调用方向 时机 作用
engine_forkchoiceUpdated CL → EL slot开始(带属性) / 区块到达 ①同步head/safe/finalized链头视图；②携带payloadAttributes时触发EL后台构建新区块
engine_getPayload CL → EL 提议者构建阶段 获取EL（或MEV‑Boost builder）构建好的ExecutionPayload，此时尚未获得任何投票
engine_newPayload CL → EL 每次区块到达 执行交易并校验stateRoot等字段，返回VALID/INVALID/SYNCING；只校验不改变链头
engine_exchangeTransitionConfiguration CL → EL 合并过渡期 握手核对TTD等配置一致，上海升级后各客户端已不再必需
核心语义：getPayload拿到的是"候选区块"，newPayload是"执行并校验"，forkchoiceUpdated才决定"它是不是链头"。区块真正成为canonical并落盘发生在fcu更新head之后，而不是newPayload阶段——这正是原文档时序图中容易被误解为"共识完成后才下发执行"的地方。

Engine API版本演进

Engine API随硬分叉演进，每次升级只新增/修改必要的字段与方法：

版本 硬分叉 激活时间 关键变化
V1 Paris（The Merge） 2022‑09 初始版本：newPayload/getPayload/forkchoiceUpdated三大件
V2 Shanghai（Shapella） 2023‑04 payload增加withdrawals提款列表
V3 Cancun（Dencun） 2024‑03 增加blobGasUsed/excessBlobGas、parentBeaconBlockRoot（EIP‑4844）
V4 Prague（Pectra） 2025‑05 增加executionRequests（EIP‑7685，EL交易驱动的系统合约请求）
V5 Osaka（Fusaka） 2025‑12 getPayloadV5返回BlobsBundleV2（含cell证明，配套PeerDAS）；新增getBlobsV2/V3

版本号按方法独立递增：例如forkchoiceUpdated直到Prague仍是V3（字段没变就不升版）。EL对跨版本调用会返回 -38005 Unsupported fork 错误，因此EL、CL必须处于同一硬分叉世代。截至2026‑08主网处于Fusaka（V5）世代。

JWT鉴权与部署要求

Engine API虽只跑在本机，但并非无鉴权：EL和CL启动时读取同一个 jwt.hex（32字节随机密钥），每个请求携带HS256签名的Bearer token，验签失败直接拒绝。Geth侧通过 --authrpc.addr / --authrpc.port（默认127.0.0.1:8551）/ --authrpc.jwtsecret 三个参数配置。

⚠️ jwt.hex泄露＝攻击者可以伪造forkchoiceUpdated/newPayload指令，等于交出出块指令权。因此Engine API绝不能暴露公网，仅本机127.0.0.1访问。

ExecutionPayload结构

ExecutionPayload是EL交给CL的"执行结果信封"。CL把payload放进信标区块（连同proposer签名、attestation聚合等共识信息）后广播。字段按来源分为三类：

字段 含义 来源 引入版本
parentHash / blockNumber / blockHash 父块哈希 / 块号 / 本块哈希 EL —
stateRoot 世界状态根（执行结果） EL执行产生 —
receiptsRoot / logsBloom 收据树根 / 日志bloom过滤器 EL执行产生 —
transactions 本块交易列表 EL从txpool选择 —
gasLimit / gasUsed / baseFeePerGas gas上限 / 实际消耗 / 基础费(EIP‑1559) EL计算 —
feeRecipient 手续费接收地址 CL下发（payloadAttributes） —
prevRandao RANDAO随机值（PoS的随机源） CL下发 —
timestamp / extraData 时间戳（＝信标slot时间）/ 附加数据 CL下发 —
withdrawals 质押提款列表 CL下发（来自信标链状态） V2(Shanghai)
parentBeaconBlockRoot 父信标区块根（打通信标链上下文） CL下发 V3(Cancun)
blobGasUsed / excessBlobGas blob gas用量 / 超额量（EIP‑4844定价） EL计算 V3(Cancun)
requestsHash 系统合约请求根（EL交易触发的质押/提款请求） EL计算 V4(Prague)

六、存储与进程模型

两套独立数据库

  • Geth数据库(EL)：区块、交易、收据、账户状态trie，业务账本；底层LevelDB/Pebble KV库，老区块头/体/收据存在ancient冷数据区。
  • Prysm数据库(CL)：信标区块、信标状态、验证者、attestation投票记录，共识账本；底层BoltDB KV库。

两套数据库完全独立、互不读写对方数据，只通过Engine API交换payload与链头信息。

进程模型

  • 普通节点（同步链、查数据、提供RPC）：EL + CL 两个进程，缺一不可。
  • 质押验证者节点：EL + CL信标节点 + VC验证者客户端三个进程。

验证者客户端 Validator Client（VC）

  • VC持有BLS签名密钥，是唯一需要"签名"的进程：签区块提案、签attestation、聚合投票；信标节点负责链同步与分叉选择，VC通过本地RPC/gRPC向信标节点领取本验证者的职责。
  • Prysm、Lighthouse的VC是独立二进制进程；Teku、Nimbus可内嵌在信标节点进程内。
  • 密钥安全：提款密钥建议离线保管；也可用Web3Signer等远程签名服务托管签名。
  • 大量质押用户通过质押池（如Lido）质押，个人并不直接运行验证者节点。

七、常见误区与风险

  • ❌ go‑ethereum包含共识层 → ✅ Geth只有执行层，内部仅有一个共识引擎接口（clique PoA只用于私链/测试网）；Prysm是独立Go项目。
  • ❌ 只跑Geth可以同步链 → ✅ 合并后Geth自己不知道哪个是链头，区块同步到合并点附近就会停下，必须搭配CL。
  • ❌ Engine API没有鉴权 → ✅ 实际使用JWT共享密钥鉴权（jwt.hex）；密钥泄露等于把出块指令权交给攻击者。
  • ⚠️ Engine API禁止暴露公网，默认仅监听127.0.0.1:8551。
  • ⚠️ EL、CL客户端必须处于同一硬分叉世代，跨版本调用返回-38005(Unsupported fork)，升级时需同步切换。
  • ⚠️ 客户端集中风险：单一客户端占比超过2/3时，其bug可能导致全网无法finality；Geth、Prysm长期占比过半，社区持续呼吁客户端多样性。

八、总结

以太坊合并实现执行与共识完全解耦：CL负责"决策、投票、调度"，EL负责"干活、执行交易、维护账本"。

不是EL挖出区块上报CL；而是CL驱动EL生产payload，CL完成共识审批，再命令EL落地状态。准确地说：getPayload产出候选区块 → newPayload执行校验 → forkchoiceUpdated确立链头并落盘，Attestation投票紧随其后，两个Epoch后完成finality。

Engine API是两层之间的标准契约：自Merge的V1演进到Fusaka的V5，核心三步交互始终不变——理解这套交互，就理解了PoS以太坊节点的全部核心。
