OP链(Optimism)与ETH链完整技术报告

一、ETH链与OP链：L1 / L2定义、相互关系

1.1 层级归属

链名称 层级 定位说明
ETH（以太坊主网 Ethereum Mainnet） L1 第一层 基础底层链，负责最终结算、数据存储、安全保障，所有Rollup都依赖以太坊L1的安全性。
OP链（Optimism Mainnet） L2 第二层（Optimistic Rollup 乐观汇总） 运行在以太坊之上的扩容链，计算在L2执行，最终数据提交回以太坊L1，继承L1安全，不能独立存在。

1.2 两者核心关系

  • 以太坊L1是OP链的结算层、数据可用层、安全根；OP链没有自己独立的共识，安全性完全依托以太坊主网。
  • OP链使用OP‑Stack开源模块构建，属于Optimistic Rollup；大量交易在L2快速执行，不占用L1计算资源，降低gas费。
  • OP链与以太坊EVM等价（EVM Equivalence）：L1上能跑的所有 Solidity 智能合约都可以原样部署到OP L2（同一份编译字节码、同样的opcode与gas语义），开发工具链不变（Hardhat / Foundry / Remix 只需切换RPC）。合约部署后代码与存储写入L2状态，随状态根一起提交L1；地址推导规则与L1相同（CREATE/CREATE2），因此同一部署者在两链可得到相同合约地址。
  • OP链有一组部署在以太坊L1上的核心合约：OptimismPortal2（存取款）、DisputeGameFactory / FaultDisputeGame（状态根提议与故障证明争议游戏）、AnchorStateRegistry（锚定状态管理）等，控制L2存款、提款、状态提交、故障证明逻辑。
  • 旧版的 L2OutputOracle 状态根提交机制（许可制）已于 2024年6月 被无需许可的故障证明体系取代，现仅部分OP Stack链仍在使用（详见1.3）。
  • L2只负责高速执行交易；交易原始压缩数据、状态根（Output Root）最终必须写入以太坊L1，保证数据可恢复、可验证。

二、如何获取OP链的OP代币；是否可以用ETH兑换

2.1 OP代币基础

OP是Optimism的治理代币。OP代币原生部署在以太坊L1上（ERC‑20，合约地址 0x4200000000000000000000000000000000000042）；OP链L2上的OP是通过官方桥桥接的版本（由L2标准桥在L2铸造）。日常交易与使用绝大多数发生在OP L2网络，但代币的"根"（原生合约）在L1。

重要区分：OP链L2的"原生代币"（gas代币）不是OP，而是ETH。OP链上所有交易的gas费都以ETH支付；钱包里显示的"OP‑ETH"或"ETH on Optimism"只是钱包对桥接到OP链的ETH的标注方式，并不是另一种代币。OP是治理代币（用于治理投票、激励分配如RetroPGF），不能用来支付gas，也不参与L2出块安全（L2没有自己的共识）。
代币 在OP链L2上的角色
ETH（L2‑ETH / 俗称OP‑ETH） 原生代币 / gas代币：支付所有L2交易手续费（L2执行费 + 转嫁的L1数据费）；同时是DeFi最主要的基础资产（WETH交易对、借贷抵押品）
OP 治理代币：Optimism Collective治理投票、激励分配（空投 / RetroPGF）；不能支付gas

2.2 OP代币原理：ERC‑20 与治理设计

  • 标准ERC‑20代币：OP就是标准的ERC‑20合约（实现 transfer / approve / balanceOf 等标准接口），没有特殊的铸造/销毁逻辑。额外实现了 ERC20Votes（EIP‑2612 permit签名转账 + 投票权委托），支持链上治理。
  • 总量与通胀：总量 4,294,967,296 枚（2³²），初始年通胀率 2%（治理可投票调整）。
  • 双链形态（1:1锁定铸造）：L1 合约是"根"；L2 上的 OP 由官方桥 1:1 铸造（存L1锁资产→L2铸币，反向提款时L2销毁），两链合计总量始终守恒。两条链上合约地址相同（0x4200…0042），但各自维护独立的余额账本——同地址≠同资产，持有L1 OP与L2 OP是两笔不同记录。
  • 治理机制（Optimism Collective双议院）：Token House——OP持币人（可委托投票权）对协议升级、资金分配投票；Citizens' House——不可转让的公民身份，投票决定 RetroPGF 资助名单。投票在L1链上进行。
  • 价值捕获：OP Mainnet 的 L2 base fee 收入目前归入 Optimism 治理基金（由链上配置决定），是 OP 代币未来价值捕获的一条路径。

2.3 获取OP代币4种途径

  1. 方式1：交易所直接提币，网络选择Optimism（最简单）

    在中心化交易所购买OP，提币时网络选 Optimism，直接到你的OP链钱包，不需要跨链桥。

  2. 方式2：OP链上DEX，用ETH兑换OP（你问的方式）

    前提：钱包已经切换到 Optimism网络，钱包有OP链上的ETH作为gas手续费。

    在Uniswap、Velodrome等DEX，交易对 ETH / OP，直接在L2内部完成币币兑换。
    ⚠️注意：这是OP链内部的兑换，不是以太坊L1的ETH直接兑换OP；必须先把ETH跨链到OP L2，才能在L2用ETH换OP。

  3. 方式3：以太坊L1资产跨链到OP链（官方桥，最安全）
    • 钱包切换以太坊主网(L1)，访问Optimism官方桥
    • 把L1的ETH、L1的OP代币（或任意受支持资产）存入官方桥合约（OptimismPortal2 锁定）
    • L1合约锁定资产，向L2发送消息；OP链 L2StandardBridge 铸造对应数量资产给到你的L2地址，一般等待数分钟到账。
  4. 方式4：第三方快速跨链桥（体验更好，注意桥风险）

    使用 Hop、Across、Celer 等第三方桥，L1的ETH / OP 可以更快转入OP链（秒级~分钟级到账）。
    ⚠️注意：第三方桥速度快的原因是垫付流动性、替用户承担7天挑战期风险，会收取一定费用，安全性取决于桥项目本身；追求最安全请优先官方桥。

重要澄清：以太坊L1上的ETH不能直接在L1兑换OP。兑换操作发生在OP链L2的DEX合约；必须先将ETH跨链桥到OP链，才能拿这份L2‑ETH去兑换OP代币。

2.4 操作顺序：想用ETH换OP完整路径

1. 钱包拥有以太坊L1的ETH
2. 通过官方桥，把L1 ETH跨链 → OP链L2（钱包切换为Optimism网络）
3. OP链钱包现在有L2‑ETH（用于gas+做兑换的币）
4. 打开OP链上DEX，选择交易对 ETH‑OP，执行swap，得到OP代币

三、场景：OP链上A地址给B地址发送100 OP币，数据如何存回ETH(L1)链？

场景：网络是Optimism(L2)，A向B转账100 OP，这笔交易发生在L2，不会立刻发送到L1；是批量、异步提交回以太坊L1。下面完整拆解全流程。

 A ──转 100 OP──▶ B（在 L2 上发起交易，支付 L2-ETH 作 gas）

   ① L2本地执行：Sequencer 立即执行，A -100 / B +100，L2出块（秒级确认）
        │
        ▼
   ② 批量打包：Batcher 收集数百~数千笔 L2 交易，压缩（zlib/brotli）成 1 个 Batch
        │
        ▼
   ③ 数据上链：以 1 笔 L1 交易把压缩数据写入以太坊（默认 Blob(EIP-4844)，calldata 为回退）
        │   └─ L1 只保存原始数据，不执行这笔 L2 转账
        │      结果：A、B 在 L1 上的余额（ETH / OP）不发生任何变化
        │      （L1 上唯一的活动是 Batcher 用自己的 ETH 支付这笔上链交易的 gas）
        ▼
   ④ 状态提交：Proposer 生成 Output Root（状态根摘要）→ 提交到 FaultDisputeGame 争议游戏
        │
        ▼
   ⑤ 挑战窗口：约 7 天内无人挑战 → 该状态根在 L1 最终确认（finalized）
        │   └─ 有人挑战 → Cannon 虚拟机链上仲裁 → 作恶方保证金被罚没

步骤1：L2本地执行转账（发生在OP链内部）

  1. A钱包切换Optimism网络，发起交易：A → B，转账100 OP；支付L2 gas费（L2‑ETH）。
  2. Sequencer（排序器）接收交易，在OP链L2执行：A余额‑100，B余额+100，L2状态发生改变，L2区块确认，A/B立刻看到余额变化。
  3. 此时，这笔转账仅存在OP链L2本地，以太坊L1完全不知道这笔交易。

步骤2：Sequencer打包批量交易，压缩交易数据（Batcher模块）

  • Sequencer持续收集大量L2交易（包含A转100OP这笔交易），攒成一批Batch；对全部交易数据做压缩，降低上链成本。
  • 注意：L1不会保存完整的执行状态，保存的是压缩后的原始交易输入数据，有了这批原始数据，任何节点都可以重放所有L2交易，重建全部L2状态。

步骤3：Batcher将压缩交易数据提交到以太坊L1

  • Batcher组件调用以太坊L1上rollup合约，把压缩过的批次数据写入以太坊L1链上。Ecotone升级（2024-03）后默认使用 Blob（EIP‑4844），calldata 作为回退方案。
  • 此时A转100OP这笔交易的压缩原始数据已经永久保存在以太坊L1，但L1并没有运行、执行这笔转账。L1只存原始输入数据。
    注意：A、B两个账户在L1上的余额（ETH / OP）完全不会发生变化；L1上唯一发生的是Batcher用自己的ETH支付了这笔批量上链交易的gas费（与A、B无关）。

步骤4：Proposer提交L2状态根（Output Root）到L1的争议游戏合约

  • Proposer定期生成L2最新的状态根（StateRoot：整个L2世界状态的Merkle‑Patricia树根，包含A、B地址余额变化后的全部状态摘要），打包为 Output Root。
  • 通过 DisputeGameFactory 创建 FaultDisputeGame 争议游戏，把Output Root提交到以太坊L1。
    StateRoot不是完整余额，只是密码学摘要；L1靠这个摘要校验L2状态是否合法。
  • 补充：2024年6月之前，OP Mainnet使用许可制的 L2OutputOracle 合约接收状态根；此后已全面切换到无需许可的故障证明体系，旧机制废弃。

步骤5：约7天挑战窗口（Fault Proof故障证明机制）

  • 状态根提交L1后，进入约7天挑战窗口期。故障证明体系基于 Cannon（链上运行的MIPS指令虚拟机）+ OP-Challenger（挑战者客户端），任何人在无需许可的情况下都可以挑战。
  • 挑战者需质押保证金（bond），通过二分法（bisection）与提议者逐步缩小分歧范围，直到定位到某一条具体的错误指令，并在链上执行验证。
  • 验证失败的一方保证金被罚没（slashing），错误状态被回滚；若游戏临近超时仍有分歧，会触发时钟扩展（clock extension），被挑战时最终确认可能超过7天。
  • 挑战期内没有有效挑战，则该L2状态根在L1完成最终确认(finalized)。

关键总结：A转100OP这件事，L1到底存了什么？

✅ L1以太坊存储：
1. 压缩后的原始交易字节数据（Blob/calldata）：可以重放复现“A转给B 100OP”这笔交易
2. L2的StateRoot（状态根摘要），密码学证明L2全部账户状态

❌ L1以太坊不会存储：
不会在L1执行A给B转账；L1不会保存A、B的完整余额；L1上OP代币余额不会变化。
补充区分：普通L2转账 vs L2提款回L1

A在OP链转给B，属于L2内部转账；只会批量提交原始数据+状态根回L1，资产不会出L2。

只有当用户执行提款（Withdraw）操作，才会把资产从OP链"取出"，经过挑战期后在以太坊L1释放代币到L1地址，这是跨层资产移动，和L2内部转账完全不同流程。完整流程见 第五节。

四、OP链如何提升L1吞吐量：扩容原理

先澄清一个常见误解：OP并没有改变以太坊L1本身的处理速度（L1每秒能处理的交易数基本不变）。OP的思路是把"执行"从L1搬走，让整个系统（L1+L2）的吞吐量大幅提升，L1只保留结算、安全与数据可用性三项职责。

4.1 核心思路：执行与结算分离

  • 交易执行外包：L2交易只在Sequencer上执行，L1节点完全不需要执行这些交易，L1宝贵的算力不再被海量用户交易占用。
  • 数据压缩上链：L1只需要保存L2压缩后的原始交易数据（用于重建状态）和状态根摘要（用于验证），不需要保存中间执行过程。

4.2 三个关键机制

  1. 批量打包（Batching）：数百~数千笔L2交易打包成一个Batch，只以1笔L1交易提交。原本需要数百笔L1交易的gas，现在由1笔交易承担，成本被大幅平摊。
  2. 数据压缩（Compression）：Batch数据经 zlib / brotli 等压缩算法压缩后体积大幅缩小（一笔简单转账可由约100字节压至十几字节量级），进一步降低L1数据成本。
  3. Blob载体（EIP‑4844）：压缩数据写入专用的Blob空间，不经过EVM执行、不参与calldata竞价，有独立的费用市场，成本远低于calldata。Blob约18天后过期删除，但18天足够L2节点同步数据、挑战者验证状态；之后的状态安全性由状态根+故障证明保证。

4.4 原理示意图与总结

L1 原生模式：
   每笔交易 ──▶ 全网所有验证节点执行 + 数据永久保存 ──▶ 吞吐量受全网共识能力限制

OP L2 模式（吞吐提升原理）：
   N 笔 L2 交易 ──▶ ① 仅 Sequencer 执行（快）
              ──▶ ② Batcher 压缩打包（小，zlib/brotli）
              ──▶ ③ 1 笔 L1 交易写入 Blob（便宜，L1 只存数据、不执行）

   每笔 L2 交易在 L1 的边际成本 ≈ (1 笔 Blob 交易的费用) ÷ N
   L1 每处理 1 笔“批次交易” = 支撑 N 笔真实用户交易 ⇒ 系统总吞吐提升约 N 倍量级
安全不打折：即便Sequencer故障或作恶，任何人都能凭L1上的压缩原始数据重建L2全部状态，并在7天窗口内挑战错误状态根。因此"提速"换来的不是更弱的安全，安全等级仍由以太坊L1背书——这正是Rollup与侧链的本质区别。

五、L2与L1之间的资产进出：存款与提款全流程

5.1 存款（L1 → L2，Deposit）

  1. 用户在L1调用 OptimismPortal2，将ETH / 代币存入并锁定；
  2. L1合约向L2发送跨链消息（depositTransaction）；
  3. L2节点收到消息后，L2StandardBridge 在L2铸造等量资产（optimismMintableERC20）到用户L2地址，一般数分钟到账。
 [L1] 资产锁定于 OptimismPortal2 ──跨链消息──▶ [L2] L2StandardBridge 铸造等量资产
                              （一般数分钟到账）

5.2 提款（L2 → L1，Withdrawal）

  1. 用户在L2发起提款，L2上资产被销毁（burn），交易记录写入 L2ToL1MessagePasser；
  2. 等待包含该交易的 Output Root 由 Proposer 提交到L1；
  3. 用户在L1调用 proveWithdrawalTransaction 提交证明；
  4. 等待约7天挑战窗口结束（期间任何人可挑战）；
  5. 调用 finalizeWithdrawalTransaction，资产在L1释放到用户地址。
 [L2] 销毁资产,发起提款 ─▶ [L1] 提交证明(prove) ─▶ 约7天挑战窗口 ─▶ [L1] 最终确认(finalize),释放资产

5.3 为什么提款要等7天？

  • 给全网验证者 / 挑战者足够时间检查L2状态是否合法：如果Sequencer作恶提交了错误状态（例如伪造提款记录），挑战者可在窗口期内发起故障证明，回滚错误状态。
  • 7天是"安全性"与"用户体验"之间的权衡。想要立即到账的用户可使用第三方快速桥（如第二节方式4所述，第三方桥垫付资金、替用户承担挑战期风险，收取一定费用），或使用交易所直接提币（方式1，由交易所内部处理）。
一图看懂两种方向：存款（L1→L2）快——只等L1消息确认，数分钟；提款（L2→L1）慢——必须经过证明+挑战期，约7天。方向不对称是Optimistic Rollup的固有特性（ZK Rollup的提款等待可缩短到小时级，但证明生成成本不同）。

六、核心概念小结

  • ETH主网 = L1 底层结算链；Optimism(OP链) = L2乐观Rollup扩容链，安全依附以太坊L1。
  • OP代币原生合约在L1，日常使用多在OP L2；想用ETH换OP，要先把ETH跨链桥到OP链，再在L2 DEX兑换，L1不能直接兑换。
  • L2内部转账(A→B转100OP)：L2立刻执行；随后Sequencer批量压缩交易数据上送L1（Blob），Proposer提交状态根到争议游戏；L1保存原始交易数据+状态摘要，约7天无需许可故障证明窗口完成最终确认；L1不执行这笔转账逻辑。
  • OP提升的是整个系统（L1+L2）的吞吐量：执行搬离L1、批量压缩、Blob载体三个机制叠加，L1处理1笔批次交易就能支撑数百~数千笔真实用户交易；L1本身吞吐不变，但安全等级不打折。
  • 资产进出不对称：存款（L1→L2）数分钟；提款（L2→L1）需证明+约7天挑战期；第三方快速桥可换取速度但引入桥风险。
  • 只要L1保存了压缩原始交易数据，任意节点可以全部重放，重建OP链全部账户状态，实现L2的安全性保障。
