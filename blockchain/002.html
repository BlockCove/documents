一、什么是 EIP-2612 Permit

EIP-2612（ERC20 Permit） 是以太坊改进提案，为标准 ERC20 代币增加链下签名授权标准。 它基于 EIP-712 结构化可读签名，允许代币所有者不用发送链上 approve 交易， 通过钱包离线签名生成授权凭证；任意账户（用户、中继Relayer、合约）可将签名上链调用 permit() 设置授权额度 allowance。

最早由 MakerDAO 的 DAI 代币率先实现 permit 模式，后标准化为 EIP-2612；目前 DAI、USDC（v2+）、UNI、LINK、AAVE 等主流代币已广泛支持。

二、传统 ERC20 approve 原生机制存在什么痛点

flowchart LR A[用户Alice] -->|"TX1：approve(DEX合约,金额)
用户支付Gas"| B[ERC20合约
更新allowance] B -->|等待区块确认| A A -->|"TX2：调用DEX.swap()
DEX内部执行transferFrom"| D[代币划转完成]
  1. 必须两笔独立链上交易：先 approve，再执行swap/deposit；交互步骤长、等待确认时间久。
  2. 授权交易必须由所有者EOA发起：approve依赖 msg.sender，无法由第三方代发。
  3. 用户必须持有原生Gas代币（ETH） 才能发起授权；新用户只有代币、没有ETH时完全无法授权。
  4. 两次Gas消耗，两笔交易均需成功才能完成操作，任一交易失败（如网络拥堵、Gas不足）将导致整个流程中断，需重新开始。

三、EIP-2612 Permit 完整工作流程

flowchart TD S[Alice 用户钱包] -->|1.链下签名 EIP-712消息（免费、无Gas）
生成v,r,s签名| SIG[Permit签名凭证] SIG -->|2.签名传给DApp/中继Relayer| RELAYER[提交者（任意账户）] RELAYER -->|"3.一笔链上交易：
token.permit(owner,spender,value,deadline,v,r,s)"| TOKEN[支持EIP2612的ERC20合约] TOKEN -->|"验签通过 → 设置 allowance(Alice→spender)=value
nonce 自增防重放"| ALLOW[授权生效] ALLOW -->|4.同一交易内继续调用业务合约
业务合约执行transferFrom| FIN[代币划转完成]

核心接口标准定义

interface IERC20Permit {
    function permit(
        address owner,      // 代币持有者
        address spender,    // 被授权合约/地址
        uint256 value,      // 授权额度
        uint256 deadline,   // 签名过期时间戳
        uint8 v, bytes32 r, bytes32 s // ECDSA签名
    ) external;

    // 获取当前nonce（防重放）
    function nonces(address owner) external view returns (uint256);
    // EIP712域分隔符，防止跨合约/跨链签名复用
    function DOMAIN_SEPARATOR() external view returns (bytes32);
}

钱包展示 普通交易弹窗 EIP712结构化可读签名弹窗，内容可解析展示

五、EIP-2612 解决的核心问题总结

  • ✅ 消除“两次交易”痛点：授权和业务操作合并为一笔链上交易，大幅优化DeFi用户体验；
  • ✅ 支持Gasless无Gas授权（元交易基础），解决“有代币但没有ETH无法交互”的新用户门槛；
  • ✅ 授权动作与提交动作解耦：谁都可以提交签名上链，催生中继Relayer服务；
  • ✅ EIP712标准化可读签名，相比原始hash签名，钱包可以展示授权明细，提升透明度；
  • ✅ 标准化安全机制：nonce防重复使用签名、deadline限制授权有效期、domain separator防止跨合约签名劫持。

六、安全风险与注意事项（重点）

⚠️ 主要风险点

  1. 钓鱼签名攻击：Permit只是签名，不会弹出Gas交易弹窗，用户警惕性更低；恶意DApp诱导签署大额授权签名后，可立刻调用transferFrom盗币；
  2. 签名有效期风险：若deadline设置极大（永久有效），签名一旦泄露可长期被攻击者提交；建议有效期控制在几十分钟~几小时；
  3. 签名泄露与被抢先提交：签名在链下传递（如通过 HTTP API 发给 Relayer）或出现在待处理交易中时，任何获取到该签名的第三方可立即调用 permit() 抢先消耗 nonce。若原始交易包含后续业务操作（如 swap），将因 nonce 已失效而回滚；若签名授权了恶意地址为 spender，则可能被盗币；
  4. 不要混用 permit + 无限授权（type(uint256).max），一旦签名泄露损失巨大；
  5. 仅支持实现EIP-2612的代币合约，普通ERC20不具备permit函数。

七、典型业务场景

  • DEX一键Swap：签名Permit，单笔交易完成授权+兑换；
  • Lending借贷平台存款：Permit + deposit合并调用；
  • 元交易Gasless产品：第三方Relayer代用户发送permit交易；
  • 钱包/支付应用：降低新用户准入门槛，不用预先购买ETH；

八、延伸：EIP-2612 vs Permit2 简要区分

EIP-2612：代币合约原生内置，仅针对当前代币生效； Permit2（Uniswap）：独立通用中介合约，单一签名支持多币种、批量授权，不依赖代币是否实现EIP2612。

9.2 签名数据结构：value 是签名的一部分

Permit 签名的 EIP-712 类型定义如下——owner、spender、value、nonce、deadline 全部被包含在签名原文中： 

// EIP-712 Permit 类型（摘自 SimpleTokenWithPermit.sol）
bytes32 private constant PERMIT_TYPEHASH = keccak256(
    "Permit(address owner,address spender,uint256 value,uint256 nonce,uint256 deadline)"
);

签名生成流程：

flowchart LR A["原始数据
owner, spender, value
nonce, deadline"] -->|"1. abi.encode + keccak256"| B["structHash
（结构化哈希）"] B -->|"2. 拼接 \x19\x01
+ DOMAIN_SEPARATOR
+ structHash"| C["digest
（最终签名摘要）"] C -->|"3. ECDSA.sign(digest, privateKey)"| D["v, r, s
（签名结果）"]

这意味着：

  • value 被 ECDSA 签名锁定——owner 线下签名时指定授权多少代币，签名就绑定多少。任何人篡改 value（比如把 100 改成 10000），签名有效载荷的哈希就变了，ecrecover 恢复出的地址对不上 owner，验证直接失败
  • owner 可以精确控制授权额度——签多少就授权多少，不会像传统 approve(spender, type(uint256).max) 那样把"无限授权"的决定权交给合约
  • spender 也是签名的一部分——签名锁定了授权对象，签名给 Vault 的凭证不能拿去给另一个恶意合约用
  • deadline 也是签名的一部分——签名过期后即使被截获也无法上链执行
⚠️ 安全推论：正因 value 被锁定在签名中，调用 depositWithPermit() 时传入的 value 必须与签名时的 value 一致。如果传更大的值，permit 设的额度不够，transferFrom 会失败；如果传更小的值，则是浪费了一次 nonce 签了一个比实际需求小的额度。所以签名脚本的 .env 中 VALUE 与最终链上参数要严格一致。

9.3 合约调用链路（以 SimpleVault 为例）

核心场景：账户 A 持有大量 MTK，A 线下签名授权 Vault 从自己账户划转 100 MTK，将签名数据给 B。B 调用 Vault，B 支付 Gas，B 收到 100 MTK。

sequenceDiagram participant A as 👤 账户A（持币者） participant Script as 📜 sign-permit.js participant B as 👤 账户B（收款人） participant Vault as 🏦 SimpleVault participant Token as 🪙 SimpleTokenWithPermit Note over A,Script: ① 链下签名（免费、无Gas） A->>Script: 配置 .env：PRIVATE_KEY=A的私钥,
SPENDER_ADDRESS=Vault地址, VALUE=100 Script->>Script: signTypedData(Permit:{owner:A, spender:Vault,
value:100, nonce, deadline}) → v,r,s Script-->>A: A 拿到签名 (v, r, s) Note over A,B: ② A 把签名数据发给 B（链下传输） A->>B: 发送：from=A地址, value=100,
deadline, v, r, s Note over B,Token: ③ B 提交一笔链上交易（B 支付 Gas，B 收到代币） B->>Vault: payWithPermit(A地址, 100, deadline, v, r, s) Vault->>Token: permit(A, Vault, 100, deadline, v, r, s) Token->>Token: ecrecover(digest, v, r, s) == A ✅ Token->>Token: allowance[A][Vault] = 100
nonces[A]++ Vault->>Token: transferFrom(A, B, 100) Token->>Token: balance[A] -= 100
balance[B] += 100 Vault->>Vault: emit Payment(A, B, 100)

关键点：

  • A 不需要持有 ETH——签名是链下的，不消耗 Gas
  • B 支付 Gas，B 收到代币——这就是"元交易"支付场景
  • 一笔交易完成验签 + 授权 + 划转，不需要 A 预先 approve
  • 签名绑定了 A、Vault、100 MTK——B 不能改金额、不能改收款人（msg.sender 即 B）

十、结论

EIP-2612 Permit 没有修改 ERC20 转账逻辑，只是新增一套授权通道。它从根本上解决传统approve“双交易、强制用户付Gas”的巨大UX短板， 是DeFi生态中Gasless交互、元交易基础设施最重要标准之一；目前是主流新项目ERC20代币标配扩展。
