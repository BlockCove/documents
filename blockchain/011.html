Chapter 01

什么是明签（Clear Signing）

一套由以太坊基金会、Ledger、MetaMask、Trezor、WalletConnect 等多方联合推动的开放标准， 目标是终结加密货币领域的"盲签"问题，实现所见即所签。

WYSIWYS · What You See Is What You Sign

明签的核心是 ERC-7730——一种结构化数据的清晰签名格式，配合 clearsigning.org 公共注册库，让钱包在用户签名前把原本不可读的 十六进制交易数据（calldata）翻译成人类能理解的交易摘要。

2026 年 5 月 12 日，以太坊基金会宣布由钱包开发者、安全公司及其万亿美元安全倡议等参与的 Clear Signing 工作组启动公开方案。需要注意：ERC-7730 本身并非在这一天才诞生， 当前规范的 2.0.0 schema 为 Active；2026-05-12 是 Clear Signing 生态方案正式对外发布的重要节点。

对用户而言，最大的变化是：签名确认界面不再只有难以理解的 hex， 而是将操作意图、金额、地址 / 对手方、协议等关键信息转成可读字段。 具体展示字段并不是固定的"四要素"，而由 descriptor 和钱包 UI 决定。

Chapter 02

解决什么问题：盲签的危害

在许多重大加密安全事件中，攻击链的最后一步涉及用户批准一笔自己无法充分理解的交易。 盲签会削弱"签名前人工复核"这道防线，因此是钱包安全体验中的重要风险点。

明签要解决的核心问题是 盲签（Blind Signing）——用户在无法理解交易 真实内容的情况下被迫签名确认。钱包界面上那串长长的十六进制 calldata，对绝大多数用户 来说等同于乱码，但点击"确认"的那一刻，授权已经生效。

01

无限授权 Draining

诱导用户签署 approve(spender, max)，把无限额度授权给恶意 spender； 一旦授权生效，该 spender 后续可通过 transferFrom 等机制转移代币。

02

前端伪装

dApp 界面看起来完全合法，但底层构造的 calldata 指向恶意合约，用户在不知情下签名。

03

硬件钱包盲区

硬件钱包只能显示原始十六进制，用户要么开启盲签（放弃硬件钱包安全意义），要么无法使用复杂 DeFi。

!
Bybit：为什么"看清楚再签"很重要

2025 年 Bybit 事件中，攻击者通过 Safe 钱包前端 / 供应链层面的入侵操纵签名者看到的交易内容，诱导其批准恶意操作。 以太坊基金会随后在 Clear Signing 公告中将该事件作为盲签风险的典型案例之一。它并不意味着"明签能解决所有供应链攻击"，而是说明可信签名屏幕的重要性。

Chapter 03

工作原理：从 calldata 到可读摘要

明签架构拆成三个核心组件：ERC-7730 描述符标准、公共注册库、钱包端本地解码与显示。 四步流水线把十六进制变成人类可验证的交易摘要。

STEP 01

dApp 发起交易

用户在 dApp 上操作，dApp 构造包含函数选择器和参数的原始 calldata，发送给钱包。

STEP 02

钱包查询注册库

钱包根据目标合约地址，从 clearsigning.org 公共注册库（或本地缓存）获取 ERC-7730 描述符。

STEP 03

本地解码

钱包用描述符中的格式化规则，把原始参数翻译成人类可读字段（如 "1,000 USDC"）。

STEP 04

安全显示

解码后的结构化摘要被送到硬件钱包的可信屏幕上，用户确认后才进行签名。

✓
关键点：签名时由钱包掌控最终展示与信任策略

钱包在签名时根据交易数据、匹配到的 descriptor 以及自身信任策略生成展示结果；descriptor 可以预先缓存， 因此不要求每次签名都实时访问链上 RPC。与此同时，注册库、地址命名、代币元数据等外部数据仍可能引入额外信任假设， 钱包应对来源、版本和匹配关系进行校验。

Chapter 04

ERC-7730 描述符结构

描述符是一个独立的 JSON 文件，与合约本身分离——无需重新部署合约，就能为现有协议添加明签支持。

context 绑定层

通过 chainId + address 将描述符绑定到具体的合约部署。钱包据此判断"这笔交易该用哪份描述符"。

metadata 元数据层

定义项目名称、版本号和可复用常量（如代币地址、合约地址别名），供 display 层引用。

display 展示层

核心部分——将每个函数签名映射为人类可读的标签和字段格式化规则（tokenAmount、contract、token 等显示类型）。

验证机制 & 内置支持

✓ 描述符可以由任何人贡献；注册流程可结合独立审查与 attestation，钱包再按自身信任策略决定是否采用
✓ 钱包自行决定信任哪些来源——可信中立治理模式
✓ 以太坊基金会的 Trillion Dollar Security Initiative（1TS）承担 Clear Signing 注册基础设施的中立托管角色
✓ ERC-7730 v2 提供 tokenAmount、addressName、date、calldata 等字段格式，可组合描述常见交易数据

Scope

明签到底解决什么，不解决什么

最容易产生的误解，是把"可读"等同于"安全"。更准确的理解是：Clear Signing 强化的是签名前的可验证性，而不是替代整个安全体系。

✓

它能解决

把函数参数、金额、地址、意图等从机器可读数据转换成更适合人工复核的签名界面，降低"不知道自己签了什么"的风险。

!

它不能保证

不能证明合约没有漏洞、协议不是 rug pull、经济模型没有风险，也不能替代交易模拟、审计、权限分析和运营安全。

→

正确的安全模型

Clear Signing + trusted display + transaction simulation + contract / protocol risk analysis 才更接近完整的交易安全闭环。

Chapter 05

明签的核心价值

从用户安全到生态开放，明签在多个维度上重构了加密交易签名的信任模型。

维度 说明
终结盲签 用户能看到交易真实意图（操作、金额、对手方、协议），而非十六进制乱码，从根本上降低钓鱼和恶意授权成功率。
硬件钱包价值回归 硬件钱包安全意义在于"可信屏幕上确认后再签名"，盲签让这道防线形同虚设；明签让硬件钱包真正发挥作用。
无需重新部署 描述符是独立的 off-chain JSON，现有协议无需修改或重新部署合约即可增加明签元数据；但仍需要 ABI / descriptor 编写、验证、注册及钱包侧支持，因此并非"零成本接入"。
开放标准、生态协作 ERC-7730 是开放标准，Ledger 最初发起，Clear Signing 注册基础设施由以太坊基金会承担中立托管角色；协议方提供描述符，钱包决定采用哪些来源与信任信号。
钱包侧验证与展示 钱包负责在签名前匹配 context、应用 display 规则并执行自身信任策略；descriptor 可预先缓存，但外部注册库、名称 / 代币元数据等仍可能存在额外信任假设。
防钓鱼 配合 Contract Lists（类似 Token Lists 的合约身份列表），钱包可以验证合约身份，防止仿冒合约。
生态正在扩张 官方 Clear Signing 生态页面的 2026-06-30 快照显示已有 51 个协议、380 个已发布 descriptor；钱包集成仍在持续推进，不能把"参与生态"等同于所有钱包均已完整支持。
Chapter 06

缺点与局限性

明签不是银弹。了解它能解决什么、不能解决什么，才能正确评估其在安全体系中的位置。

01

覆盖率仍受长尾协议影响

当前公共注册路径是开放、无许可的，任何人都可以提交 descriptor；真正的瓶颈变成是否有人为协议编写、验证并维护 descriptor，以及钱包是否接受其来源。 因此大量新部署或低关注度合约仍可能无法获得可读展示，最终回退到未明签 / 原始或基础解码展示。

02

descriptor 信任与注册表仍是安全面

ERC-7730 通过 context 约束 descriptor 适用于哪个合约 / 消息，并要求钱包校验这些约束；但 descriptor 本身是链下元数据。 因此恶意或错误 descriptor、注册表污染、来源与 attestation 信任策略，以及外部名称 / 元数据解析，仍然是需要防护的风险面。钱包必须避免把"可读"误认为"天然可信"。

03

钱包支持与 descriptor 供给仍是双侧瓶颈

钱包必须支持 ERC-7730 才能消费 descriptor；协议方则需要提供并维护准确的描述符。这里不是要求 dApp 在每次交易时参与解码，而是生态需要同时具备descriptor 供给与wallet consumer。 任一侧缺失，用户都可能回退到未明签展示。

04

不验证业务逻辑和经济安全性

明签只解决"你知不知道自己在签什么"，不验证合约代码是否有漏洞、经济模型是否合理、项目是否是骗局。一个明签显示清晰的 rug pull 交易仍然危险。

05

不等于完整的执行模拟 / trace

ERC-7730 可以描述 embedded calldata 等嵌套调用，但它本身不是 EVM 执行模拟器，也不会自动重建任意交易执行后的 internal-call trace。 对 multicall、复杂 proxy、动态调用等场景，仍需要相应 descriptor、钱包实现以及必要时的交易模拟 / trace 能力。

06

跨链与实现碎片化

ERC-7730 当前核心规范面向 EVM calldata 与 EIP-712 typed messages。其他生态可以复用 descriptor 思路，但仍需定义自己的交易容器、地址与信任策略。 例如 TRON 在 2026 年已出现跟进 ERC-7730 的 TIP-7730 草案，说明跨链适配正在发生，但仍处于早期。

Chapter 07

总结

明签是以太坊安全基础设施的重要升级，但它只是多层安全体系中的一环。

核心判断

明签把"签名确认"这道最后防线从"盲猜"变成"可读可验"。核心是 ERC-7730 标准 + 公共注册库 + 钱包本地解码， 最大价值是让硬件钱包的可信屏幕真正发挥作用——在此之前，硬件钱包对复杂 DeFi 交易几乎形同虚设。

但目前仍处于早期推广阶段，存在长尾覆盖不足、缺乏链上密码学绑定、需要生态双向支持等局限。 明签不能替代用户自身的风险判断，也不能替代交易模拟、合约审计、代码审查等其他安全层。

长远来看，随着 On-chain Clear Signing、跨链标准统一、生态参与度提升，明签有潜力成为 加密钱包的默认体验——就像今天浏览器地址栏的 HTTPS 锁标识一样，从"新功能"变成"基础设施"。
