1核心问题回顾：EOA 的 getBytecode 为什么一直是空

一个由 privateKeyToAccount 生成的普通 EOA（外部拥有账户）在未启用 EIP-7702 时没有可执行合约代码，因此 publicClient.getBytecode({ address: alice.address }) 通常返回 null。一旦该 EOA 被 EIP-7702 委托，账户的 code 不再为空，而是一个 23 字节的委托指示器 0xef0100‖delegateAddr。

🧾 EOA 账户
由私钥控制：传统 EOA 不执行合约代码，也没有应用层可用的合约 storage；账户状态仍包含 balance、nonce、codeHash、storageRoot 等协议字段。
getBytecode → null
📦 合约账户
地址下保存部署时的 bytecode。
getBytecode → 0x6080...（十六进制字节码）
⚠️ 最容易踩的第一个坑
不要把 getBytecode() 的返回值简单等同于「EOA / 合约」二分判断。null 表示 RPC/viem 视角下没有代码，0x 表示空代码；而 EIP-7702 委托账户返回的是 0xef0100‖delegateAddr。另外，Cancun 之后 SELFDESTRUCT 通常不会清除既有合约代码，因此“0x = 被 SELFDESTRUCT 销毁的合约”这一旧说法并不准确。

2Type-4 交易的完整执行流程

EIP-7702 引入 Type-4（0x04）set-code transaction，使 EOA 可以把一个已部署合约指定为自己的委托实现（implementation）。它是协议层的 EOA code delegation 机制，可用于批处理、赞助交易等，但不应简单称为“账户抽象的 EVM 原生实现”；它与 ERC-4337 是不同层次的机制。关键在：authorizationList 的处理发生在交易主逻辑（calldata）之前，属于协议预处理阶段。

STEP 1

交易进块，发送方（bob）nonce 自增、预扣 gas

交易本身由 bobWalletClient 签名发送，gas 由 bob 承担（做 relayer / 代付）。

▼
STEP 2 · 协议预处理阶段

顺序遍历整个 authorizationList，逐条 applyAuthorization

对每一条：ecrecover 恢复签名者 → 校验 chainId 与 authorization-nonce → 合法则把 0xef0100 || delegateAddr 写入该 EOA 的 code 槽，并使其 authorization-nonce +1。

▼
合法

委托生效

该 EOA 账户 code 被持久写入为委托指示器；在没有再次授权改变/清除之前，它会跨交易、跨区块保持。

非法

仅跳过本条

签名错误 / nonce 不匹配 / chainId 不符 → 跳过这一条，不回滚整笔交易，继续处理下一条。

▼
STEP 3 · 关键

全部授权处理完毕，才执行交易 calldata（如 alice.execute(calls)）

即使后面的 execute(calls) revert，前面已成功处理的委托指示器也不会回滚！委托状态会持久保留，与本次 calldata 的执行成败无关；但它并非不可修改，后续可以再次委托到其他地址或显式清除。

💣 致命坑（代码层面直接踩）
业务逻辑失败（交易 status = 0）≠ 撤销 7702 委托。
你写的 writeContract({... authorizationList:[auth]}) 即使 execute revert，alice 的委托也已经留在链上。若不处理，alice 会一直处于可被调用的委托状态。

3authorizationList 多元素行为（两条铁律）

这是你问的核心问题。authorizationList 里放多个元素，不是叠加、不是批量给一个账户委托多个实现，规则非常明确：

场景执行结果示例
同一 authority 签名多条 按顺序逐条处理，最后一条有效授权生效，前面的有效授权会被后续有效授权覆盖。
每条有效授权都会使该 authority 的 authorization nonce +1；如果 nonce 不匹配，该条失败并跳过。		 [authA, authB]（都是 alice 签）→ 仅 authB 生效
不同 EOA 签名多条 全部独立生效，互不干扰。一笔交易同时完成多个账户的 set-code，gas 由交易发送方承担。 [authA(Alice), authB(Charlie)] → alice、charlie 同时完成委托
单条校验失败 仅跳过失败的那一条，不影响整笔交易和其他条目，不会 revert。 —

3.1 同账户多条 → 取最后（常见误用）

❌ 错误用法

同一个 alice 签两条 auth 塞进一个列表：authorizationList: [authX, authY]（假设两条 nonce 连续且都有效）

最终 alice 委托到 Y，X 的委托结果被 Y 覆盖；两条有效授权都会消耗一个 authorization nonce。若业务本身需要在同一笔 Type-4 交易里连续修改委托，这种写法有意义，但普通场景下通常没有必要。

3.2 不同账户多条 → 全部生效（正确用途）

交易字段

authorizationList: [authA, authB]

authA ← 由 alice 私钥签名；authB ← 由 charlie 私钥签名。列表与谁发交易、谁付 gas 无关。

▼ 协议顺序 apply
alice

code ← 0xef0100‖delegateA，alice 委托生效

charlie

code ← 0xef0100‖delegateB，charlie 委托生效

▼ 然后执行

本交易 calldata：alice.execute(calls) —— 此时 alice 已经是委托账户，调用走代理逻辑。

📌 关键认知
authorizationList 是协议层字段，和合约 ABI 无关。合约本身看不到这个列表——它在 EVM 预处理阶段就被消耗完，执行 calldata 时列表已不存在。

4最大误区：委托是「当前交易」还是「链上持久」？

这是整份报告最重要的一节。authorizationList 只属于当前这笔 Type-4 交易，但由它成功写入的委托状态会持久存在于链上——两者完全不同。

对象生命周期说明
authorizationList 字段本身 仅当前这笔 Type-4 交易 别的交易（普通交易、别的 Type-4 交易）不带这个 list，就完全不会走这轮处理逻辑。
委托状态（EOA 的 code 槽） 链上持久，跨交易、跨区块 一旦写入 0xef0100‖addr，不会自动消失；任何后续交易都不会「顺手撤销」它。

4.1 时间线：为什么「下一笔交易没带 authorizationList」也不会恢复 EOA

交易 A（Type-4）

携带 [aliceAuth]，bob 发送，打包上链

预处理阶段：alice 的 code 被持久写入 0xef0100‖delegateAddr。然后执行 alice.execute(calls)。即使 execute revert，alice 的 code 修改也不回滚。

▼ 链上状态
中间态

alice 账户 code = 0xef0100...

alice 已是委托账户，不是普通 EOA。

▼
交易 B（任意交易）

任何人不带 authorizationList 发交易

协议完全不会碰 alice 账户——但 alice 链上 code 依旧是 0xef0100...，仍然处于委托模式。任何 CALL/STATICCALL 打到 alice 地址，都会走委托代理逻辑。getBytecode 依旧返回 0xef...，不会变回 null。

▼
交易 C（Type-4）

显式清零：sign contractAddress = 0x0 的 authorization

必须再提交包含清除授权的 Type-4 交易，将授权中的 address 设为零地址；协议会清除 alice 的委托指示器，恢复为空代码状态。若没有其他代码，getBytecode 回到 null（具体 RPC 返回仍应以客户端行为为准）。

💥 一句话说清误区
「authorizationList 只在当前交易生效」——对，但这只说明列表的字段不会被别的交易复用。绝不能说「委托只在当前交易生效」：authorizationList 只是写入/修改/清除委托状态的手段，一旦写入，状态持久驻留链上。
⚠️ 早期的「仅本交易生效」版本
早期 EIP-7702 草案曾有过「委托仅当笔交易生效、执行完自动还原」的语义，最终定稿已删除，全部改为持久状态。网上旧资料若说「临时委托」务必以最终规范为准。原生 7702 没有「临时模式」，想实现临时效果只能在委托合约内部自己写逻辑清除自己（合约层，非协议原生）。

5getBytecode 四种返回值对照

地址类型getBytecode 返回判断方式 / 说明
普通 EOA null 无字节码。你 alice 的情况。
空代码账户 0x 当前没有代码。不能简单理解为“曾经被 SELFDESTRUCT 销毁”；Cancun 之后，SELFDESTRUCT 对既有合约代码通常不会再产生清码效果。
存活合约 0x6080...（非空字节码） 正常部署的合约。
EIP-7702 委托账户 0xef0100‖delegateAddr（40 位十六进制） 委托已生效的标志；地址部分可解码出委托目标。
📌 判断函数
async function isContract(address, publicClient) {
  const bytecode = await publicClient.getBytecode({ address });
  // null = 没有代码；0x = 空代码；非空 = 合约代码或 7702 委托指示器
  return bytecode !== null && bytecode !== '0x';
}
⚠️ 需要区分「有代码」与「普通合约」

bytecode !== null && bytecode !== '0x' 只能说明账户当前存在非空 code，不能区分普通合约和 EIP-7702 委托账户。若要识别 7702，可检查 bytecode.startsWith('0xef0100')；此时后 20 字节是委托目标地址。

6易错点清单（务必逐条核对）

以下每一条都是实际开发中踩过 / 容易踩的坑，按「误解 → 正确认知」呈现。

❌ 误解 1：委托只在带 authorizationList 的那笔交易里生效，交易结束就还原
正确：委托状态写入后链上持久。不带 authorizationList 的后续交易不会自动还原 EOA；必须显式提交清除授权（zero-address authorization）。
❌ 误解 2：同一账户往一个列表塞多条授权，会叠加多个委托实现
正确：同一 authority 的多条授权按顺序处理，最终以最后一条有效授权指定的地址为准；每条有效授权都会使该 authority 的 nonce +1。
❌ 误解 3：execute(calls) revert，整笔交易回滚，委托也一起撤销
正确：委托写入发生在预处理阶段，与 calldata 执行成败无关；业务 revert 不会撤销已写入的委托状态。
❌ 误解 4：authorization 的 nonce 就是普通交易 nonce
正确：是 authority 账户自己的 nonce，用于授权签名的重放保护；它与“交易发送方的当前交易 nonce”在语义上需要区分。每成功处理一条授权，authority nonce +1；失败条目不会递增。若 authority 同时就是 Type-4 交易发送方，还要注意发送方交易 nonce 会先递增，因此自执行场景的授权 nonce 需要与交易 nonce 正确配合。
❌ 误解 5：code.length > 0 就是有效合约
正确：0x 是空字节码，其字节长度为 0；不要用 JavaScript 字符串的 '0x'.length 来判断代码长度。并且 Cancun 之后不能把 0x 简单解释为 SELFDESTRUCT 的结果。若要识别 7702 委托，应额外检查 0xef0100 前缀。
❌ 误解 6：EOA 地址可以像合约一样直接 writeContract / simulateContract
正确：普通 EOA 无 code，直接调用会失败；必须先完成 7702 委托，且委托目标需实现对应函数。
❌ 误解 7：把 alice 当普通 EOA 转账，会意外绕过委托
正确：一旦委托生效，针对 alice 的交易以及 CALL/STATICCALL 等代码执行路径会解析其委托目标并执行目标代码，但执行上下文仍是 alice；同时 EXTCODE* 等代码读取指令不会把委托解析成目标合约代码。发送 ETH 时是否成功，仍取决于委托代码是否正确处理相应的 receive/fallback 路径。

7代码实操示例

7.1 一笔交易给两个不同 EOA 同时做委托，再执行 alice.execute

// authA 由 alice 签，authB 由 charlie 签；交易由 bob 发送并付 gas
const authA = await client.signAuthorization({ account: alice, contractAddress: delegateA });
const authB = await client.signAuthorization({ account: charlie, contractAddress: delegateB });

const hash = await bobWalletClient.writeContract({
  abi: SimpleDelegateAbi,
  address: alice.address,
  functionName: 'execute',
  args: [calls],
  authorizationList: [authA, authB],   // 不同账户 → 全部生效
});

7.2 把委托账户恢复成普通 EOA（清零）

// 用 address = 0x0 的授权把 alice 的 code 清空
const clearAuth = await client.signAuthorization({
  account: alice,
  contractAddress: '0x0000000000000000000000000000000000000000',
});
const hash = await bobWalletClient.sendTransaction({
  to: alice.address,
  data: '0x',                    // 空 calldata，只做清零
  authorizationList: [clearAuth],
});

7.3 判断委托是否已生效

const code = await publicClient.getBytecode({ address: alice.address });
// 委托成功 → '0xef0100' 开头；无代码 → null（或 RPC 返回空代码时为 '0x'）
const delegated = code !== null && code.startsWith('0xef0100');
⚠️ 实操提醒
若 execute(calls) 业务逻辑会 revert，请先确认你是否希望委托保留。若不该保留，需要在业务失败时补一笔清零交易——委托不会因为你业务失败就自动消失。

8快速记忆

一句话记住整个机制：

authorizationList = 「批量的写委托开关」，一笔交易内顺序处理；
同账户多条 → 取最后，不同账户 → 全部生效，单条失败只跳过自己；
委托一旦写入就是持久状态，业务失败不撤销、后续交易不自动还原；可以再次授权到其他实现，也可以通过零地址授权显式清除。

「列表只活在当前交易，委托状态持久存在」——记住这句就够了。

销毁合约 → 0x
活合约 → 0x字节码

委托是 持久状态
