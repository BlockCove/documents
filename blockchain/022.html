0产品总览

CRE 与 VRF 的定位不同：CRE 是面向机构级智能合约的全栈编排层；VRF 是提供可验证随机性的专用服务。二者都属于 Chainlink 平台能力，但不应理解为同一层级的产品。

CRE — Runtime Environment

CRE 是 Chainlink 的全栈编排层。开发者使用 TypeScript 或 Go SDK 编写 Workflow，由 CRE CLI 编译为 WASM 二进制并部署到 DON；Workflow 可组合链上/链下数据、API、计算、合规、隐私及跨链等能力。

VRF — Verifiable Random Function

可验证随机函数，Chainlink 的核心随机性服务之一（2019 年上线）。它利用密码学证明生成可验证随机数，使消费者合约能够在链上验证结果与指定请求输入及预言机密钥相符；它是许多区块链游戏、NFT 和其他需要可验证随机性的应用的重要基础设施。

一句话区分 CRE 解决的是「智能合约如何与真实世界系统安全协作」的编排问题；VRF 解决的是「链上如何获得可信随机数」的密码学问题。两者可以独立使用，也可以在 CRE 工作流中调用 VRF 能力。

1CRE 核心架构

CRE 将 Automation、Functions 等历史上独立的能力升级为统一的 Workflow 模型，并提供更丰富的触发器、Capability、共识与隐私能力；因此更准确地说，CRE 是其后继/统一编排层，而不是严格意义上的“超集”。

1.1 定位与设计哲学

CRE 的全称是 Chainlink Runtime Environment，官方定义为「解锁机构级智能合约的全栈编排层」。机构级智能合约需要同时满足四个条件：

  • 数据连接（Data-connected）——能安全读取外部 API、链上状态和专有数据
  • 合规就绪（Compliance-ready）——可集成 KYC/AML、地址黑名单、额度策略等合规检查
  • 隐私保护（Privacy-preserving）——支持 TEE 飞地执行，敏感逻辑和密钥不暴露给节点运营商
  • 跨链互操作（Interoperable）——原生集成 CCIP，可跨公有链、私有链和传统系统执行

1.2 Trigger-and-Callback 编程模型

CRE 采用「触发器 + 回调」的代码优先开发模式，这是 CRE 工作流的核心架构模式：

Trigger 触发器事件源 · 何时执行
→
Handler 处理器连接 Trigger 与 Callback
→
Callback 回调函数业务逻辑 · 做什么
→
Capability 能力调用HTTP / EVM / 签名
→
DON 共识验证BFT 聚合结果
Trigger（触发器）

工作流的「何时」。当前文档列出的核心触发器包括 Cron（定时调度）、HTTP（外部请求触发）和 EVM Log（监听链上事件触发）。具体调度限制与配额应以当前 CRE 文档为准，不宜写死一个通用的“最小 30 秒”。

Callback（回调）

工作流的「做什么」。包含核心业务逻辑的函数，每次触发器触发时独立、无状态地执行。在回调中通过 SDK 客户端调用各种 Capability。

Handler（处理器）

连接单个 Trigger 与单个 Callback 的胶水。一个工作流可定义多个 Handler，也可将同一个 Callback 挂载到多个 Trigger 上实现复用。

无状态执行模型 每次触发器触发 = 一次全新的独立执行。回调函数是无状态的，执行间不保留持久状态，返回值仅代表本次执行的结果。这确保了工作流的可重入性和可验证性。

  • Workflow DON——负责编排整个工作流，监听触发器、协调执行、聚合结果。工作流被编译为 WASM 二进制后部署到 Workflow DON 上运行。
  • Capability DON——专门执行特定任务的能力网络，如 HTTP 数据获取、EVM 链上读写、机密 HTTP 调用等。每个能力由独立的 DON 提供，结果经过 BFT 共识聚合。
内置共识是 CRE 的核心安全保证 能力执行会由 DON 中的多个独立节点执行，并通过 BFT 共识对结果进行验证与聚合，以降低单点故障和单节点作恶带来的风险。这里的“正确”应理解为在给定信任假设和共识规则下得到一致、经过验证的结果，而不是对外部数据真实性的绝对保证。

1.5 机密工作流（Confidential Workflows）

CRE 提供 Confidential Workflows、Confidential HTTP 等隐私能力，可结合门限加密与 TEE，在支持的场景中保护敏感工作流、数据和密钥材料，降低节点运营商直接看到明文的风险。隐私保证取决于具体 Confidential Compute 架构、加密流程与 TEE 及其证明机制，不宜概括为“所有节点都完全不可见”。

何时需要机密执行

钱包私钥、交易所 API 密钥、支付网络凭证、LLM 付费密钥、专有评分模型、交易策略、风险阈值——任何泄露会造成经济损失或策略被抢跑的场景。

普通 DON 执行即可

公开数据 API 密钥（天气、行情、体育数据）、公开钱包地址、公共 RPC 凭证等低敏感度信息，常规 DON 执行已足够安全。

2CRE 重点使用场景

CRE 的价值在于将「链上智能合约」与「链下真实世界系统」编织成可验证、可审计、可合规的端到端工作流。以下是官方资料中已有展示或明确可由 CRE 构建的代表性场景；其中部分属于演示、试点或可构建模式，不应一律表述为已规模化商用。

1
稳定币发行（Stablecoin Issuance）

金融机构和稳定币发行方利用 CRE 编排端到端的跨链稳定币发行流程，涵盖存款捕获、储备证明（PoR）验证、合规检查（ACE）、链上铸造和跨链交付。整个流程分为「验证与铸造」和「合规与发行」两个阶段。

银行/托管人 → 外部事件/HTTP → 储备与合规检查 → 链上 Mint → CCIP 跨链交付 → 目标链接收方

关键价值：将传统金融系统、合规策略、链上铸造与跨链流程连接起来。CRE 可作为这些系统之间的编排层，但具体消息标准、合规流程和发行基础设施取决于机构方案，不能概括为一个固定的“SWIFT MT103 → Mint”标准流程。

2
通证化资产服务（Tokenized Asset Servicing）

CRE 可以作为链下系统、外部 API 与链上智能合约之间的编排层，实现事件驱动的数据同步和状态更新。具体数据库、云服务和资产标准应根据实际项目确定，并非 CRE 固定绑定某一种数据库或 NFT 标准。

链上事件 → CRE EVM Log Trigger → 数据处理/校验 → 链下系统 ｜ 链下状态变化 → HTTP Trigger → CRE Workflow → 生成报告 → 链上合约更新

关键价值：消除链上链下状态不一致的运营瓶颈，事件驱动替代手动轮询，发行方、托管人、过户代理人和合规工具始终保持同步。

3
AI 驱动的预测市场结算

CRE 结合 LLM（如 AI 模型 + 外部搜索/数据源）实现预测市场的自动化、可审计结算。当市场合约发出 SettlementRequested 事件时，CRE 自动触发工作流，调用 AI 判定结果（含置信度和引用来源），生成经过 DON 共识验证的结果/报告后写入链上合约完成结算。低置信度案例自动升级人工复核。

链上 SettlementRequested 事件 → CRE LogTrigger → Gemini AI（搜索接地）→ 结构化判定结果 → 加密签名报告 → 链上 onReport() → Firestore 审计留痕

关键价值：将 AI 的概率推理与区块链的确定性保证结合，减少人工干预、缩短结算时间、支持依赖多源证据的复杂市场，全程可审计。

4
AI Agent + x402 微支付触发可验证工作流

Chainlink 已展示 x402 与 CRE 的组合方式：AI Agent/客户端可以通过 x402 支付并调用 CRE 工作流，Workflow 对输入、规则和执行结果进行验证与编排。这里的 x402 是支付/调用模式，不是 CRE 本身的支付系统。Agent 决定做什么，但验证和执行在 CRE 中完成，确保 Agent 的行为受规则约束、结果可审计。

AI Agent 决策 → x402 支付凭证 + 请求 → CRE 验证支付 → 策略/合规检查 → 链上写入结果 → 可验证审计轨迹

关键价值：解决 AI Agent「黑箱操作」的信任问题。Agent 可以自主行动，但每一步都经过共识验证和策略约束，为 AI 驱动的链上经济提供安全基础设施。

5
自定义储备证明（PoR）数据馈送

开发者用 CRE 构建自定义的链下数据到链上的数据管道。工作流定时（Cron）或按需（HTTP/Log Trigger）获取外部 API 数据（如储备余额），读取链上代币总供应量，计算对比后生成签名报告写入链上。支持主动（定时/HTTP）和被动（事件驱动）两种执行路径。

Cron/HTTP/Log Trigger → HTTP 获取储备数据 → EVM Read 读取供应量 → 计算/格式化 → 签名报告 → EVM Write 写入链上

关键价值：无需管理独立的中间件或基础设施，即可构建类似 Chainlink PoR 的自定义数据馈送，支持本地模拟和测试网验证。

2.6 机密工作流专属场景

以下场景的核心逻辑或数据必须在 TEE 飞地内执行，以防止被节点运营商或外部观察者预测、抢跑或复制：

自动清算保护

监控杠杆头寸的抵押品健康度，在清算前自动平仓或调整。风险阈值和防御策略在飞地内执行，防止被预测和抢跑。

自动投资组合再平衡

当投资组合偏离目标配置超过阈值时自动再平衡。配置策略和交易规模在飞地内决策，防止被对手方预判和交易。

AI 驱动的交易/合约审查

在交易执行前用两个独立 LLM 审计拟议交易/合约，合并风险标记后输出 ALLOW/DENY/MANUAL_REVIEW 判定。评估标准和 API 密钥在飞地内保密。

自动交易策略

基于私有策略执行交易逻辑。策略本身在飞地内运行，即使最终交易上链公开，策略逻辑也不会被复制或被抢跑。

自动支付编排

生成银行转账、支付网络、私有链代币化存款的支付指令。路由逻辑和账户详情在飞地内保护，不暴露给节点运营商。

自动风险管理

持续评估风险敞口并触发保护动作。定义何时采取行动的阈值和参数在飞地内保密，防止被逆向工程或博弈。

3VRF 核心原理

Chainlink VRF（Verifiable Random Function）是 Chainlink 提供的可验证随机性服务，通过密码学证明让消费者合约能够验证随机结果的正确性。它解决了区块链原生无法产生安全随机数的根本问题——链上执行本身是确定性的。区块哈希、时间戳等链上值虽然带有一定不可预测性，但出块者在协议约束下对部分值拥有影响空间，应用若直接依赖单一区块属性作为高价值随机源，可能遭受操纵、选择性不发布或重组等风险。

3.1 为什么链上需要 VRF

链上随机数的困境

区块链是确定性状态机。区块哈希、时间戳、区块难度等「看似随机」的值都可被出块者操纵或预测。直接使用这些值作为随机数，在博彩、抽奖、NFT 盲盒等高价值场景中会被恶意利用。

VRF 的解决方案

将随机数生成移到链下（预言机节点用私钥 + 不可预测的种子计算），但结果附带密码学证明，任何人都可以在链上验证结果确实由指定节点按指定种子正确生成，无法篡改。

3.2 两步工作流程

VRF 的核心是「请求-履行」两步异步流程：

消费者合约
VRF Coordinator
Chainlink 预言机节点
1
请求随机数 链上
消费者合约调用 Coordinator 的 requestRandomWords，提交 keyHash、订阅/支付信息、确认数、callbackGasLimit、numWords 等请求参数；Coordinator 为请求建立记录。最终随机输入会结合请求相关信息以及稍后确定的区块哈希，而不是简单地由用户直接提供一个“未知 seed”。
2
链下生成随机数 + 证明 链下
VRF 节点使用其私钥及协议规定的请求输入执行 VRF 计算并生成输出和证明；节点不能在证明仍有效的前提下任意替换输出。计算是确定性的，节点无法自由选择输出值，唯一作恶方式是不响应。
3
提交结果到链上 链上
节点将随机数和密码学证明（proof）提交到 VRF Coordinator 合约。
4
链上验证证明 验证
Coordinator 在链上验证 VRF 证明，确认输出与请求输入及对应公钥匹配；验证失败时该履约不会按正常流程完成。
5
回调消费随机数 链上
验证通过后，Coordinator 调用消费者合约的 fulfillRandomWords(requestId, randomness[]) 回调，将随机数传递给业务逻辑（如 mint NFT、选 winner、掷骰子）。
密码学保证的核心 VRF 输出由预言机私钥和请求输入确定。节点不能在保持有效证明的同时任意挑选另一个输出；如果节点选择不履行请求，则表现为可用性问题。关键安全点在于请求输入包含请求后才能确定的区块哈希等信息，使节点在生成证明时不能事先自由选择最终输出。

3.4 两种资助模式

订阅模式（Subscription）

创建 VRF 订阅账户并预充值（LINK 或原生代币），多个消费者合约共享同一订阅余额。请求履行后根据 VRF 服务的计费规则从订阅余额中扣费，实际费用还与网络 gas、服务费等因素有关；无需每次请求前单独为消费者合约准备付款余额。

适合：高频请求、多合约项目、企业集中计费和成本控制。优势：降低总 gas 成本，简化资金管理。

直接资助（Direct Funding）

消费者使用 v2.5 Direct Funding wrapper 机制，以请求时提供的支付资产承担该次随机数请求的费用；具体可用支付资产和计费方式取决于目标网络与对应部署。需要确保合约有足够资金支付随机数请求。

适合：低频请求、单个合约、简单集成。优势：无需管理订阅，集成更简单，合约自包含。

3.5 关键安全参数

  • keyHash / gas lane：用于选择 VRF Coordinator 支持的 gas lane（对应一组服务配置），而不是简单地指定某一个预言机节点。不同 gas lane 对应不同的最大 gas price / 服务配置。
  • minimumRequestConfirmations：请求被节点处理前需要等待的区块确认数。确认数越高，抗重组攻击能力越强，但延迟越高。高价值场景建议设置较高值。
  • callbackGasLimit：消费者回调可使用的 gas 上限。必须足够执行业务逻辑；若回调耗尽 gas，随机数履约并不等于你的业务逻辑一定成功，消费者需要正确处理这种情况。
  • numWords：单次请求的随机数数量（v2/v2.5 支持一次请求多个 uint256 随机数），减少请求次数和 gas 成本。

4VRF 重点使用场景

Chainlink 官方列出了 35+ 种 VRF 使用场景。以下按领域分类，聚焦最具代表性和商业价值的落地场景。

4.1 区块链游戏

游戏是 VRF 的重要应用领域。区块链游戏的核心特征是生成稀缺的游戏物品（多为 NFT），物品的稀缺性需要客观证明，且开发者和外部人员都无法操纵生成结果。

随机战利品掉落

击败 Boss 或完成任务后，用 VRF 决定掉落物品的种类和稀有度。确保稀有装备的掉落概率公开可验证，开发者无法暗改掉率。

角色属性生成

创建角色时随机生成力量、敏捷、智力等属性值，或决定角色的职业、天赋、初始技能。每个角色的属性都是唯一且可验证的。

战斗结果判定

回合制战斗中的暴击、闪避、命中判定，或卡牌游戏中的抽牌顺序、随机事件触发。确保战斗公平，双方都无法操纵随机性。

随机地图/关卡生成

Roguelike 类游戏中用 VRF 生成随机地图布局、敌人分布、宝箱位置。每局游戏的地图都是唯一的，且种子可复现。

4.2 NFT 与数字藏品

盲盒 / Reveal 机制

NFT 铸造时不暴露属性，购买后用 VRF 随机分配属性并 reveal。降低在随机结果生成前提前挑选稀有属性的空间；具体防作弊效果仍取决于 mint、reveal 和随机数消费的整体设计。

稀有 NFT 分发

在空投或公售中，用 VRF 随机决定哪些地址获得稀有版本 NFT。分发过程完全透明，项目方无法偏袒特定地址。

随机属性组合

为 PFP（头像类）NFT 随机组合背景、服装、配饰、表情等特征，生成独一无二的 NFT。属性分布和稀有度可链上验证。

NFT 抽奖铸造

热门 NFT 项目供不应求时，用 VRF 从白名单中随机抽取获胜者获得铸造资格。公平分配，杜绝科学家抢跑和机器人垄断。

4.3 DeFi 与链上金融

公平发射 / 随机空投

代币公平发射（Fair Launch）中，用 VRF 从符合条件的地址中随机选择早期参与者或分配额外奖励。可用于随机抽取或分配，但 VRF 本身不能解决巨鲸或女巫问题；资格集合、身份和额度规则仍需要应用层设计。

随机清算选择

在借贷协议中，当多个清算人同时竞争同一笔清算时，用 VRF 随机选择清算人。可用于设计随机选择机制，但 VRF 本身不会自动消除 MEV；随机选择何时发生以及候选集合如何确定仍需协议设计。

流动性挖矿随机奖励

为流动性提供者设计随机奖励机制，如每隔一段时间随机抽取部分 LP 获得额外代币奖励。增加挖矿趣味性和用户粘性。

预测市场随机事件

部分预测市场需要模拟随机事件（如体育比赛中的随机因素），或在结果争议时用 VRF 选择仲裁委员会成员。

4.4 DAO 治理与社交

随机委员会选择

DAO 治理中用 VRF 随机选择委员会成员（如 Grants 评审委员会、仲裁委员会），防止权力集中和游说腐败。被选中者可验证自己是公平选出的。

随机验证者/排序

在需要多签验证或排序的场景中，用 VRF 随机选择验证者或随机排列提案投票顺序，减少投票策略行为和羊群效应。

社区抽奖活动

项目方举办社区活动（如转发抽奖、AMA 抽奖）时，用 VRF 从参与者中公平抽取获奖者。抽奖过程链上可验证，杜绝「内定」嫌疑。

随机配对/匹配

社交类 dApp 中用 VRF 实现随机配对（如匿名聊天、导师匹配、交易对手匹配）。确保配对公平，无法被算法操纵。

4.5 博彩与竞猜类 dApp

这是 VRF 最直接的应用场景，但也是合规风险最高的领域。 掷骰子、硬币翻转、轮盘、老虎机、彩票等纯随机博彩类 dApp 是 VRF 的经典用例——随机结果可由 VRF 生成并被链上验证，从而降低运营方操纵随机结果的空间；但公平性仍取决于应用本身如何设计请求、结果消费和奖池/赔率逻辑。但在中国大陆等司法管辖区，线上博彩属于非法活动，开发者需严格遵守当地法律法规。

5CRE 与 VRF 的对比与协同

两者定位不同但可以互补：CRE 是编排层，VRF 是密码学原语。在 CRE 工作流中可以通过 EVM Write 触发 VRF 请求，或将 VRF 作为工作流的一个能力节点。

  • CRE 编排 + VRF 提供随机性：CRE 工作流在执行业务逻辑时，通过 EVM Write 调用链上合约触发 VRF 请求，VRF 生成随机数后回调业务合约。CRE 负责整体流程编排；VRF 作为独立随机性服务，为需要可验证随机性的环节提供随机数。二者可以通过链上合约或其他受支持的工作流方式组合。（如随机选择清算人、随机分配 NFT 属性）。
  • CRE 机密工作流 + VRF：机密 CRE Workflow 可以保护工作流本身及敏感输入，但 VRF 输出一旦用于公开链上业务，通常最终会成为可验证的链上数据。因此“随机结果不提前暴露”不能单靠 VRF 或 TEE 保证，需要从请求、等待、揭示和结算时序整体设计。
  • AI Agent + CRE + VRF：AI Agent 可通过 x402 调用 CRE Workflow；Workflow 再组合其他受支持的能力。若业务还需要可验证随机性，可把 VRF 作为独立随机性组件加入整体架构，但不要把 VRF 描述成 CRE 内置的通用 Capability。

6总结

CRE 和 VRF 分别代表了 Chainlink 预言机网络的两个发展方向：CRE 向「机构级全栈编排」演进，VRF 向「公平随机性密码学原语」深耕。

CRE 的核心价值

将传统金融系统、合规框架、AI 服务和多链生态编织成可验证、可审计、可合规的端到端工作流。它是 Chainlink 从「数据预言机」向「链上金融操作系统」演进的关键产品，已获得 SWIFT、摩根大通、ANZ、Visa、Mastercard 等顶级机构的采用。

VRF 的核心价值

为区块链提供了第一个可公开验证的公平随机数源，是链上游戏、NFT、DeFi、DAO 治理等场景的公平性基石。经过 v1→v2→v2.5 的持续迭代，已支持原生代币支付、统一 Coordinator 地址和优化的 gas 效率，是 Chainlink 最成熟、使用最广泛的服务之一。

选型建议
  • 需要连接传统系统、编排多步流程、集成合规/AI/跨链 → 使用 CRE
  • 只需要链上公平随机数（游戏、NFT、抽奖、治理） → 使用 VRF v2.5
  • 复杂应用中两者可以同时使用：CRE 做编排，VRF 做随机数原语
  • 现有 Chainlink Automation 用户应按官方迁移指南迁移到 CRE；截至 2026 年，Automation 正在弃用
  • 新的 VRF 集成应优先采用当前推荐的 v2.5；v1/v2 主要涉及已有集成的维护与迁移。
